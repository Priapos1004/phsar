## Block 0 — returning to the page you were on after signing in (`a2a8831`)

Already committed when this doc was started, so its reasoning was never written
down. What is worth recovering at PR time, from the code and the commit:

- Two carriers, split by what fits where: the **route** travels as `?next=` on
  the login URL (`utils/returnTo.ts`), the **filters** as a per-tab
  sessionStorage stash (`utils/resumeSession.ts`, `phsar.resume`, 3h TTL, bound
  to the token's `sub`). Neither carrier reaches on its own — a hard
  `window.location.href` hands nothing forward, and a shared link opened in a
  fresh tab has no stash to read.
- `safeReturnPath` deliberately validates the *origin* rather than allowlisting
  routes: an allowlist breaks silently when a route is added, a resolve-check
  cannot.
- The stash is one-shot and removed on read whatever the verdict, so nothing
  survives into a second login. "Cannot prove this is the same user" lands on
  the same side as "different user" — the untested case is the one that would
  otherwise leak a filter set.
- `persistedFilter`'s self-registering registry was added here, so no whole-set
  operation (reset / snapshot / restore) can miss a filter the way the
  hand-maintained `bell-session.ts` key list can.

## Block 1 — `aired_from` / `aired_to` become `Date`

### Why this happened at all

It was not on the plan. It surfaced while scoping the airing end-date line
(Block 2): the question "should we render the date in the viewer's timezone?"
has no good answer while the column is a `DateTime(timezone=True)` holding a
padded midnight, because **there is no time of day to convert**. Fixing the type
first meant the Block 2 formatter could be written once, against
`"2026-09-21"`, instead of written around the padding and rewritten later.

### What MAL actually sends — researched, not assumed

- `start_date` / `end_date` are bare calendar dates (`yyyy-mm-dd`), documented
  with **no timezone**. They are the Japanese broadcast dates shown under
  "Aired:" on the site.
- `broadcast` carries `day_of_the_week` + `start_time` (`"23:30"`) — a
  time-of-day, also with no timezone in the field itself. MAL's site renders it
  "(JST)"; Jikan, scraping the same source, normalizes it with an explicit
  `timezone: "Asia/Tokyo"`. JST is the de-facto answer.
- **`broadcast` is not in `_DETAIL_FIELDS`** — this repo has never fetched it.

### Key decisions

- **`Date`, not `timestamp without time zone`.** Dropping only the zone keeps a
  meaningless `00:00:00` and still invites `new Date(iso)` on the frontend. It
  buys honesty about the timezone and nothing else, for the same migration
  cost. `Date` makes "MAL sent no time of day" structural, and serializes as
  `"2026-09-21"` — the hazard is removed rather than documented.
- **Render the published date verbatim, for every viewer** (the decision Block 2
  consumes). Rejected: converting to the viewer's zone. It is not localization
  when the source has no time — it just moves the date a day west of Greenwich.
  Also rejected: re-anchoring the pad to midnight *JST*, which sounds more
  principled and is worse — midnight Asia/Tokyo is 17:00 the previous day in
  Berlin, so a European viewer would start seeing the day before the one MAL
  publishes.
- **`parse_mal_date` is lenient — malformed input is None, not an exception.**
  The first cut used `date.fromisoformat`, which rejects anything but a bare
  date, on a fail-fast argument. That died with the parser collapse below: the
  surviving function also serves the MAL wire form, where partial and malformed
  values are routine, and the sweep's air-date comparison now shares it — so one
  bad record must not abort the run holding it. The old full-ISO strings in
  historical `result_summary` rows are render-only and never re-parsed, so
  nothing depends on rejecting them.

### Gotchas & learnings

What made this its own commit block rather than a line in Block 2:

1. **The sweep diff would have silently flooded.** `_apply_media_diff` compares
   `media.aired_to != new_aired_to`. A `date` never equals a `datetime`, so
   retyping the column without retyping the shared parser reports **every media
   as drifting on every sweep** — stability counters reset catalogue-wide.
   Worse, `aired_from` deliberately does **not** flip `changed`, so its half of
   the bug is invisible: it rewrites the column and floods `result_summary`
   while every existing test still passes. That is why the new regression test
   asserts the diff **sink is empty**, not just that `changed` is False.

2. **`timestamptz::date` resolves through the session `TimeZone`.** Demonstrated
   against the dev DB under `America/Los_Angeles`:

   ```
   bare  ::date          -> 2026-09-20   <-- the trap
   (v AT TIME ZONE 'UTC')::date -> 2026-09-21
   ```

   A bare cast on a server whose TimeZone is not UTC moves every date back a
   day, silently and permanently. CI's container runs UTC, so CI would never
   have caught it. The migration writes the `USING` clause out for both columns.

3. **`_jsonable` needed widening — but not the way it first looked.** A pure
   `date` is not an instance of `datetime`, so the existing check let it fall
   through to `json.dumps`, which raises: the sweep's JSONB write would have
   broken on the first air-date drift.

   Two wrong turns before the one-line answer, both worth recording:

   - The first fix added a second branch with `datetime` checked first, on the
     reasoning that `datetime` subclasses `date` and the reverse order would
     truncate timestamps. **That reasoning was wrong** — `.isoformat()` is
     polymorphic, so both branches did the same thing and there was no order to
     pin. The test written to pin it passed with the branches deliberately
     swapped, which is how it was caught.
   - The replacement test then pinned *datetime* precision, which review showed
     is unreachable: after this change no field reaching `_jsonable` is a
     datetime at all. `aired_from` / `aired_to` were the last ones. So the test
     was deleted rather than rewritten — the end-to-end sink test already
     covers the date case, `json.dumps` included.

   Two method notes fell out. **A new test is not a guard until it has been
   seen to fail** — sabotaging the code is the only way to tell a real guard
   from a vacuous one in a green run. And **a comment defending a branch is
   worth less than knowing whether anything reaches it**: the "don't flatten
   timestamps" note was protecting a case production cannot produce.

4. **Collapsing the two parsers was a consequence, not a cleanup.** Before the
   retype, `parse_mal_datetime` and `_mal_date_to_datetime` read genuinely
   different string forms — the storage form (full ISO, with a `Z` fixup) and
   the MAL wire form (partial `YYYY` / `YYYY-MM`). Normalizing storage to
   `YYYY-MM-DD` collapsed both onto one form, leaving two bodies and two
   docstrings each claiming to be "the shared parser". One lenient
   `parse_mal_date` now serves both, and malformed input returns None rather
   than raising, because the sweep's air-date comparison shares it and one bad
   record must not abort the run holding it.

   The general shape: **changing a serialization format can silently make two
   functions redundant that were previously distinct.** Nothing fails; they
   just stop differing.

### Reviewed and deliberately not changed

**The sweep-tier SQL still compares `aired_from` against `now()`** —
`_is_recent_main` and the archival cutoff in `daos/anime_dao.py`. Those were
type-matched (`timestamptz` vs `timestamptz`) before the retype and are now
cross-type, so Postgres promotes the date through the session `TimeZone`.

Measured before deciding, because the obvious worry did not hold: **the
index-only scan on `ix_media_main_aired_from` survives both forms** — Postgres
pushes the cross-type comparison into the Index Cond, so there is no per-row
cast and no plan regression. What remains is a sub-day shift in where the 5-year
and archival boundaries fall, and `current_date` is *also* session-TimeZone
dependent, so there is no TimeZone-independent target to move to — only a
type-matched one.

Left alone because changing sweep-tier membership semantics is a different
change from a type retype, and this query family was tuned against a prod dump
in v0.15.4. Worth revisiting deliberately, with the tier tests as the check;
they now seed real `date` values, so they can actually exercise it.

### Future work / debt

- **Scrape `broadcast.start_time` and make the air date genuinely viewer-local.**
  `end_date` + JST `start_time` is a real instant, and late-night anime air
  22:00–01:00 JST — which lands mid-afternoon in Europe and morning in the
  Americas, so the local date matches, and where it *does* differ the local date
  is the honest answer. Needs: `broadcast` added to `_DETAIL_FIELDS`, a
  `Media.broadcast_time` column + migration, sweep volatile-bucket wiring, and a
  combine step at the schema boundary. **Caveat that decided the deferral:** it
  reads null for the entire existing catalogue until each media's next sweep
  refresh reaches it — weeks for the long tail — so every row falls back to the
  verbatim date anyway in the meantime. Pairs naturally with this block: same
  columns, same sweep-diff path, same traps.
- **Partial-date precision is still unrecoverable.** MAL emits `YYYY` and
  `YYYY-MM` for older records and the scraper fills the missing parts with `01`,
  so a stored `2011-01-01` may mean "sometime in 2011". The `Date` column does
  not fix this — recording precision would need a second column. The containment
  Block 2 relies on is to render a date only for **Currently Airing** titles,
  where imprecise values are rare; revisit if anything ever wants to show a
  finished title's air range.

## Block 2 — "Currently Airing until Sep 19"

### Key decisions

- **Inside the existing green badge, not a new line or a fact-grid cell.** The
  date qualifies the status, so it reads as part of it. Rejected: a muted
  sentence under the badge, and a second line in the `Calendar` fact cell —
  both make it a separate fact the eye has to reassemble.
- **Currently Airing only.** `aired_from` for unaired titles and full ranges for
  finished ones were both considered and dropped: MAL pads partial dates to the
  1st and those cluster in old finished records, so a day-precision render there
  would be a lie. The scoping lives in `airingStatusParts`, which returns before
  the date is ever composed for the finished/unaired branches — a template `{#if}`
  would have put the same rule in two places.
- **The year is dropped when it matches the current one.** A show airing now
  almost always ends inside it, and "until Sep 21" is the shorter read; a show
  running into next year still says so.
- **`until X` composes *before* `+ upcoming content`**, never after. "Currently
  Airing + upcoming content until Sep 19" parses as though the *upcoming* content
  ends on that date. The date belongs to the airing.
- **The anime aggregate takes MAX over the currently-airing media**, so a
  franchise with two seasons in flight reads to the later one — the badge claims
  "the airing content runs until X", which the earlier date would understate.
- **The badge wraps only under width pressure.** First cut forced the qualifier
  onto its own line with `basis-full`; corrected to `whitespace-nowrap` on the
  qualifier inside a `flex-wrap` container, so a roomy badge stays single-line and
  a cramped one breaks before the `+` rather than inside the phrase.

### Where the date deliberately does NOT appear

Only the two detail heroes show it. Three surfaces that render the same status
string stay dateless, and all three by the same mechanism — **they call
`formatAiringStatus` with two arguments and simply never pass the third**:

- **The share card** (`utils/shareContent.ts`, `statusBadges`). A shared PNG
  travels without the app around it and never refreshes, so a date baked into it
  is wrong the moment the season ends — and unlike the page, nothing will ever
  correct it. The card is also a fixed layout budget where a longer status pill
  costs space that the score and attribute profile need more. `statusBadges`
  already documents that it passes `false` for the media grain; the air date is
  the second thing it deliberately declines.
- **Search result cards** (`MediaInfo.svelte`) — decided up front: search is for
  finding a title, not reading its schedule, and the anime-view card would need a
  new aggregate field shipped on every row to show one.
- **The related-media carousel** (`RelatedMediaCarousel.svelte`) — sibling tiles
  are navigation, and `MediaSibling` carries no dates at all.

Making the parameter optional is what keeps this cheap: the exclusion needs no
guard and no branch, and a future caller that *should* show a date opts in by
passing it. The cost is that the exclusion is invisible at those call sites —
hence this note, and the assertion in `format-string.test.ts` that the two-argument
form is unchanged.

### Gotchas & learnings

- **`formatAirDate` must never let the string reach `Date`.** A bare
  `YYYY-MM-DD` parses as UTC midnight, so `new Date(ymd).toLocaleDateString()`
  renders the previous day for every viewer west of Greenwich. It splits the
  string, builds from `Date.UTC(...)` and reads back with `timeZone: 'UTC'`.
  A second formatter beside `formatShortDate` rather than a change to it — that
  one takes real timestamps, where the viewer's zone *is* the right answer.
  (`Date.UTC` rolls over rather than rejecting, so the parts are range-checked;
  month 13 would otherwise render as the following January.)
- **The vacuous-test trap, again, in a new disguise.** The first version of the
  timezone guard looped over `process.env.TZ` and asserted the rendered value.
  Node reads `TZ` once at startup, so reassigning it mid-run changes nothing —
  and CI runs UTC, where the correct and the broken implementations agree. The
  test passed under a deliberately Date-based implementation. It now spies the
  `Date` constructor and asserts no construction was handed a *string*, which
  fails under UTC. **Where an invariant is "this code path is never taken",
  assert on the path, not on an output that only differs in an environment CI
  does not run.**
- **The guard shaped the implementation, then review reshaped both.** The first
  cut avoided `Date` entirely with a hand-rolled month table, because that was
  the version the spy test could protect. Review pointed out the table
  duplicates what `Intl` already does two functions below. Building from
  `Date.UTC` and formatting at `timeZone: 'UTC'` gets both: no table, and a
  guard that still holds because the assertion narrowed from "no Date" to "no
  Date *parsed from a string*" — which is the actual hazard. **A guard that
  forces an awkward implementation is usually a guard pointed at the wrong
  invariant.**

## Block 3 — the back button returns to the item you clicked

### Key decisions

- **The detail page IS the item that was clicked, so its own `uuid` is the
  anchor.** `focusUuid = searchParams.get('focus') ?? searchParams.get('uuid')`,
  travelling back on the back link as `?focus=` and propagating across
  anime↔media hops exactly like `q` / `from` / `job`. The `??` fallback is what
  removes any need for list-side href changes — six components gained a
  `data-focus-uuid` attribute and nothing else.
- **Propagating rather than using the current page's uuid** is what makes a deep
  dive work: after search → anime → media, back-to-search centres the *anime*
  card, which is the only one of the two present in an anime-view result set.
- **The back link emits `focus` only to targets that consume it**; every detail
  hop *carries* it regardless. The plan's prose said only `ratings-stats` is
  excluded, but its own scope table also excluded library / curation /
  completion / job — the table won, because a param nothing reads and nothing
  strips is URL cruft. Carrying it anyway means opting one of those in later is a
  one-line `BackLink` change.
- **The Jobs Log page offset joined the persisted filter** instead of staying
  component state. It is a list control with the same lifetime as the filters
  beside it, so `filterLifecycle` governs it for free — and it fixes the
  standalone bug where page 3 → a job → back landed on page 1.
- **Scroll state is app-owned and URL-keyed**, the same call `filterLifecycle`
  already made for filter state and for the same reasons; its header argues why
  SvelteKit's `snapshot` fits neither.

### Gotchas & learnings

1. **Stripping `?focus=` re-runs the page that stripped it.** `replaceState`
   updates `page.url`, and `/search` reloads on `page.url` — so tidying the param
   away refetched the results and reset `visibleCount` to 20, undoing the restore
   a microsecond after it happened. The load effect is now keyed on what the
   results were loaded *for*. **A page that reloads on `page.url` reloads on any
   param edit, including its own housekeeping.**

2. **A scroll restore is not "scroll once the data has arrived."** That is what
   was built, and it failed differently on each surface, with the *same* code:

   | Surface | Symptom | Why |
   |---|---|---|
   | `/watchlist` | worked | ~100ms network fetch |
   | `/ratings` | landed at the top | warm `ensureRatingScores` cache resolves in a microtask, so the scroll raced SvelteKit's post-navigation `scrollTo(0, 0)` — also a microtask after mount — and lost |
   | `/search`, last card | landed too high | scroll computed before paint, against a document still laying out |
   | `/search`, last card | landed short | the page kept growing *after* any plausible settle window |

   The differences were data-source latency, not code. **A timing assumption that
   holds on a surface with a network fetch is untested, not correct** — the fetch
   is hiding the race rather than making it safe.

3. **Two dead ends before holding beat timing.** Both are recorded because both
   look right on paper:

   - *Scroll immediately, correct once 150ms later.* Fixed the position, but the
     correction is a **visible second scroll** — the page lurches twice. Rejected
     on feel, not correctness.
   - *Wait until `document.documentElement.scrollHeight` holds steady for two
     frames (capped), then scroll once.* Sound in principle and strictly worse in
     practice: the growth arrives **after** any settle window, because it is a
     store landing post-paint rather than layout finishing.

   Replaced by `pinCentred` — re-centre every frame for 600ms, release the moment
   `window.scrollY` is not what it last set. It is *less* code than either
   attempt, and it subsumes the SvelteKit race, the pre-paint measurement and the
   late growth without distinguishing between them. **When you cannot predict
   when a page stops moving, hold the target instead of timing the scroll.**

4. **The growth was diagnosed from a symptom matrix, not from the code.** One
   column fine; two columns showed half the last row; two columns after a "Show
   More" click showed none of it; media view always fine. Growth proportional to
   the rows *above* the target, present only when cards are narrow — which points
   at `MediaInfo`'s header, a `flex justify-between` whose title block has no
   `min-w-0`. A bookmark icon arriving from the async watchlist store steals
   width, the title re-wraps, and `auto-rows-fr` lifts every row in the grid to
   the new tallest. Anime-only because a media card shows the icon when *that*
   media is watchlisted, an anime card when *any* of its media is. Not fixed —
   see debt below.

5. **A background loop outlives the test that started it — twice.** Both the
   settle sampler and the pin keep scheduling frames past the end of their test
   and fire into the *next* one, against a detached node and the shared spy. Both
   surfaced as a **neighbouring** test failing with an inflated call count, which
   is the tell. The pin's teardown hands over to "the user" via the same escape
   hatch production has. **Any DOM helper that outlives its call needs a teardown
   story in the tests, and its symptom is never the test that caused it.**

6. **Sabotage caught a constant whose justification was wrong.** `SETTLED_FRAMES
   = 2` was documented as "a single sample proves nothing — any height equals
   itself", which is not the reason (one stable frame is a real signal; the real
   reason is that layout lands in fits). Nothing pinned the value at all, so
   nothing had ever contradicted the comment. The logic is gone now, but the
   shape recurs: **an unpinned constant's comment is unreviewed prose.**

7. **A `<tr>` is not a box.** Tailwind Preflight sets `border-collapse: collapse`,
   under which a table row paints no `box-shadow` — so the card treatment (a ring)
   is simply invisible on every table. Rows take a background sweep instead, which
   they *do* paint, broad and low-contrast because a narrow high-contrast band
   crosses as a **flicker** rather than as a wash going past. (Several rounds were
   spent tuning that sweep against a tint underneath it. See the post-deploy
   section below for why that tint was not there.)

### After the deploy — `color-mix()` inside `@keyframes` is silently dropped

The flash shipped broken, and the way it broke is worth more than the fix.

`@keyframes focus-flash` held `background-color: color-mix(in oklab, var(--primary)
20%, transparent)`. The production minifier emits `color-mix` fallbacks by
**duplicating the rule** that holds them — which it cannot do inside `@keyframes`,
so it discarded the whole `from` block instead:

```css
/* authored */  @keyframes focus-flash { from { box-shadow: …var(--ring); background-color: color-mix(…) } to { … } }
/* shipped  */  @keyframes focus-flash{to{background-color:#0000;box-shadow:0 0 0 3px #0000}}
```

With no `from`, an animation interpolates from each element's *current* computed
value — here, to the same value. A no-op. The identical `color-mix` in the
neighbouring `tr.focus-flash` rule was handled correctly, fallback and all, because
that one is a rule.

**It is `app.css`'s pipeline, not CSS.** `AttributeBadges`' `pill-burst` keyframes
carry six `color-mix` calls and ship whole — checked in the bundle, not assumed.
Component `<style>` blocks are minified without the fallback generation that drops
the block, so the first draft of the rule ("never `color-mix` in `@keyframes`")
would have banned a pattern demonstrably working ten files away. **An invariant
written from one instance is a guess until a second instance is checked** — and the
second instance is what turned a false rule into an accurate one.

Three things fell out of it:

1. **The rows only looked right by accident.** `focus-flash-sweep` has no
   `color-mix`, survived intact, and was doing every visible thing on a table row.
   The tint had never once rendered in production — so the rounds spent tuning the
   sweep against the tint were tuning something that was not shipping. Cards, which
   have only the ring, showed nothing at all.

2. **Every gate we own passes it.** The build *succeeds*; it just emits less CSS.
   `bun run check`, `bun run test` and even adding `bun run build` to CI are all
   green. Only a production bundle differs from dev, and only a deploy surfaces it.
   **An animation verified solely against `bun run dev` is unverified** — that is
   the durable lesson, and it generalises past CSS to anything the production
   pipeline transforms.

3. **The guard is still missing, and the reason it was dropped was wrong.** The
   attempt was a Vitest test reading `app.css`; that needs `@types/node`, which this
   frontend does not carry, and Vite's `?raw` returns an empty string because the CSS
   plugin intercepts it. Both obstacles are about reading the **source** from inside
   the test runner — but the hazard lives in the **output**, an ordinary file on disk
   after `bun run build`, greppable from CI with no dependency at all. Review caught
   that; it is recorded here because the same misaimed reasoning ("this is hard to
   test" when the artifact under test was chosen wrongly) is easy to repeat.

   Worth recording too that the abandoned test caught its own failure only because it
   carried a *guards-the-guard* assertion — "does the parser find any keyframes at
   all" — without which it would have reported a clean pass over an empty set.

Resolved by splitting the two surfaces properly rather than restoring the tint: the
row keeps sweep-only, which is what production had been showing and what was
approved on that basis, and the card keeps the ring. `flash()` then simplified —
each surface runs exactly one animation, so it clears the class on the first
`animationend` instead of matching a name. That name check would have been *wrong*
under the split: a row runs `focus-flash-sweep`, never matches `focus-flash`, and
the class would have stuck, killing every second return to the same row.

### Verification note

**jsdom has no layout, no paint and no scrolling**, so every assertion about
*when* something happens here is a timer assertion wearing a paint assertion's
clothes. Demonstrated rather than assumed: a one-frame implementation passed the
tests written for a two-frame one. The unit tests pin the arithmetic
(`pageCovering`), the URL handling (`hrefWithFocus`, `consumeFocus`) and the
lifecycle of the pin (holds, yields to the user, releases). Everything about
where the page actually lands was caught by user verification across four rounds —
and it caught all three failures.

### Future work / debt

- **`MediaInfo`'s header re-wraps when the bookmark icon lands** (gotcha 4). The
  fix is `min-w-0 flex-1` on the title block plus a reserved slot for the icon, so
  card height stops depending on an async store. Deferred because the pin makes it
  invisible, and it changes a shared component's layout on a diagnosis verified by
  symptom rather than by measurement. Worth doing on its own terms: a grid whose
  row heights depend on fetch timing will surface again somewhere else.
- **A white flash when scrolling immediately after returning to anime search.**
  Observed, reproducible-ish, not diagnosed. Plausibly a large repaint of
  never-painted content below the fold; unrelated to the scroll restore, which no
  longer moves the page by then.
- **The `target="_blank"` comments** in `admin/MediaChangeCard.svelte` and its
  job-detail mirror argue that change cards open in a new tab *because* returning
  would lose scroll position. Still true — those admin surfaces are out of scope —
  but the mechanism to revisit them with now exists.
- **The excluded back-link targets** (statistics, library, curation, completion,
  job detail) each opt in with one `hrefWithFocus` call plus an anchor attribute,
  since the uuid already travels to all of them.
