## Block 0 — returning to the page you were on after signing in (`a2a8831`)

Already committed when this doc was started, so its reasoning was never written
down. What is worth recovering at PR time, from the code and the commit:

- Two carriers, split by what fits where: the **route** travels as `?next=` on
  the login URL (`utils/returnTo.ts`), the **filters** as a per-tab
  sessionStorage stash (`utils/resumeSession.ts`, `phsar.resume`, 3h TTL, bound
  to the token's `sub`). Neither carrier reaches on its own — a hard
  `window.location.href` hands nothing forward, and a shared link opened in a
  fresh tab has no stash to read.
- `safeReturnPath` deliberately validates the *origin* rather than allowlisting
  routes: an allowlist breaks silently when a route is added, a resolve-check
  cannot.
- The stash is one-shot and removed on read whatever the verdict, so nothing
  survives into a second login. "Cannot prove this is the same user" lands on
  the same side as "different user" — the untested case is the one that would
  otherwise leak a filter set.
- `persistedFilter`'s self-registering registry was added here, so no whole-set
  operation (reset / snapshot / restore) can miss a filter the way the
  hand-maintained `bell-session.ts` key list can.

## Block 1 — `aired_from` / `aired_to` become `Date`

### Why this happened at all

It was not on the plan. It surfaced while scoping the airing end-date line
(Block 2): the question "should we render the date in the viewer's timezone?"
has no good answer while the column is a `DateTime(timezone=True)` holding a
padded midnight, because **there is no time of day to convert**. Fixing the type
first meant the Block 2 formatter could be written once, against
`"2026-09-21"`, instead of written around the padding and rewritten later.

### What MAL actually sends — researched, not assumed

- `start_date` / `end_date` are bare calendar dates (`yyyy-mm-dd`), documented
  with **no timezone**. They are the Japanese broadcast dates shown under
  "Aired:" on the site.
- `broadcast` carries `day_of_the_week` + `start_time` (`"23:30"`) — a
  time-of-day, also with no timezone in the field itself. MAL's site renders it
  "(JST)"; Jikan, scraping the same source, normalizes it with an explicit
  `timezone: "Asia/Tokyo"`. JST is the de-facto answer.
- **`broadcast` is not in `_DETAIL_FIELDS`** — this repo has never fetched it.

### Key decisions

- **`Date`, not `timestamp without time zone`.** Dropping only the zone keeps a
  meaningless `00:00:00` and still invites `new Date(iso)` on the frontend. It
  buys honesty about the timezone and nothing else, for the same migration
  cost. `Date` makes "MAL sent no time of day" structural, and serializes as
  `"2026-09-21"` — the hazard is removed rather than documented.
- **Render the published date verbatim, for every viewer** (the decision Block 2
  consumes). Rejected: converting to the viewer's zone. It is not localization
  when the source has no time — it just moves the date a day west of Greenwich.
  Also rejected: re-anchoring the pad to midnight *JST*, which sounds more
  principled and is worse — midnight Asia/Tokyo is 17:00 the previous day in
  Berlin, so a European viewer would start seeing the day before the one MAL
  publishes.
- **`parse_mal_date` is lenient — malformed input is None, not an exception.**
  The first cut used `date.fromisoformat`, which rejects anything but a bare
  date, on a fail-fast argument. That died with the parser collapse below: the
  surviving function also serves the MAL wire form, where partial and malformed
  values are routine, and the sweep's air-date comparison now shares it — so one
  bad record must not abort the run holding it. The old full-ISO strings in
  historical `result_summary` rows are render-only and never re-parsed, so
  nothing depends on rejecting them.

### Gotchas & learnings

What made this its own commit block rather than a line in Block 2:

1. **The sweep diff would have silently flooded.** `_apply_media_diff` compares
   `media.aired_to != new_aired_to`. A `date` never equals a `datetime`, so
   retyping the column without retyping the shared parser reports **every media
   as drifting on every sweep** — stability counters reset catalogue-wide.
   Worse, `aired_from` deliberately does **not** flip `changed`, so its half of
   the bug is invisible: it rewrites the column and floods `result_summary`
   while every existing test still passes. That is why the new regression test
   asserts the diff **sink is empty**, not just that `changed` is False.

2. **`timestamptz::date` resolves through the session `TimeZone`.** Demonstrated
   against the dev DB under `America/Los_Angeles`:

   ```
   bare  ::date          -> 2026-09-20   <-- the trap
   (v AT TIME ZONE 'UTC')::date -> 2026-09-21
   ```

   A bare cast on a server whose TimeZone is not UTC moves every date back a
   day, silently and permanently. CI's container runs UTC, so CI would never
   have caught it. The migration writes the `USING` clause out for both columns.

3. **`_jsonable` needed widening — but not the way it first looked.** A pure
   `date` is not an instance of `datetime`, so the existing check let it fall
   through to `json.dumps`, which raises: the sweep's JSONB write would have
   broken on the first air-date drift.

   Two wrong turns before the one-line answer, both worth recording:

   - The first fix added a second branch with `datetime` checked first, on the
     reasoning that `datetime` subclasses `date` and the reverse order would
     truncate timestamps. **That reasoning was wrong** — `.isoformat()` is
     polymorphic, so both branches did the same thing and there was no order to
     pin. The test written to pin it passed with the branches deliberately
     swapped, which is how it was caught.
   - The replacement test then pinned *datetime* precision, which review showed
     is unreachable: after this change no field reaching `_jsonable` is a
     datetime at all. `aired_from` / `aired_to` were the last ones. So the test
     was deleted rather than rewritten — the end-to-end sink test already
     covers the date case, `json.dumps` included.

   Two method notes fell out. **A new test is not a guard until it has been
   seen to fail** — sabotaging the code is the only way to tell a real guard
   from a vacuous one in a green run. And **a comment defending a branch is
   worth less than knowing whether anything reaches it**: the "don't flatten
   timestamps" note was protecting a case production cannot produce.

4. **Collapsing the two parsers was a consequence, not a cleanup.** Before the
   retype, `parse_mal_datetime` and `_mal_date_to_datetime` read genuinely
   different string forms — the storage form (full ISO, with a `Z` fixup) and
   the MAL wire form (partial `YYYY` / `YYYY-MM`). Normalizing storage to
   `YYYY-MM-DD` collapsed both onto one form, leaving two bodies and two
   docstrings each claiming to be "the shared parser". One lenient
   `parse_mal_date` now serves both, and malformed input returns None rather
   than raising, because the sweep's air-date comparison shares it and one bad
   record must not abort the run holding it.

   The general shape: **changing a serialization format can silently make two
   functions redundant that were previously distinct.** Nothing fails; they
   just stop differing.

### Reviewed and deliberately not changed

**The sweep-tier SQL still compares `aired_from` against `now()`** —
`_is_recent_main` and the archival cutoff in `daos/anime_dao.py`. Those were
type-matched (`timestamptz` vs `timestamptz`) before the retype and are now
cross-type, so Postgres promotes the date through the session `TimeZone`.

Measured before deciding, because the obvious worry did not hold: **the
index-only scan on `ix_media_main_aired_from` survives both forms** — Postgres
pushes the cross-type comparison into the Index Cond, so there is no per-row
cast and no plan regression. What remains is a sub-day shift in where the 5-year
and archival boundaries fall, and `current_date` is *also* session-TimeZone
dependent, so there is no TimeZone-independent target to move to — only a
type-matched one.

Left alone because changing sweep-tier membership semantics is a different
change from a type retype, and this query family was tuned against a prod dump
in v0.15.4. Worth revisiting deliberately, with the tier tests as the check;
they now seed real `date` values, so they can actually exercise it.

### Future work / debt

- **Scrape `broadcast.start_time` and make the air date genuinely viewer-local.**
  `end_date` + JST `start_time` is a real instant, and late-night anime air
  22:00–01:00 JST — which lands mid-afternoon in Europe and morning in the
  Americas, so the local date matches, and where it *does* differ the local date
  is the honest answer. Needs: `broadcast` added to `_DETAIL_FIELDS`, a
  `Media.broadcast_time` column + migration, sweep volatile-bucket wiring, and a
  combine step at the schema boundary. **Caveat that decided the deferral:** it
  reads null for the entire existing catalogue until each media's next sweep
  refresh reaches it — weeks for the long tail — so every row falls back to the
  verbatim date anyway in the meantime. Pairs naturally with this block: same
  columns, same sweep-diff path, same traps.
- **Partial-date precision is still unrecoverable.** MAL emits `YYYY` and
  `YYYY-MM` for older records and the scraper fills the missing parts with `01`,
  so a stored `2011-01-01` may mean "sometime in 2011". The `Date` column does
  not fix this — recording precision would need a second column. The containment
  Block 2 relies on is to render a date only for **Currently Airing** titles,
  where imprecise values are rare; revisit if anything ever wants to show a
  finished title's air range.

## Block 2 — "Currently Airing until Sep 19"

### Key decisions

- **Inside the existing green badge, not a new line or a fact-grid cell.** The
  date qualifies the status, so it reads as part of it. Rejected: a muted
  sentence under the badge, and a second line in the `Calendar` fact cell —
  both make it a separate fact the eye has to reassemble.
- **Currently Airing only.** `aired_from` for unaired titles and full ranges for
  finished ones were both considered and dropped: MAL pads partial dates to the
  1st and those cluster in old finished records, so a day-precision render there
  would be a lie. The scoping lives in `airingStatusParts`, which returns before
  the date is ever composed for the finished/unaired branches — a template `{#if}`
  would have put the same rule in two places.
- **The year is dropped when it matches the current one.** A show airing now
  almost always ends inside it, and "until Sep 21" is the shorter read; a show
  running into next year still says so.
- **`until X` composes *before* `+ upcoming content`**, never after. "Currently
  Airing + upcoming content until Sep 19" parses as though the *upcoming* content
  ends on that date. The date belongs to the airing.
- **The anime aggregate takes MAX over the currently-airing media**, so a
  franchise with two seasons in flight reads to the later one — the badge claims
  "the airing content runs until X", which the earlier date would understate.
- **The badge wraps only under width pressure.** First cut forced the qualifier
  onto its own line with `basis-full`; corrected to `whitespace-nowrap` on the
  qualifier inside a `flex-wrap` container, so a roomy badge stays single-line and
  a cramped one breaks before the `+` rather than inside the phrase.

### Where the date deliberately does NOT appear

Only the two detail heroes show it. Three surfaces that render the same status
string stay dateless, and all three by the same mechanism — **they call
`formatAiringStatus` with two arguments and simply never pass the third**:

- **The share card** (`utils/shareContent.ts`, `statusBadges`). A shared PNG
  travels without the app around it and never refreshes, so a date baked into it
  is wrong the moment the season ends — and unlike the page, nothing will ever
  correct it. The card is also a fixed layout budget where a longer status pill
  costs space that the score and attribute profile need more. `statusBadges`
  already documents that it passes `false` for the media grain; the air date is
  the second thing it deliberately declines.
- **Search result cards** (`MediaInfo.svelte`) — decided up front: search is for
  finding a title, not reading its schedule, and the anime-view card would need a
  new aggregate field shipped on every row to show one.
- **The related-media carousel** (`RelatedMediaCarousel.svelte`) — sibling tiles
  are navigation, and `MediaSibling` carries no dates at all.

Making the parameter optional is what keeps this cheap: the exclusion needs no
guard and no branch, and a future caller that *should* show a date opts in by
passing it. The cost is that the exclusion is invisible at those call sites —
hence this note, and the assertion in `format-string.test.ts` that the two-argument
form is unchanged.

### Gotchas & learnings

- **`formatAirDate` must never let the string reach `Date`.** A bare
  `YYYY-MM-DD` parses as UTC midnight, so `new Date(ymd).toLocaleDateString()`
  renders the previous day for every viewer west of Greenwich. It splits the
  string, builds from `Date.UTC(...)` and reads back with `timeZone: 'UTC'`.
  A second formatter beside `formatShortDate` rather than a change to it — that
  one takes real timestamps, where the viewer's zone *is* the right answer.
  (`Date.UTC` rolls over rather than rejecting, so the parts are range-checked;
  month 13 would otherwise render as the following January.)
- **The vacuous-test trap, again, in a new disguise.** The first version of the
  timezone guard looped over `process.env.TZ` and asserted the rendered value.
  Node reads `TZ` once at startup, so reassigning it mid-run changes nothing —
  and CI runs UTC, where the correct and the broken implementations agree. The
  test passed under a deliberately Date-based implementation. It now spies the
  `Date` constructor and asserts no construction was handed a *string*, which
  fails under UTC. **Where an invariant is "this code path is never taken",
  assert on the path, not on an output that only differs in an environment CI
  does not run.**
- **The guard shaped the implementation, then review reshaped both.** The first
  cut avoided `Date` entirely with a hand-rolled month table, because that was
  the version the spy test could protect. Review pointed out the table
  duplicates what `Intl` already does two functions below. Building from
  `Date.UTC` and formatting at `timeZone: 'UTC'` gets both: no table, and a
  guard that still holds because the assertion narrowed from "no Date" to "no
  Date *parsed from a string*" — which is the actual hazard. **A guard that
  forces an awkward implementation is usually a guard pointed at the wrong
  invariant.**

## Block 3 — the back button returns to the item you clicked

### Key decisions

- **The detail page IS the item that was clicked, so its own `uuid` is the
  anchor.** `focusUuid = searchParams.get('focus') ?? searchParams.get('uuid')`,
  travelling back on the back link as `?focus=` and propagating across
  anime↔media hops exactly like `q` / `from` / `job`. The `??` fallback is what
  removes any need for list-side href changes — six components gained a
  `data-focus-uuid` attribute and nothing else.
- **Propagating rather than using the current page's uuid** is what makes a deep
  dive work: after search → anime → media, back-to-search centres the *anime*
  card, which is the only one of the two present in an anime-view result set.
- **The back link emits `focus` only to targets that consume it**; every detail
  hop *carries* it regardless. The plan's prose said only `ratings-stats` is
  excluded, but its own scope table also excluded library / curation /
  completion / job — the table won, because a param nothing reads and nothing
  strips is URL cruft. Carrying it anyway means opting one of those in later is a
  one-line `BackLink` change.
- **The Jobs Log page offset joined the persisted filter** instead of staying
  component state. It is a list control with the same lifetime as the filters
  beside it, so `filterLifecycle` governs it for free — and it fixes the
  standalone bug where page 3 → a job → back landed on page 1.
- **Scroll state is app-owned and URL-keyed**, the same call `filterLifecycle`
  already made for filter state and for the same reasons; its header argues why
  SvelteKit's `snapshot` fits neither.

### Gotchas & learnings

1. **Stripping `?focus=` re-runs the page that stripped it.** `replaceState`
   updates `page.url`, and `/search` reloads on `page.url` — so tidying the param
   away refetched the results and reset `visibleCount` to 20, undoing the restore
   a microsecond after it happened. The load effect is now keyed on what the
   results were loaded *for*. **A page that reloads on `page.url` reloads on any
   param edit, including its own housekeeping.**

2. **A scroll restore is not "scroll once the data has arrived."** That is what
   was built, and it failed differently on each surface, with the *same* code:

   | Surface | Symptom | Why |
   |---|---|---|
   | `/watchlist` | worked | ~100ms network fetch |
   | `/ratings` | landed at the top | warm `ensureRatingScores` cache resolves in a microtask, so the scroll raced SvelteKit's post-navigation `scrollTo(0, 0)` — also a microtask after mount — and lost |
   | `/search`, last card | landed too high | scroll computed before paint, against a document still laying out |
   | `/search`, last card | landed short | the page kept growing *after* any plausible settle window |

   The differences were data-source latency, not code. **A timing assumption that
   holds on a surface with a network fetch is untested, not correct** — the fetch
   is hiding the race rather than making it safe.

3. **Two dead ends before holding beat timing.** Both are recorded because both
   look right on paper:

   - *Scroll immediately, correct once 150ms later.* Fixed the position, but the
     correction is a **visible second scroll** — the page lurches twice. Rejected
     on feel, not correctness.
   - *Wait until `document.documentElement.scrollHeight` holds steady for two
     frames (capped), then scroll once.* Sound in principle and strictly worse in
     practice: the growth arrives **after** any settle window, because it is a
     store landing post-paint rather than layout finishing.

   Replaced by `pinCentred` — re-centre every frame for 600ms, release the moment
   `window.scrollY` is not what it last set. It is *less* code than either
   attempt, and it subsumes the SvelteKit race, the pre-paint measurement and the
   late growth without distinguishing between them. **When you cannot predict
   when a page stops moving, hold the target instead of timing the scroll.**

4. **The growth was diagnosed from a symptom matrix, not from the code.** One
   column fine; two columns showed half the last row; two columns after a "Show
   More" click showed none of it; media view always fine. Growth proportional to
   the rows *above* the target, present only when cards are narrow — which points
   at `MediaInfo`'s header, a `flex justify-between` whose title block has no
   `min-w-0`. A bookmark icon arriving from the async watchlist store steals
   width, the title re-wraps, and `auto-rows-fr` lifts every row in the grid to
   the new tallest. Anime-only because a media card shows the icon when *that*
   media is watchlisted, an anime card when *any* of its media is. Not fixed —
   see debt below.

5. **A background loop outlives the test that started it — twice.** Both the
   settle sampler and the pin keep scheduling frames past the end of their test
   and fire into the *next* one, against a detached node and the shared spy. Both
   surfaced as a **neighbouring** test failing with an inflated call count, which
   is the tell. The pin's teardown hands over to "the user" via the same escape
   hatch production has. **Any DOM helper that outlives its call needs a teardown
   story in the tests, and its symptom is never the test that caused it.**

6. **Sabotage caught a constant whose justification was wrong.** `SETTLED_FRAMES
   = 2` was documented as "a single sample proves nothing — any height equals
   itself", which is not the reason (one stable frame is a real signal; the real
   reason is that layout lands in fits). Nothing pinned the value at all, so
   nothing had ever contradicted the comment. The logic is gone now, but the
   shape recurs: **an unpinned constant's comment is unreviewed prose.**

7. **A `<tr>` is not a box.** Tailwind Preflight sets `border-collapse: collapse`,
   under which a table row paints no `box-shadow` — so the card treatment (a ring)
   is simply invisible on every table. Rows take a background sweep instead, which
   they *do* paint, broad and low-contrast because a narrow high-contrast band
   crosses as a **flicker** rather than as a wash going past. (Several rounds were
   spent tuning that sweep against a tint underneath it. See the post-deploy
   section below for why that tint was not there.)

### After the deploy — `color-mix()` inside `@keyframes` is silently dropped

The flash shipped broken, and the way it broke is worth more than the fix.

`@keyframes focus-flash` held `background-color: color-mix(in oklab, var(--primary)
20%, transparent)`. The production minifier emits `color-mix` fallbacks by
**duplicating the rule** that holds them — which it cannot do inside `@keyframes`,
so it discarded the whole `from` block instead:

```css
/* authored */  @keyframes focus-flash { from { box-shadow: …var(--ring); background-color: color-mix(…) } to { … } }
/* shipped  */  @keyframes focus-flash{to{background-color:#0000;box-shadow:0 0 0 3px #0000}}
```

With no `from`, an animation interpolates from each element's *current* computed
value — here, to the same value. A no-op. The identical `color-mix` in the
neighbouring `tr.focus-flash` rule was handled correctly, fallback and all, because
that one is a rule.

**It is `app.css`'s pipeline, not CSS.** `AttributeBadges`' `pill-burst` keyframes
carry six `color-mix` calls and ship whole — checked in the bundle, not assumed.
Component `<style>` blocks are minified without the fallback generation that drops
the block, so the first draft of the rule ("never `color-mix` in `@keyframes`")
would have banned a pattern demonstrably working ten files away. **An invariant
written from one instance is a guess until a second instance is checked** — and the
second instance is what turned a false rule into an accurate one.

Three things fell out of it:

1. **The rows only looked right by accident.** `focus-flash-sweep` has no
   `color-mix`, survived intact, and was doing every visible thing on a table row.
   The tint had never once rendered in production — so the rounds spent tuning the
   sweep against the tint were tuning something that was not shipping. Cards, which
   have only the ring, showed nothing at all.

2. **Every gate we own passes it.** The build *succeeds*; it just emits less CSS.
   `bun run check`, `bun run test` and even adding `bun run build` to CI are all
   green. Only a production bundle differs from dev, and only a deploy surfaces it.
   **An animation verified solely against `bun run dev` is unverified** — that is
   the durable lesson, and it generalises past CSS to anything the production
   pipeline transforms.

3. **The guard is still missing, and the reason it was dropped was wrong.** The
   attempt was a Vitest test reading `app.css`; that needs `@types/node`, which this
   frontend does not carry, and Vite's `?raw` returns an empty string because the CSS
   plugin intercepts it. Both obstacles are about reading the **source** from inside
   the test runner — but the hazard lives in the **output**, an ordinary file on disk
   after `bun run build`, greppable from CI with no dependency at all. Review caught
   that; it is recorded here because the same misaimed reasoning ("this is hard to
   test" when the artifact under test was chosen wrongly) is easy to repeat.

   Worth recording too that the abandoned test caught its own failure only because it
   carried a *guards-the-guard* assertion — "does the parser find any keyframes at
   all" — without which it would have reported a clean pass over an empty set.

Resolved by splitting the two surfaces properly rather than restoring the tint: the
row keeps sweep-only, which is what production had been showing and what was
approved on that basis, and the card keeps the ring. `flash()` then simplified —
each surface runs exactly one animation, so it clears the class on the first
`animationend` instead of matching a name. That name check would have been *wrong*
under the split: a row runs `focus-flash-sweep`, never matches `focus-flash`, and
the class would have stuck, killing every second return to the same row.

### Verification note

**jsdom has no layout, no paint and no scrolling**, so every assertion about
*when* something happens here is a timer assertion wearing a paint assertion's
clothes. Demonstrated rather than assumed: a one-frame implementation passed the
tests written for a two-frame one. The unit tests pin the arithmetic
(`pageCovering`), the URL handling (`hrefWithFocus`, `consumeFocus`) and the
lifecycle of the pin (holds, yields to the user, releases). Everything about
where the page actually lands was caught by user verification across four rounds —
and it caught all three failures.

### Future work / debt

- **`MediaInfo`'s header re-wraps when the bookmark icon lands** (gotcha 4). The
  fix is `min-w-0 flex-1` on the title block plus a reserved slot for the icon, so
  card height stops depending on an async store. Deferred because the pin makes it
  invisible, and it changes a shared component's layout on a diagnosis verified by
  symptom rather than by measurement. Worth doing on its own terms: a grid whose
  row heights depend on fetch timing will surface again somewhere else.
- **A white flash when scrolling immediately after returning to anime search.**
  Observed, reproducible-ish, not diagnosed. Plausibly a large repaint of
  never-painted content below the fold; unrelated to the scroll restore, which no
  longer moves the page by then.
- **The `target="_blank"` comments** in `admin/MediaChangeCard.svelte` and its
  job-detail mirror argue that change cards open in a new tab *because* returning
  would lose scroll position. Still true — those admin surfaces are out of scope —
  but the mechanism to revisit them with now exists.
- **The excluded back-link targets** (statistics, library, curation, completion,
  job detail) each opt in with one `hrefWithFocus` call plus an anchor attribute,
  since the uuid already travels to all of them.

## Block 4 — the job detail page

### Key decisions

- **A medal table, not bucket-then-count.** The old key bucketed a row by its
  *highest* category and then ranked within the bucket by summed field count, so
  five static metadata edits outranked one `airing_status` flip. The new key
  counts each category separately and compares them in order, so the first count
  to differ decides and **one gold beats any number of bronze**. The rank order
  `dynamic > genre > studio > static > rating` tracks how volatile MAL is with
  each category: a dynamic field moving is news, a description rewrite is not.
- **Four medals, not the five the plan specified.** The rating medal is inert:
  `ratingKey`'s subrank sits directly beneath it and encodes the same ordering at
  finer grain — `r=2 ⟺ s=0` (both moved), `r=1 ⟺ s∈{1,2}` (one moved), `r=0 ⟺ s=3`
  (neither) — an order-reversing monotone map, so a rating count adds nothing the
  subrank does not already impose. Removed rather than commented, following Block
  1's `_jsonable` precedent on this same branch. The approved *semantics* is
  untouched: a rating-only row still sorts below any row with a static edit,
  because the static medal decides that.
- **The A→Z tiebreak compares the media title as the card prints it**, through
  the admin's name language, so an alphabetical run reads as alphabetical down
  the page. Sorting on the parent anime title was rejected: it reads as *grouped*
  rather than alphabetical, because the anime title is nowhere on the card. Both
  sides now call one exported `mediaChangeTitle` — the tiebreak is *defined* as
  "what the card prints", so two call sites agreeing by convention was the wrong
  shape.
- **The rank order is one exported constant, and a test — not a comment — holds
  the card to it.** `CHANGE_TONE_ORDER` lives in the sort util; `MediaChangeCard`
  keys its row order off the `TONE_RANK` derived from it. See gotcha 3.
- **Anime changes stay unsorted** — `AnimeUmbrellaCard` has no tone categories, so
  the medal table has nothing to rank there.

### Gotchas & learnings

1. **Two vacuous assertions, one shape.** Ten mutations were run against the
   comparator; two of them changed the code and killed nothing.

   | Mutation | Why it survived |
   |---|---|
   | rating subrank comparison dropped | the two rows' *magnitudes* happened to order the same way the subrank does, so the fallback produced the same answer |
   | genre medal zeroed | every row in the cascade test carried a genre drift, so genre tied everywhere and never decided anything |

   One failure in two costumes: **the test data agreed with a mechanism other
   than the one under test.** A tiebreak assertion is only a guard when every
   *other* mechanism in the comparator points the opposite way. Both were fixed by
   constructing exactly that opposition — magnitudes set against the subrank, and
   a genre row pitted against one carrying studio *and* five statics.

2. **A surviving mutation is not always a test gap.** Zeroing the rating medal
   left all ten tests green, and the right response was to delete the medal, not
   to write an eleventh test. Sabotage is usually read as a verdict on the test;
   it is equally a verdict on the code, and the proof above only got written
   because a green mutation forced the question "what *would* this ever change?"

3. **A cross-file invariant asserted in three comments is asserted nowhere.**
   Review caught this: the rank order existed as two independent literals — the
   comparator's medal sequence and the card's `TONE_ORDER` — with `mediaChangeSort`,
   `MediaChangeCard` and USER_FLOWS each stating in English that they mirror each
   other, and nothing checking it. A re-rank would have silently shipped a page
   whose list order and in-card row order disagreed, which is the exact confusion
   the change set out to remove.

   Fixed by making the order importable (`CHANGE_TONE_ORDER` + a derived
   `TONE_RANK`) and then walking it in a test: for each tone, one change of it
   versus five of every tone ranked below. Reordering the constant *or* the
   comparator alone now fails — verified in both directions. **The reach for
   "single source of truth" is usually about deduplication; here the point was
   that a fact spread across two files with no importable form cannot be
   tested at all.**

4. **Three of the reviewers' findings were declined, and the reasons matter more
   than the count.** Decorating once outside the search `$derived` (so sort keys
   survive a keystroke), replacing the medal array with scalar fields, and fusing
   the three `m.dynamic` traversals are all correct as stated. All three trade
   readability for allocations that do not matter at a few hundred rows, and the
   first would restructure the page's derived chain for a sort-order change.
   Recorded because the argument would be different at 10× the list size — the
   sort is `O(n log n)` with a decorate pass that is re-run per keystroke, and
   that shape is the thing to revisit, not the micro-allocations.

5. **A decline is a policy, and the accepts have to be checked against it.**
   Alongside those three, a fourth micro-optimisation was *accepted* — hoisting a
   module-level `Intl.Collator` in place of `localeCompare` in the comparator. A
   later reviewer pointed out the contradiction: same order of magnitude, same
   kind of win, opposite verdict, and six other sorts in this frontend
   (`ratingStats`, `watchlistStats`, `spoilerFrontier`, `CompletionStatusCard`)
   all call `localeCompare` bare, one of them inside its comparator on comparable
   row counts. Reverted. Introducing an idiom at one of seven sites costs more in
   inconsistency than it wins in time; if title comparison ever shows up in a
   profile, it should be fixed across all seven at once.

   The defence written for it had also drifted into being **wrong**: it claimed
   the "Static only" chip makes every row tie on all four medals, but that chip
   keeps rows that *have* a static change, not rows with *only* static changes —
   so those rows differ on the static medal. **A micro-optimisation nobody asked
   for tends to grow a justification nobody checked.**

## Block 5 — the Job health card windows each kind separately

Raised after the plan was written: the card read one 7-day window for every job
kind, and a window is only a rate if it holds several runs. `seasonal_sweep` runs
weekly, so 7d held exactly one run and the row could only ever say 0% or 100%.
`upcoming_sweep` runs Wednesdays in the last month of the quarter, so 7d was
empty almost always. `restore` is manual and read "—" permanently.

### Key decisions

- **Per-kind windows, not one retuned global one.** 7d stays for the kinds that
  run at least nightly (`user_scrape`, `update_sweep`, `backup`) — 7 runs is
  already a rate, and a short window is what makes a failure *last night* visible
  instead of averaged into a quarter. 90d for the rest. Uniform 90d was the
  simpler option and was rejected for exactly that dilution: three bad nights in
  90 reads 97% green.
- **90d specifically fits `upcoming_sweep`** because quarter-months sit three
  months apart, so a 90-day window always covers one such block wherever you
  stand in the quarter — it never falls into a gap. It lands ~4–5 runs, which is
  thin; 120d is the fallback if that ever reads as noise.
- **The window ships per row as `window_days`** rather than the frontend keeping
  its own copy of the table. The card groups by it, so retuning a window regroups
  the card with no frontend edit.
- **`JOB_HEALTH_WINDOW_DAYS` is keyed on `JobKind` with no default**, so a new
  kind fails there rather than silently inheriting someone else's cadence.
- **One GROUP BY with an OR of per-kind `(kind, cutoff)` pairs**, not a widest-window
  scan plus a per-kind `CASE`. `jobs` is small and carries `ix_jobs_created_at_desc`;
  the CASE form buys plan shape at the cost of a filter the reader has to re-derive.
- **`AdminOverviewStats.jobs_7d` → `jobs`**, once the cost was measured rather
  than estimated. The first framing ("crosses schema, service, frontend types
  and tests") made it sound expensive and it was kept on that basis through two
  rounds; two reviewers independently counted the real figure — **10 in-repo
  occurrences, no external consumer, no versioned contract** — against three
  permanent comments whose only job was to say the field name lied. The rename
  was the cheaper side and deleted all three. `activity_7d` beside it keeps its
  suffix because it genuinely is one 7-day window.

  **An estimate stated once becomes the basis for every later decision.** Nobody
  re-derived that cost until a reviewer put a number on it, and the wrong number
  had already survived a plan, a handoff and a commit-plan draft.
- **User activity stays 7d.** It was working; only job health had the cadence
  mismatch.

### The card took four attempts, and the discards are the useful part

Each was rejected by the user on sight, and each for a different reason worth
keeping:

| Attempt | Why it died |
|---|---|
| Heading tooltip explaining the windows | "Feels like documentation." A tooltip explaining your own layout means the layout has not done its job |
| ` · 7d` trailing each counts line | A duration and a count are different kinds of fact; putting them in one line makes both harder to read |
| One pip per run | Does not scale — `user_scrape` can run 50+ in a week, so the cap engages constantly and the track stops being a count |
| Failure-share ratio bar | **Redundant**: it encoded the percentage and nothing else, so the card drew the same fact twice |

What landed: one grid for the whole card so the number columns align *across*
window groups, `Ok` / `Failed` / `Rate` headers stated once, zeros dimmed nearly
out and non-zero failures in `destructive` — so the Failed column is a vertical
line and any red is the only red on the card. The window becomes a **centred
rule** between groups (the user's suggestion) rather than a flush-left label that
read as another row, and the heading sits in the header row's first column rather
than in a `Card.Header` above it, which had left a band of empty card between the
title and the columns it labels.

The lesson under all four: **the ask was "something innovative" and the answer was
typography, not graphics.** Every graphical option either failed to scale or
re-drew a number already on screen; alignment and weight carried it.

### Gotchas & learnings

1. **The test had to distinguish per-kind windows from *any* global cutoff.**
   Asserting "a 30-day-old seasonal row counts" passes under a global 90d window
   too, which is a different design. The test seeds a 30-day-old row for *both* a
   90d kind and a 7d kind and asserts the counts move differently — no single
   cutoff of any length can satisfy that. Confirmed by sabotage: reverting to a
   global 7d **and** to a global 90d each fail it.

2. **Reading the wrong build is a real failure mode.** A screenshot arrived
   showing a layout two revisions old, with feedback attached. The feedback was
   still valid, but it would have been easy to act on it as though it described
   the current code. Worth naming the version under discussion when UI is
   iterating fast.

3. **"It's only presentation" was the wrong reason to leave `byWindow` untested.**
   The argument for keeping it inline in the component was that grouping is
   trivial and any failure is visible on the page. Both halves were wrong.
   `/admin/stats/overview` emits one row per `JobKind` in enum order, so the two
   windows arrive **interleaved** — un-interleaving them is the function's actual
   job, not cosmetics — and its two contracts (shortest window first, backend
   order preserved within a group) were enforced by nothing, in a component with
   no test file at all. The repo already had two tested siblings of the identical
   shape (`toScoreBands`, `toPriorityBands`) in `lib/utils/`, which is the
   convention that should have decided it. **The tell was reaching for a
   justification instead of a precedent.**

4. **A defence can point at the wrong seam.** The extracted helper first carried
   a paragraph arguing the three band helpers should not collapse into a generic
   `groupBy`, because they differ in key type, ordering and labelling. All true,
   and irrelevant: what is actually duplicated across the three is the six-line
   Map-bucket loop, which *would* unify behind a single `bucketBy(rows, keyFn)`
   with the ordering and labelling left exactly where they are. The paragraph was
   deleted rather than rewritten — foreclosing a refactor on a mis-aimed argument
   is worse than saying nothing.

### Future work / debt

- **`bucketBy(rows, keyFn)`.** The Map-bucket loop is now written three times
  (`jobHealth.ts`, `ratingStats.ts`'s `toScoreBands`, `watchlistStats.ts`'s
  `toPriorityBands`), byte-identical modulo the key expression. Extracting it
  drops ~5 lines from each and leaves each helper's ordering and labelling
  untouched. Deferred here only because it edits two tested utils that this
  change otherwise does not touch.

## Block 6 — the watchlist readiness filter

Two commits: the backend projection (`28d1eb4`), then the rules, filter, badges
and `docs/features/readiness.md`.

### The question, and why it is two layers

"Can I start this tonight?" fails for two unrelated reasons, and neither is
visible from a watchlist entry: something in the franchise is airing or about to,
or everything listed is already watched and the rest has not aired.

The user's opening premise was that readiness is an anime-level property, and the
Dragon Ball case they raised in the same message disproves it — two users with the
same anime get different answers, because the verdict reads their own selection
and their own ratings. What *is* user-independent is a single media's temporal
class. Splitting those two layers is what made the rest tractable.

### Season, not date — the finding that killed a whole option

The first design compared `aired_from` against a rolling 92-day window. Querying
the dev DB (a restored prod dump) killed it:

- `aired_from` and `anime_season_*` are present in **exactly** the same rows —
  zero rows carry one without the other, so consulting the date buys no coverage.
- Among **unaired** media with a date, roughly half land exactly on a season-start
  day (Jan/Apr/Jul/Oct 1), against ~3% of airing and ~3% of finished media. That
  is `parse_mal_date` padding a bare year or year-month. At the time of the study
  Winter 2027 was 22 padded out of 24 — "Winter 2027" there means "sometime in
  2027", not January.
- Where the two disagree, the season wins: it comes from MAL's own `start_season`,
  while a date-derived season is only a fallback.

So the horizon is season arithmetic and `aired_from` is not read at all. A
day-precision window would have been false precision on half the rows that matter.

### The threshold is per media, never summed

The "Dragon Ball rule" — a listed entry long enough to stand on its own releases
the franchise block. The user asked whether it should be per-media rather than
over the selection, and the catalogue answers it: a set of franchises are one
continuous story told in short seasons (Boku no Hero, Nanatsu no Taizai, JoJo),
whose total clears any sane threshold while no single season comes close. Summed,
they read as standalone and a new airing season gets hidden — exactly wrong. Taking
the max gets them right and still clears every long-runner, because those are one
huge media each (Naruto, Dragon Ball Z, Gintama, Bleach).

`STANDALONE_SECONDS = 20h` sits at the classic 4-cour (~50 episode) format. There
is a cliff there: raising it to 22h roughly halves the qualifying set, splitting
the 50–52-episode cluster on nothing but a runtime rounding difference. 25h was the
first proposal and would have wrongly blocked Digimon Adventure, FMA 2003, Gintama',
Soul Eater, Eureka Seven and most of Gundam.

**Re-measure before moving this.** Every number above is a property of the
catalogue on the day, not a constant.

### The rule, and the asymmetry that is easy to get wrong

`READY = A ∧ B1 ∧ B2`, with the exemptions deliberately NOT symmetric:

| | on-list (B1) | off-list (B2) |
|---|---|---|
| airing, unrated | blocks | blocks |
| airing, **dropped** | **blocks** | **exempt** |
| a listed entry ≥ 20h | blocks | exempt |

Listing a season means you want it, so dropping it is ambiguous and the escape
hatch is to unlist it. Dropping something you never listed is unambiguous. This got
written wrong twice before the user's correction pinned it; the table is the spec.

Rated media still count as content — a listed, finished, already-rated entry is a
**rewatch**. What makes an entry not-ready is the list *waiting on something
unaired* with no fresh finished content to fill the gap.

### Why the verdict is computed on the client

It is computable server-side as one column — `_franchise_signals` already groups by
anime and the projection already carries every other input — and that would delete the
rules module and its suite. It stays on the client because the rules are UI-shaped and
changed three times inside one review session on visual feedback, and because "next
season" is read off the viewer's clock, which the server does not have. Worth
re-opening if a second surface ever needs the same verdict: that is the point where
duplicating it costs more than shipping it.

The media *class* needs no stored column for a different reason. It is a CASE over
columns the sweeps already keep current, so a derived class is correct the instant they
are; a cached copy would need a write hook in every sweep, the save path and curation,
**plus** a recompute at each season boundary, where the class changes with no row
touched.

### Dead ends

- **`case(mapping, value=...)`** (SQLAlchemy's simple-CASE shorthand) reads better
  and was applied on a review finding, but it binds its keys untyped and asyncpg
  rejects `operator does not exist: seasontype = character varying`. The explicit
  `[(col == member, rank), ...]` form is required against a PG enum column, which
  is why `search_filters._score_weight_case` is written that way too. Compiling the
  statement is not enough to catch this — it only failed against a real database.
- **Two mutation checks came back vacuous** and were worth more than the passing
  ones. `else_=0` → `else_=None` on the season CASE is unobservable, because
  `check_season_parts_both_or_none` makes year-without-season unstorable; the
  comment now says so instead of claiming it fixes a live hazard. The
  `COALESCE(franchise_airing, false)` had no test at all until one was written for
  the reachable-but-absent state (an anime whose only watchlisted media is side
  content, so the franchise subquery misses) — without it a NULL fails Pydantic's
  `bool` and 500s the whole page.

### Gotchas

- **`str`-enum members hash by VALUE, not name.** `hash(RelationType.Main) ==
  hash('main')`. So a member-keyed dict is string-lookupable, which let
  `SEASON_ORDER` lose its by-name twin, and `spoiler_service._ANCHOR_TYPES` become
  `MAIN_STORY_RELATIONS` with no `.value` bridge. `SeasonType` hides this because
  its names equal its values — `RelationType` is the one that proves it.
- **`MAIN_STORY_RELATIONS` is deliberately NOT derived from
  `RELATION_SCORE_WEIGHTS`.** Same membership today, different questions: one is
  the scoring dial with a prod-data study behind it, the other decides whether an
  upcoming media parks a franchise. Deriving would let a scoring tweak silently
  change the readiness filter.
- **"Only main story blocks" carries further than it looks.** The classifier files
  a franchise's separate continuities as side stories, so an anthology (Digimon,
  Gundam, Precure) can have a new series airing while the listed entry stays
  plainly ready. Digimon Beatbreak is `SideStory`, which is why Digimon Adventure
  shows no badge — correct, and surprising enough that the feature doc says so.
- **`Tooltip` wraps children in its own `<span>`.** A pill nested inside that is an
  inline box, and vertical padding on an inline box adds no layout height — so it
  renders shorter than the `mutedPill` beside it. Put the pill classes on the
  Tooltip's own `class` prop instead. The trigger snippet is the equivalent escape
  for an interactive trigger.
- **A theme token beside a literal hue collides under the matching theme.**
  `bg-primary` for the Ready chip next to `bg-blue-500` for Waiting is one chip
  twice under the Ocean theme. Selected chips now reuse the badge tints, so three
  fixed hues stay distinct under every theme and none is the primary.

### Verification note

The rules are client-side, so the backend tests cover only the projection. The case
table lives twice on purpose: `tests/watchlist-ready.test.ts` is the executable
copy, `docs/features/readiness.md` the prose one. `franchise_upcoming_key`'s
`year * 10 + rank` encoding spans Python and TypeScript with no import between
them — a test on each side pins the same season to the same number, and that pair
is the whole guard.

### Future work / debt

- **Standalone fires on none of the author's 177 watchlisted anime**, because the
  badge marks a *rescue* (something would have blocked, a long entry overrode it),
  not a property. If it should instead mark "long enough to watch alone" as a
  standing fact, that is a rule change, not a tweak — and it would badge a large
  share of cards, which the "an unbadged card is the ordinary case" design spends
  its quiet on.
- **The verdict is computed at mount with a single `new Date()`**, so a season
  boundary crossed mid-session waits for the next load. Deliberate: the alternative
  is a timer nobody would ever see fire.

## Block 7 — the watchtime filter

"Is this a short one or a long haul?" — the watchlist could not answer it. The
Statistics subtab had a single "Queued time" tile for the whole list; no card
anywhere showed a runtime.

### It cost no backend at all

`total_watch_time` was already on the `WatchlistItem` projection — readiness put it
there for the standalone rule — and `/watchlist/items` takes no query params, so
every watchlist filter is already client-side over one fetch. `formatDurationCompact`
already existed and already produced the wanted shape to two units (`4h`, `4h 23m`,
`1d 2h`, trailing zero units trimmed so `4h` never renders `4h 0m`), and the
Statistics tab already used it. The whole feature is the two watchlist utils, the filter store and the page's components.

Worth remembering when scoping the next one: the wide projection is broad enough
that a new *derived* watchlist attribute is usually a frontend-only change, and the
question to ask first is whether the column is already shipping.

### Summed, where readiness takes a maximum

Block 6 is emphatic that `STANDALONE_SECONDS` is **per media, never summed** — a
franchise told in short seasons must not sum its way past the line. This block sums.

They are not in tension because they ask different questions. Standalone asks *is one
entry a commitment on its own*, so a sum would launder many small seasons into one
big one. Watchtime asks *how long is the thing I listed*, where the sum is the answer
by definition. The row comment says so at both sites, because "we sum here and take
the max there" reads as an inconsistency until you know which question each is for.

The search page aggregates anime watch time by **sum** too, so the sum side has the
precedent; readiness is the deliberate exception.

### Scoped to the selection, where readiness is not

`statusByAnime` runs over the **unfiltered** entry set on purpose. The watchtime runs
over the filtered one: pick a list and the number re-sums to that list.

The reasoning is the same shape as above — a readiness verdict is a property of the
*franchise*, so the chips must not move it; a watchtime is a property of *what you
listed*, and splitting a franchise across lists means you intend to watch those groups
separately. It also fell out for free: `toAnimeRows` already receives the tag-filtered
items, so summing inside it covers exactly the entries whose media count and main/side
split the row already shows.

**This asymmetry did not survive review.** Bleach's main entry on one list and a
29-minute side story on another produced a card reading "29m" beside a **Standalone**
badge claiming it was long enough to watch alone — the badge had read the list you
were not looking at. The badge was always franchise-scoped; putting a contradicting
number next to it is what made it visible. Scoping the verdict to the selected lists
is queued as its own change, and it reverses Block 6's documented decision and inverts
a test that pins it. Note the hazard that decision names — "parking an airing season
on a separate list would silently unblock the franchise" — is mostly already covered,
because `franchise_airing` / `franchise_upcoming_key` come from the database over the
whole franchise rather than from the entry set. Only B1 narrows.

### The bands, and the two readings that are not a band

`< 5h` / `5–10h` / `> 10h`. 5h is one 12-episode cour at ~25 min — the point a season
stops being a single evening — and 10h is two. A boundary belongs to the band above it.

Null `total_watch_time` is the open-ended shows, and it is neither a fourth band nor
zero:

- **Treated as 0 it lands in `< 5h`**, which files One Piece under "under five hours".
  That is the tempting reuse — `queuedSeconds()` already collapses null to 0 for the
  Statistics tab — and it is wrong here, so the row aggregation splits the sum from a
  count of unknowns instead.
- It matches **no chip**, so such a row shows with no selection and hides under any —
  the same shape as readiness letting a null runtime never clear its threshold.
- It sorts **last in both directions**. Missing data is not a short show, so flipping
  the direction must not parade it to the top; the comparator returns before the sign
  is applied.
- A partial sum renders **`8h 40m+`**. A known runtime is always > 0 (the backend maps
  MAL's `0` episodes/duration to NULL), so "some entries known" is exactly `sum > 0`,
  and `8h` sorts before `8h+` because the `+` is part of the magnitude — signed with
  the direction, unlike the title tiebreak.

### Colour took four passes, and the discards are the point

- **Purple, the first instinct, is the Default theme's own `--primary`** (`oklch(0.558
  0.288 302.321)`, hue 302). The watchlist's Grid/Table pills render `bg-primary/15`,
  so a purple chip would echo the control directly above it. Block 6 already names this
  trap for the Ready chip; it applies to any new tint.
- **`scoreColor`'s ramp was the better-sounding idea and is still wrong**: four bands
  not three, its top band *is* the theme primary, and it means "how good" — a 20-hour
  anime is not a badly-rated one. `PRIORITY_ACCENT` likewise owns red/amber/sky one
  chip group over.
- **Teal, ramped by weight rather than three hues**, so the ramp itself says "longer".
- **Two ramps kept in step by hand is the mistake to avoid.** The table got a text-only
  twin of the pill fills, picked for a dark surface — but the table renders on
  `bg-card/80`, which is light, so `teal-200` ("longest, most prominent") came out as
  the faintest value on the page and `teal-600` ("shortest") the boldest. Exactly
  inverted, and it looked like a data bug.

It ends as **one palette rendered two ways**: `teal-400 / 600 / 800`, as a fill on the
chips and the card badge, as text in the table column. Both live on one line per band in
`WATCHTIME_FILTERS`, and a test extracts the shade from each and asserts they match —
Tailwind scans source for literal class strings, so `bg-teal-${shade}` can never be
composed and the two literals are unavoidable. Adjacency is not a guard; the test is.

### Where it goes on a card, and where it does not

`WatchlistCard` argues the readiness badge sits beside the title "rather than over the
cover, where it competes with the tag dot and the note icon". That reasoning is about
the **top** corners, which are the taken ones — both bottom corners were free app-wide
(`absolute bottom` had zero hits outside shadcn primitives). The watchtime pill takes
bottom-right, and the comment now says why the readiness badge does not follow it: the
runtime is on nearly every card, while the verdict badge is absent for a plainly-ready
anime and for every media row, so keeping it in the text column is what lets it read as
the exception.

**Pills do not belong in a table column.** The first table pass reused the card's pill
so the tint would be identical by construction. A pill is only as wide as its own text,
so a column of them tears along the aligned edge — visible immediately and ugly. Tinted
text, the shape the Priority cell already uses, is the answer; the band still comes off
one source, only the rendering differs.

### Verification note

Every guard was broken and seen to fail before being believed: the band boundaries,
unknown getting no band, the union and empty-selection conventions, the sum, the partial
flag, the all-unknown null, both sort rules, and the fill/text shade match.

One is weaker than its name suggests and says so in place: the list-scoping test covers
that the sum follows whatever entry set it is handed, but the decision that matters is
the **order** in `WatchlistListTab` — passing the tag-filtered set rather than the raw
one — which no util test can reach. Swapping it there leaves the suite green.

### Future work / debt

- **Scoping the readiness verdict to the selected lists**, above — built in Block 8, which
  also closes the ordering gap the verification note above names.
- **The bands are hardcoded and should stay that way** unless a user is ever meant to
  choose them; the thresholds are a design decision, not a setting.

## Block 8 — scoping the readiness verdict to the selected lists

Block 7 left this queued: the watchtime sum followed the Lists chips and the verdict did
not, so Bleach's main entry on one list and a 29-minute side story on another rendered
**"29m" beside a Standalone badge**. The badge had always been franchise-scoped; putting a
contradicting number next to it is what made it visible.

### The hazard Block 6 named was already covered

`readiness.md` argued against list-scoping on the grounds that parking an airing season on
another list would silently unblock the franchise. Checking it against the code rather than
the doc: `_franchise_signals` computes both signals in SQL over the anime's whole main
story, and the LEFT JOIN puts the same pair on every entry of an anime. So `items[0]`'s
copy is identical whether the group was tag-filtered or not — **B2 does not narrow**, and a
watchlisted airing main-story media is part of its own franchise, so it reports itself.

What narrows is everything derived from the entry set:

| | Narrows | Consequence |
|---|---|---|
| **A** | yes | a list of finished seasons reads ready-as-rewatch where the whole watchlist read `waiting` |
| **B1** | yes | observable **only** in the dropped-airing case, since `franchise_airing` already excludes dropped media |
| **standalone** | yes | the fix — a short side story alone on a list cannot borrow the exemption |
| **B2** | no | DB columns over the whole main story |

Both consequences were accepted rather than designed around, and both are in `readiness.md`
now: B1's "the escape hatch is to unlist it" gains a second hatch (park it elsewhere, if you
dropped it), and a far-off sequel on another list stops forcing `waiting`.

The general shape worth keeping: **a doc that argues against a change can be arguing from a
constraint that has since moved.** The scope question here was settled entirely by reading
where each input comes from, and the answer was in SQL, not in the file that stated the rule.

### The pipeline became a function so its order could be tested

Block 7's own verification note flagged that the load-bearing decision was the **order** in
`WatchlistListTab` — which entry set reaches which step — and that no util test could reach
a `$derived` chain in a component. This block put a second such decision on the same line,
which settled it: the five steps moved into `buildWatchlistView(items, filter, lang, now)`.

Three things ride on the order, and each now has a test that fails when it moves:

- **Lists scope the verdict** — `statusByAnime` reads the tag-filtered entries.
- **Priority and watchtime cannot** — both are *row* filters, running after the badge is
  stamped. They are excluded by construction, not by a rule someone has to remember.
- **Item filters before normalization, row filters after** — so an anime row's aggregates
  describe exactly the entries that survived, which is what makes the runtime agree with
  the badge.

The alternative considered was a component test of the tab. Rejected: it mounts the filter
bar, grid and cards for one assertion, and `rules/tests.md` asks for the arithmetic in a
pure function with a thin DOM half anyway.

**One import-graph trap.** `buildWatchlistView` takes `WatchlistFilterState`, whose module
deliberately imports only *types* from `watchlistStats` — it is reachable from the root
layout, and a value import pulls the readiness rules into `/login`'s chunk. Taking the type
back the other way is a type-only cycle, erased before the bundler sees it, and the comment
at the import says it must stay that way.

### What the sabotage pass found

Every new test was broken and seen to fail. Two results worth recording:

- The first version of *"priority and watchtime cannot move a verdict"* was **wrong, not
  the code**: it selected priority 3 and expected the row to survive, but `toAnimeRows`
  collapses the pair into one row carrying the *most urgent* priority. The guard is the
  opposite assertion — those chips match **no** row, and a hoist above `toAnimeRows` would
  produce one.
- The Bleach test is **weaker than its name** and says so in place: neither scoped group can
  reach the sum-vs-max distinction, so it records the two-way reading rather than separating
  two implementations. The guard for the scoping itself lives in `watchlist-stats`.

## Block 9 — the delete-candidates queue

Started from a live failure rather than a feature idea: the nightly sweep had been
404ing MAL id 64875 ("Niu Lai") every run. The investigation turned up three
things, and only the first was the reported symptom.

**MAL deleted the entry.** Confirmed against the API *and* the web page (both 404,
a control id 200), and MAL's search returns nothing for the title — so it was
deleted, not merged or renamed. It is a 2026 Chinese donghua that went viral for
crude animation and was pulled from cinemas; the kind of entry MAL's moderators
remove after the fact.

**The failure never drained.** `_try_step1_refresh` rolls its savepoint back on
any exception, so `MediaFreshness.last_checked_at` was never stamped. The row
stayed permanently past its due window and re-failed every single night. The dev
DB still showed `2026-09-02` as its last check, eleven days on.

**The blast radius scales with franchise size.** *(Closed in Block 11.)*
`_refresh_one_anime` loops
`refresh_anime(media.mal_id)` over every due media inside one savepoint, so a 404
on a *single* media aborts the whole anime's refresh. Niu Lai is standalone, so
only it was stuck — the same 404 on one of Meitantei Conan's 78 entries would
freeze that entire franchise's refresh indefinitely. That is what decided the
grain below.

### Why a queue and not an auto-delete

A 404 is good evidence about one row and terrible evidence during an outage. Auto-
deleting on it means a bad hour at MAL silently strips the catalogue, with a backup
restore as the only way back. So detection raises a proposal and an admin decides —
the same shape merge and split already use, which is why this became a third queue
on the existing tab rather than a new surface.

### The decisions worth recording

**Media grain, anime removed when empty.** The Conan case above rules out an
anime-grained queue: it could only express "delete the whole franchise". One
candidate is one media; the anime goes when its last media does. A surviving anime
is reclassified afterwards, because the deleted media may have been the anchor and
`anime.mal_id` tracks the anchor's mal_id.

**`ON DELETE SET NULL`, not CASCADE — the one place the sibling schema must not be
copied.** `merge_candidates` cascades from anime, and that cascade is *why* `merge()`
never records a `merged` status: deleting anime B destroys the row. A delete
candidate **records** a deletion, so CASCADE would erase the audit trail at the
exact moment it becomes the only record. The row therefore carries an identity
snapshot (mal_id, title, name_*), which is also the only thing a later sweep could
rediscover on and the only key a blacklist can use.

The service sets `media_id = None` explicitly as well as relying on the FK action,
because sessions run `expire_on_commit=False` — the ORM would otherwise keep
serving a `media_id` pointing at a row that no longer exists.

**Stamp the clock on 404 only.** This is the actual bug fix and it is independent of
the queue. *(Block 11 moves where the stamp happens; the reasoning below stands.)*
Scoped to 404 because stamping on any failure would let one outage push
the whole catalogue to a 90-day cadence overnight — the failure the circuit breaker
exists to bound. The subtle half is that `_advance_media_freshness` must advance the
*stability counter* too, not just the timestamp: the stabilizing tier is a bare
`stable_check_count < 3` with no staleness term, so a media still inside it is due
every night no matter how recently it was checked.

Self-healing falls out of it — if MAL restores the entry, the 90-day check picks it
up with no admin action.

**Blacklisting is a separate, opt-out choice.** First draft defaulted the checkbox
**on**; the user flipped it, and the reasoning is the one that should survive: the
two mistakes are not symmetric. Forgetting to block costs one more trip through this
queue when a later sweep rediscovers the entry. Blocking wrongly is permanent —
nothing in the API or the UI removes a `media_unwanted` row.

**The low-signal detector needs an age floor.** `score IS NULL` turns out to be
almost exactly `scored_by < 50` (MAL withholds the mean below its own vote floor),
so vote count is the signal and duration is a red herring — Niu Lai is an 86-minute
feature, 20001-nen is 8 minutes, both junk. *Standalone* is the gate that carries
the rule: 275 finished media have no score, but 241 are legitimate side-entries of
real franchises.

The first version stopped there and raised 25 candidates, 17 of them from 2026. The
user's objection was correct and is the interesting part: MAL votes accumulate for
months after a premiere, so a current-season entry's empty vote count is *earliness*,
not a verdict. A one-year floor drops it to 8. Undated media (`aired_from IS NULL`)
fall out with the young ones — we cannot age them, and proposing deletion is the
wrong place to guess.

### Two things that were wrong on the way

**The identity-map trap, caught by a test.** `remove()` originally loaded
`Anime.media` in its first query. That put every sibling into the identity map
*without* their `relation_edges`; SQLAlchemy then skipped the nested loader on the
reclassify query — it leaves an already-loaded collection alone — and the classifier
tripped `lazy="raise"`. It would have failed on every franchise with a surviving
sibling. Fixed by not loading the collection early and adding `populate_existing` to
the reclassify query, which is needed anyway so the classifier is not handed a media
set still containing the deleted row.

**A claim that the postmortem check was dead.** Hoisting the blacklist gate above the
BFS (needed because `search_title` subtracts its own seed from the exclusion set, so
an admin-curated entry — ordinary content no downstream gate stops — would sail back
in), it looked like the existing check at the bottom of `user_scrape_dispatcher` was
now unreachable. A test disagreed: it also covers the BFS *discovering* a seed is a
PV and writing the `media_unwanted` row mid-scrape, which did not exist when the
hoisted gate ran. Both are needed, and the comment now names the two moments.

### Test pollution the SET NULL design creates

The low-signal pass is the one part of a sweep that is **catalogue-wide** — it
ignores the patched `select_due_media_for_sweep` and runs against whatever the
developer's DB holds. Four sweep tests call `update_sweep_dispatcher` directly rather
than through the harness, so a suite run was writing real candidate rows.

Two fixes, each with its own job: the harness stubs the pass (so
`delete_candidates_raised` does not depend on the local catalogue), and an autouse
id-watermark fixture cleans up what the tests do create. `tracked_anime` cannot cover
the latter — the candidate row deliberately outlives the anime cascade, which is the
whole point of the SET NULL.

### Verified against real MAL

The sweep was run through the running API (cron endpoint → worker → maintenance
bracket), not by importing the dispatcher. It refreshed 499/500 media in 11m26s and
produced `step1_failed: 1`, `delete_candidates_raised: 26`. Niu Lai's
`last_checked_at` moved to the run's timestamp — the first time it had moved since
the entry died — and `error_category` stayed `null`, so the 404 never touched the
circuit breaker.

### Carried as a side fix

`AnimeUmbrellaCard` declared `<table class="w-full">` with no `table-fixed` and
relied on `max-w-sm truncate` on the cells. In an auto-layout table those are only
hints — the column sizes to its content — so `max-w-sm` was inert and a long
`cover_image` URL pushed the table outside its card. Both change cards now use
`table-fixed` + `<colgroup>` and `break-words` rather than `truncate`, because on a
URL diff `truncate` cuts the *tail*, which is exactly the part that changed.

Not unit-tested: jsdom computes no layout, so the assertion would pass with or
without the fix (`rules/tests.md`). Verified visually instead.

## Block 10 — resurfacing a dismissal stops being a ceremony

Fell out of reviewing Block 9: the "Resurface" button in the dismissed-decisions
section sat behind a type-your-admin-username dialog, the same gate as a backup
restore. Checking `git log` showed that was not something Block 9 introduced —
it shipped with the section in `fef43cf` (v0.14.9) and the delete queue simply
inherited it by reusing the component.

**Why it was wrong.** The gate exists to make an irreversible action deliberate.
Resurfacing deletes a *decision*, not data: the candidate re-appears on the next
detection, and re-dismissing it is one click. It was the heaviest confirm in the
admin UI guarding the lightest action in it, one tier above deleting a backup
file.

**Ungate the API too, not just the UI.** Dropping the dialog while the endpoint
still demanded `confirm` would have meant the frontend auto-sending the username
— which keeps the awkward API surface while removing the only thing the gate
bought. So `delete_decision` lost `confirm`/`username` in all three services, the
three routers lost the body and the per-route `current_user` dependency, and
`DeleteDecisionRequest` was deleted. `CurationConfirmationMismatchError` now has
exactly one caller — applying a delete candidate — and its docstring says so
instead of describing the three it used to serve.

**Click-to-arm, not an inline confirm pair.** The codebase already has a
three-rung ladder: click-to-arm (completion unmark) → inline confirm/cancel
(merge, split, dismiss) → username dialog (backup restore, delete-apply). The
lightest rung is the right one, and `CompletionStatusCard`'s 3s auto-disarm is
the pattern to copy.

The one thing that needed thought is that the completion card gets no-reflow for
free — it is `size="icon"`, a fixed square swapping X → Check. A *text* button
shrinks: "Sure?" is shorter than "Resurface", so a plain label swap moves the
row. Hence `min-w-[7.5rem]`, floored at the wider label.

**A dead prop fell out.** `currentUsername` existed on the merge and split cards
only to feed that dialog, so both lost the prop and the admin page stopped
passing it. The delete card keeps it — its remove dialog is still gated.

**Two test notes.** The first assertion written for the new ungated endpoint was
vacuous: it compared the dismissed list against a re-fetch of *itself* filtered,
which holds whether or not the row went away. Rewritten to assert absence
directly, then confirmed as a guard by putting a required body back on the route
(`422 != 204`). And the three services' `..._username_gate` tests were not just
re-signatured but renamed — a test called "username gate" that no longer asserts
a gate is a lie in the file listing.

**Deferred, deliberately.** The username dialog is now down to two copies (backup
restore, delete-apply). `/simplify` flagged the third copy during Block 9 and the
extraction was skipped *because* this block was going to remove one; two is not
enough to earn a shared `UsernameConfirmDialog`.

## Block 11 — a 404 becomes loop control instead of an exception (`75478dc`)

Block 9 stamped the clock but kept the shape that caused the symptom.
`_refresh_one_anime` raised `MediaGoneUpstreamError` out of its per-media loop,
aborting the anime's savepoint, and the dispatcher rebuilt the lost state
afterwards — so the exception existed only to carry `media.id` across a rollback
it had itself caused. `HentaiRemoval`, in the same file, was already the
counter-example: the same situation as a return marker.

Handling it in the loop — raise the candidate, stamp, `continue` — is what
actually fixes the blast radius, and it deletes the error class, both
`Step1Failure.gone_media_*` fields, the unwrap, the re-read and the second commit.

**Both writes go in the savepoint.** The first plan raised the candidate on the
dispatcher's success branch, after the stamp had already committed. Splitting them
across two transactions makes the failure between them silent and long-lived: a
stamped clock with nothing queued takes the media off the sweep for the whole
long-tail window with no record to act on.

**`candidate_raised` travels per entry.** Sticky dismissal means a re-404 raises
nothing, so counting the list length would inflate the counter the Jobs Log tints
on.

**The progress gap became multi-causal.** A 404 is discounted from
`media_refreshed` — checked, not refreshed. The divergence notice had been
claiming the gap "retries next sweep", already false for Hentai removals since v7;
it now sizes the gap and points at the cards, which own what retries.

### The bug the refactor uncovered

`_probe_relations_for_anime` seeds off `anime.media`, and a dead media stays there
until an admin acts on its candidate — so it remains a probe seed long after the
404 is old news. That seed fetch raises `MalIdNotFoundError`, while the handler
written for exactly this case caught `AnimeNotFoundError`. They are **siblings**
under `PermanentPhsarError`, so it never fired: every sweep touching such an anime
failed its probe and left `AnimeFreshness` unstamped, which stops the franchise
discovering new media at all.

The first fix skipped the probe for any anime with a dead media, and that was the
wrong altitude — it only suppresses the failure on the night the 404 is fresh, and
a dead *Side* media never affected the seed list anyway (only `Main` ids seed).
Naming both exceptions is smaller and covers every night.

### Notes

The sibling case — a 404 on one media leaving the rest of a multi-media anime
refreshed — is the bug Block 9 documented and nothing asserted. Ordering is
load-bearing in that test: the dead media goes first, or a regression that aborts
never reaches the survivor. Proving the probe fix needed `_FakeScraper` to raise
`MalIdNotFoundError`, which it had never modelled.

Verified through the cron endpoint → worker: v9, 392/393 (the gap exactly the one
dead media), `step1_failed: 0`, `gone_upstream: 1`, `probe_failed: 0`. That run
predates the probe-handler fix, which is covered by test and sabotage only. Niu
Lai had to be pushed back past its due window first — Block 9's stamp had already
dropped it to the long-tail cadence, which is the fix working.

## Block 12 — the cover extension stops flapping

`main_picture.large` comes back from MAL v2 with a non-deterministic extension:
the identical CDN path answers `.jpg` from one backend and `.webp` from another.
Nothing about the image differs. Every sweep wrote the other spelling and logged
a diff for it.

**It is a reporting bug, not a data bug**, which is why it survived so long.
`cover_image` sits in `_METADATA_NONTEXT_FIELDS`, so a flip triggers no embedding
regen and no stability-counter reset — `embedding_regenerated: false` on every
one. What it destroyed was the audit trail: **1788 of 1890
`anime_umbrella_changes` entries (94%)** existed only because of a flip
(`anchor_changed: false`, `reclassified: []`, one `cover_image` field), so the
job-detail page's "Anime changes" card — the thing Block 3 spent effort
ordering — was reporting almost nothing real.

### The evidence, since the ratio is the whole argument

Across v6+ sweeps in `jobs.result_summary`: 4038 `cover_image` changes, 4x the
next-largest static-field diff (`mal_url`, 948). **3972 (98.4%) are the same path
with only the extension swapped** — `jpg→webp` 2096, `webp→jpg` 1876. Only 66 are
real cover replacements. 1167 of the 1598 affected media flipped more than once;
One Piece flipped 24 times on one path.

Onset is exactly the Jikan→MAL v2 migration (`cb125b0`): 1-2/day before, 92 that
day, and undiminished two months later. Jikan normalized the extension and v2
does not — so this is upstream behaviour, not migration residue that would age
out. Eight consecutive calls from one machine all returned `.jpg`, which is why
it reproduces on the VM and not on a laptop: it varies by which backend answers,
not per request.

### Why `.webp`, and the one URL that must not be rewritten

HEAD on all 4762 distinct catalogue covers rewritten to `.webp`: 4759 → 200. The
3 exceptions 404 in **both** formats — already-stale rows, not a webp gap. It is
also ~3x smaller (27-69 KB vs 99-178 KB sampled), which is the reason to pick it
over pinning to `.jpg` instead.

Media mal_id 39169 holds a Jikan-era `/img/sp/icon/apple-touch-icon-256.png`
placeholder whose `.webp` is a 404. MAL v2 omits `main_picture` for that anime
entirely and `_apply_metadata_diff` is None-guarded, so a bad rewrite there is
**unrecoverable** — nothing can ever produce the value again. The `.jpg` half of
the condition already excludes it, since it is `.png`; the `/images/anime/` half
does a different job, keeping the rewrite to the one path whose `.webp`
derivative is known to exist. Conflating the two is the error the notes below
record.

### One normalizer, not a patch on the sweep

`extract_information` is the only place `cover_image` originates from a MAL
payload. Every other writer — `media_unconnected_from_info`, the sweep's
`_METADATA_NONTEXT_FIELDS` loop, `reclassify_anime`'s umbrella copy,
`create_anime_from_media`, `_new_anime_from_anchor` — copies that dict or an
already-stored column. Normalizing at the anti-corruption layer covers all five;
normalizing in the sweep would have covered one.

### The migration converges both tables in one pass

~5300 rows were `.jpg` (4277 media, 1042 anime). The alternative — letting sweeps
drain it — is one final ~5300-change burst spread over weeks, with long-tail rows
taking 90-180 days at `JOBS_SWEEP_MAX_PER_RUN = 500`. That is the noise being
removed, stretched out, so a data migration is what makes the fix produce **zero**
transition noise.

**`media` and `anime` must move together, and that constraint is the reason it is
one migration rather than two statements anyone could reorder.** `reclassify_anime`
compares the umbrella row against its anchor media, so a catalogue with `media`
converted and `anime` not would report cover drift on every anime — and
`RELATION_BACKFILL_ON_STARTUP` fires at the next boot, well before any sweep. On
the dev DB after applying: 0 `.jpg` on both tables, the placeholder untouched, and
**0 anime whose cover disagrees with any of its media** — that last count is the
direct proof the two converged in the same pass, and is worth re-running rather
than inferring.

### Notes

Both tests were sabotage-checked and each fails only on its own mutation: making
the normalizer a no-op fails the equality test, dropping the path anchor fails the
pass-through test.

The pass-through test first asserted the real `/img/sp/icon/` placeholder, which
reads like the strongest possible case and is in fact vacuous. That URL is
excluded by the *path* half of the anchor, so every mutation keeping that half
leaves it alone, and every mutation dropping it is already caught by a `.jpg` off
the cover path. Sabotage is what settled it — the argument for keeping it survived
being written down and did not survive being run. A `.jpg` outside
`/images/anime/` is the only shape that separates the implementations.

No `result_summary` version bump: no key added, removed or reshaped.

Two things were rejected. A cover-availability HEAD pass at sweep start/end was
attractive — it would catch a stored URL going dead — but the 3 known-dead covers
404 in both formats, every cover render already falls back to a placeholder on
`onerror`, and the sweep re-fetches `main_picture` on its normal tier regardless.
Against that, a nightly 4762-request CDN scan fails toward "transient blip marks
thousands of media due", which is 1.3 h of MAL scraping at 1 req/s; damping it
costs more than the bug. A frontend `.webp → .jpg` fallback was rejected on the
measured 100% availability — it would replace one working `onerror` branch with
two in eight components.

`AnimeUmbrellaCard`'s comment justifying `break-words` over `truncate` cited
`.webp -> .jpg` as the tail that changed. That case no longer occurs; a genuine
cover diff differs mid-path, which still argues for the same CSS.
