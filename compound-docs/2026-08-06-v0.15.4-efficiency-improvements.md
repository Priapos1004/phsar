## Block A — index & migration hygiene

### The autogenerate drift was worse than "drift"

`alembic check` failed on **five** items, and two of them
(`ix_media_airing_now`, `ix_media_main_aired_from`) are the indexes root
`CLAUDE.md` documents as backing `select_due_media_for_sweep`. They existed only
in migration `8d4f2a1c9e7b`, never in `__table_args__`, so the *next* generated
migration would have dropped them — silently, unless someone read the diff
carefully.

**The durable rule:** an index that lives only in a migration is an index
autogenerate wants to delete. Declaring it in the model metadata is not
documentation, it's what keeps it alive.

### Gotcha: expression indexes must be spelled the way Postgres reflects them

`ix_jobs_scrape_query` was declared `func.lower(func.trim(payload["query"].astext))`
and proposed for drop-and-recreate on **every** autogenerate run. The cause is
that alembic diffs index expressions as *reflected strings*:

```
reflected (DB):  lower(TRIM(BOTH FROM payload ->> 'query'::text))
metadata:        lower(trim(payload ->> 'query'))
```

Postgres normalizes both spellings into the first when it stores the DDL, so the
`func.*` form could never match. Fixed by declaring the index with a
`text()` element in Postgres's own normalized form. **This changes no SQL** —
both spellings produce byte-identical stored DDL on both build paths
(`create_all` and the migration) — only what autogenerate compares.

The alternative considered and rejected: an `include_object` skip for this index
name in `env.py`. It would silence the noise but also silence *real* future
drift on the one index that most needs watching (it backs the dedup check on
every `/jobs/scrape` POST).

### The `alembic check` CI step needs its own database

The obvious placement — check the existing test DB — is useless, and this is
worth remembering because it looks fine:

`backend-test.yml` builds `testdb` with `Base.metadata.create_all` + `alembic
stamp head`. Running `alembic check` there compares **metadata against a schema
built from that same metadata**, so it passes no matter how far the migrations
have drifted. The check only means something against a database built by
*replaying the chain*, which is why the step creates a throwaway
`migrationcheck` DB and runs `alembic upgrade head` into it first.

Side benefit, and the reason the step is named "replay and match": this is now
the only place CI exercises the chain from empty at all — which answers the
v0.15.3 follow-up ("CI never replays the chain") far more cheaply than swapping
`create_all` for `upgrade head` in the test job. Verified locally: all 28
migrations apply to an empty DB and `alembic check` is green against the result.

### B3's index-drop justification is a write-path argument, not a size one

The two `last_checked_at` sidecar indexes are 88 kB and 56 kB — dropping them
for space would be pointless. The reason they're worth removing is that
`last_checked_at` is the only indexed **mutable** column on either sidecar, so
indexing it makes every sweep write a **non-HOT update** (prod: `n_tup_hot_upd
= 0` across ~5.1k lifetime updates). The nightly sweep pays that on every row it
touches.

They were also unusable, not merely unused: the staleness predicate is a
`coalesce` across a joined table (not sargable) and the `ORDER BY` sits on the
nullable side of a LEFT JOIN.

### Side effect of Stage 0: `pytest` is now slow locally

Not a Block A change, but it shapes the workflow for the rest of this branch.
The dev DB is a restored prod dump (66 MB) instead of the old 279-anime
catalogue, and the ~36 backup tests each shell out a **real** `pg_dump` /
`pg_restore` against it. The suite now takes tens of minutes locally where it
used to take a couple.

CI is unaffected — its DB is built empty by `create_all`, so its dumps are
trivial. This is a local-only cost, and the fix if it becomes intolerable is to
scope the backup tests to a small dedicated database rather than the dev one.
Worth a follow-up, not worth blocking this branch.

## Block D — payload size

### Decided up front: opt the backup download out of gzip

`GZipMiddleware` decides purely on size + content-type (it excludes only
`text/event-stream`), so the backup `FileResponse` — a `pg_dump -Fc` archive,
already zlib-compressed, up to ~2 GiB — would be streamed through gzip for ~0 %
gain, burning CPU on a 2-vCPU VM and dropping `Content-Length`. Setting
`Content-Encoding: identity` on that one response opts it out:
`IdentityResponder.send_with_compression` skips compression whenever
`content-encoding` is already present (verified in starlette 0.46.2's source).

Known wart to record rather than hide: RFC 9110 reserves `identity` for
`Accept-Encoding`, so this is the pragmatic FastAPI opt-out idiom, not a
conforming header. Alternatives weighed were accepting the waste (admin-only,
rare) and a custom middleware with a content-type allowlist (starlette keeps its
exclusion list in a module-level constant read inside the responder, so a clean
subclass means reimplementing more than it first appears).
