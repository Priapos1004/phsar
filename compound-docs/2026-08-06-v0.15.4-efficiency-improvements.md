# v0.15.4 — efficiency improvements

## Summary

Implements the findings measured in
[the performance baseline](2026-08-06-performance-baseline.md), which stays the
*reference* doc — the numbers a future release re-runs. This one holds the
decisions and the dead ends, which the diff cannot show.

The theme worth carrying forward: **every genuinely useful thing on this branch
came from asking a question the measurement did not ask.** The baseline found
slow queries and they were fixed as predicted. What it could not find — a latent
ordering bug, a filter helper duplicated in two spellings, a rule that described
code it no longer matched, a config file that never loaded — is the part that
took judgment, and it is most of what follows.

## Key decisions

**An index declared only in a migration is an index autogenerate wants to
delete.** Two indexes backing `select_due_media_for_sweep` lived in a migration
but never in `__table_args__`, so the next generated migration would have dropped
them — silently, unless someone read the diff closely. Declaring an index in
model metadata is not documentation; it is what keeps it alive. `alembic check`
in CI is the guard.

**Expression indexes must be spelled the way Postgres reflects them.** Alembic
diffs index expressions as reflected strings, and Postgres normalizes
`lower(trim(payload ->> 'query'))` into `lower(TRIM(BOTH FROM payload ->>
'query'::text))` when it stores the DDL — so a `func.*` spelling can never match
and gets proposed for drop-and-recreate on every run. Declaring it with a
`text()` element in Postgres's own normalized form changes no SQL on either build
path, only what autogenerate compares. *Rejected:* an `include_object` skip in
`env.py`, which would silence the noise and also silence real future drift on the
one index that most needs watching — it backs the dedup check on every
`/jobs/scrape` POST.

**`alembic check` needs its own chain-replayed database.** The obvious placement
is useless in a way that looks fine: the test DB is built by
`Base.metadata.create_all` + `alembic stamp head`, so checking there compares
metadata against a schema built from that same metadata and passes no matter how
far the migrations have drifted. The check only means something against a
database built by replaying the chain, hence the throwaway `migrationcheck` DB.
Side benefit: this is now the only place CI exercises the chain from empty.

**Dropping the sidecar `last_checked_at` indexes is a write-path argument, not a
size one.** At 88 kB and 56 kB, dropping them for space would be pointless. They
matter because `last_checked_at` is the only indexed *mutable* column on either
sidecar, so indexing it makes every sweep write a non-HOT update — paid on every
row the nightly sweep touches. They were also unusable rather than merely unused:
the staleness predicate is a `coalesce` across a joined table, so it isn't
sargable, and the `ORDER BY` sits on the nullable side of a LEFT JOIN.

**Genre majority moved from HAVING to WHERE, and that is the stronger form.** It
reads like a semantic loosening and is the opposite: the invariant is *a filter
selects which anime, it never rescopes the aggregates*, and `Anime.id IN (…)` is
exactly the shape that guarantees it — the HAVING form was the one comparing
against `media_count`, an aggregate over the grouped rows. It is deliberately a
**second, separate** `IN` rather than folded into the existing categorical/studio
subquery: those conditions must all hold for the *same* media row ("studio X +
type TV" = one media that is a TV by X), whereas genre majority is an aggregate
over the anime's whole media set. Folding them would silently change both.

**The ordering aggregate must be size-invariant.** `min(vector)` doesn't exist in
pgvector, so the aggregate goes around `cosine_distance(...)`, not the embedding.
Less obvious: anime-level title search groups over the joined media rows, so a
6-media anime contributes six identical rows. `min` and `avg` are
size-invariant; `sum` would rank a franchise six times worse purely for being a
franchise. No existing ranking fixture had more than one media per anime, so
nothing would have caught it.

**The embedding cache memoizes the sync encode and hands back a copy.**
`functools.lru_cache` can't wrap the coroutine — it would cache an awaitable
usable once. The cached value is shared by every caller of a key and callers
assign it straight onto ORM attributes, so `_encode_cached` returns a tuple and
`generate_embedding` copies it into a fresh list per call; a cached list would be
a shared mutable with no owner, and one caller mutating its embedding would
corrupt every later hit on that text. A hit still pays the thread hop —
microseconds against a ~30 ms miss, versus maintaining an on-loop fast path and a
threaded slow one for a single operation.

**Query and document embeddings need separate caches.** A single shared LRU is
the wrong shape: document text (titles, descriptions, notes) has a structurally
0 % hit rate, and a sweep inserts thousands of such keys, evicting every query —
leaving the cache coldest right after the nightly window.

**The backup download opts out of gzip.** `GZipMiddleware` decides on size +
content-type alone, so a `pg_dump -Fc` archive — already zlib-compressed, up to
~2 GiB — would stream through gzip for ~0 % gain, burning CPU on a 2-vCPU VM and
dropping `Content-Length`. Setting `Content-Encoding: identity` opts it out.
Recorded rather than hidden: RFC 9110 reserves `identity` for `Accept-Encoding`,
so this is the pragmatic FastAPI idiom, not a conforming header. *Rejected:*
accepting the waste (admin-only, rare), and a custom middleware with a
content-type allowlist — starlette keeps its exclusion list in a module-level
constant read inside the responder, so a clean subclass reimplements more than it
first appears.

**Denylist, not allowlist, for the Jobs Log summary projection.** An allowlist is
more future-proof — a new heavy key stays out automatically — but it has to
enumerate every kind's small keys, and a forgotten entry *blanks a Jobs Log
cell*. The denylist's failure is that a future heavy key re-inflates a payload:
worse in theory, far more visible, and it cannot render wrong data.

**`set_committed_value` is what keeps that projection from leaking upward.** The
list needs a different `result_summary` than the detail endpoint without the
shared response schema splitting in two. The DAO defers the real column, selects
`result_summary - text[]` alongside the entity, and writes the projected value on
as if it had been loaded; service and schema layers are untouched. Plain
assignment would mark the instance dirty, which is the version of this that
eventually persists a truncated summary. `defer(..., raiseload=True)` guards the
other side.

**A visibility-gated poll is gated on elapsed time, not on the transition.**
Fired on every hidden→visible transition, an admin flicking between admin tabs
issues a full request per return, where the ungated 30 s interval would have
issued one — so gating on the transition can cost *more* than not gating at all.
The catch-up fetch exists to make up for missed ticks; when none were missed
there is nothing to make up.

**Describe an exception by its property, never by listing its members.** The
services-run-SQL exception in `backend.md` named three categories covering well
under half the sites, so a reader could not answer "is my case inside it?" — the
only question the exception exists to answer. The rewrite gives a test instead:
new SQL goes in a DAO, assume you are outside the exception. This is the
"don't write counts that go stale" rule applied to a set rather than a number — a
list of members is a count in prose and decays the same way.

## Failed approaches

**Scoping the genre-majority denominator (proposed at PR review, measured
worse).** `media_totals` aggregates the whole `media` table on every
genre-filtered search, which looks like an obvious fixed cost to scope down to
the anime that can actually join. Measured on the prod dump, the scoped form is
slower at every genre count — 5.30 ms vs 4.18 ms at one genre, 16.28 ms vs
8.70 ms at three — because the scoping subquery makes Postgres compute
`genre_counts` twice. The unscoped aggregate is ~1.9 ms of the 4.18 ms and a
forced index-only path saves ~0.35 ms, which the planner won't choose anyway. The
lever here is not the denominator.

**`LEFT JOIN LATERAL` for the correlated `array_agg`.** The obvious optimization,
and it produces a byte-identical plan (11.0 ms / 6,239 buffers against the
correlated form's 9.3 ms / 6,239). Grouping over the whole catalogue was worse
still (17.2 ms). What worked was grouping *scoped to the user's media* (5.0 ms),
which also stops the cost scaling with page size.

**A shared cache factory for the frontend session caches.** The genuinely common
body is ~8 lines; a generic `createRequestCache<K,T>` is ~14 on its own, and
`genres.ts` can't join it — it populates a writable, returns `Promise<void>`, and
*swallows* failures because tooltips are progressive enhancement. Folding it in
would mean options for store-vs-promise and rethrow-vs-swallow, which is where a
factory starts costing more than it saves. Revisit at a third keyed, rethrowing
cache.

**Two rewrites of the anime genre filter's nested loop.** Postgres underestimates
`genre.name IN (...)` selectivity by ~7×, so it nested-loops back into `media`;
10,407 of 11,330 buffers are that probe, just to fetch `anime_id`. Neither
rewrite moved the plan. The lever is getting `anime_id` onto the genre rows.

**Testing a rule's `paths:` widening — both arms lied before telling the truth.**
The first pass asked a question the model could answer *without* the rule, by
reasoning from context it already had, so a correct answer proved nothing. The
second returned a false *absent*: the prompt said "do not read anything under
`.claude/rules/`", and the model honoured that as a gag order on knowledge it
already had rather than as a scoping instruction. A prohibition in the test prompt
fakes the very failure the test is looking for — ask for "guidance already in your
context" instead of forbidding a directory.

## Gotchas & learnings

**Buffer counts are not portable across harnesses, and this bit twice.** A
harness that sums every `Buffers: shared hit=` in the plan tree double-counts,
because EXPLAIN reports cumulatively up the tree; top-level figures and summed
figures differ by several times. Fold *ratios* between docs, never absolutes.
The second bite was at PR review, where a reviewer compared one harness's
"before" against another's "after" and reported a 2.8× regression that
re-measurement showed does not exist — the landed form beats the old one on both
buffers and wall-clock at every genre count.

**A flat projection made a latent ordering bug visible.** The rewrite produced
every field identical but a different row *order*. Not a regression: both queries
ordered by `modified_at` alone, and that column ties hard on real data — a bulk
rate stamps one timestamp across every media in an anime, so the biggest tie group
was 12 rows. The same request could already render tied rows differently on two
loads. Two things made the verification honest: **equivalence had to be judged
modulo ties** (comparing raw order would have reported a false failure, so the
harness compares the sequence of tie *groups*), and **the test asserts that repeat
calls agree rather than asserting a fixed order** — a hardcoded expected order
passes against a nondeterministic query on a small fixture.

**A review panel only looks where you point it either — and the same shape
recurs.** The tiebreak sweep prompted by the panel converted the newest-first
orderings and walked straight past the *ascending* ones, where the tie is
stronger: a backfill inserts an entire candidate set in one transaction, so the
whole first-run admin queue shares a `created_at` and reshuffles between
refreshes. Descending was where the attention was, so descending was what got
fixed — one loop out from the lesson below, and the same lesson.

**A measurement harness only looks where you point it.** The tiebreak was first
applied only to the two queries the harness had exercised. Two others ordered on a
bare timestamp and were *paginated*, where a tie doesn't merely reshuffle — the
same row can appear on page 1 and page 2, or be skipped — and the ties are
guaranteed by construction there, since a seasonal sweep bulk-inserts hundreds of
children in one transaction. "I fixed the thing I measured" and "I fixed the
thing" are different claims; the second needs someone asking *where else does this
shape occur*. The rule now lives once, in `base_dao.recency_order(model)`, at every
newest-first site.

**The Jobs Log projection does not save the database read.** The tempting phrasing
("the heavy arrays never leave Postgres") is wrong. `jsonb - text[]` resolves to
`jsonb_delete_array`, which needs a fully materialised value — there is no partial
detoast for jsonb the way there is for text — so every listed row still pays the
full TOAST read and decompression, plus an allocation for the trimmed copy.
Postgres-side cost goes marginally *up*. What the change removes is everything past
the socket, which is both the larger half and the half that repeats on a 3 s poll.

**An entity carrying a value the database doesn't have is a liar inside its
session.** Once the list query runs, that row sits in the identity map with a
projected summary and the next read gets the truncated version. Production sessions
are per-request and would not have hit it, which is exactly why it would have
survived to become a real bug the first time anything else read a job in that
session. `populate_existing=True` on the detail query is the fix — that endpoint
must be authoritative about the whole summary. A test found this, not a reviewer,
because the list and detail assertions were merged onto **one seeded row**;
splitting them for tidiness would have hidden it, and either assertion alone passes
vacuously.

**A guard test is worth nothing until you have watched it go red.** Every invariant
test on this branch was verified against an injected fault rather than assumed to
work — coalescing a pre-aggregated `min_stable` (which moves a media-less anime
into the wrong tier), breaking the scrape-dedup index expression, short-circuiting
the poll's visibility check. This matters most when a test asserts a *negative*
("no fetch fired"), which passes for many reasons other than the intended one.
Asking Postgres whether an index is still usable (`EXPLAIN` with
`enable_seqscan=off`) beats comparing SQL strings, which would need the very
normalization under test — and note the index is *partial*, so the probe query must
constrain the partial column or the planner can't use it regardless.

**A config file that looks correct proves nothing about whether anything loads
it.** This branch re-learned it three times, on three artifact kinds. Rubric files
under `.claude/agents/` do not register as agent types, so a pipeline naming them
fails loudly mid-run; the fix is to *read* the rubric into a general agent, which
keeps the anti-drift property without depending on registration. A skill's `!`
pre-run fence is permission-checked as one literal string, so a `$( … )` inside it
is refused before the body is ever read — that step shipped dead and stayed silent
until someone invoked it. And the rule that owns this lesson had a `paths:` glob too
narrow to load when either was being edited. Write the falsifying check before
trusting the file.

**`$CLAUDE_PROJECT_DIR` is set for hooks, not for tool calls.** It is the obvious
way to make a skill's script invocation cwd-independent, and it expands to the
empty string in an ordinary Bash tool call — so `"$CLAUDE_PROJECT_DIR"/.claude/…`
resolves to `/.claude/…` and fails. The working form is
`cd "$(git rev-parse --show-toplevel)" && …`, which also self-heals the cwd that
caused the problem. This is the same lesson as the paragraph above on a fourth
artifact, and it arrived the same way: a reviewer proposed the variable, the fix
looked right, and running it was the only thing that said otherwise.

**A glob that enumerates kinds fails by matching nothing.** The sequence
`rules` → `{rules,agents}` → `{rules,agents,skills}` widened once per artifact that
had already broken. A brace set has to be edited by whoever adds a kind, and its
failure is silent; `.claude/**/*.md` does not have that property.

**Prose describing code cannot be reviewed by reading the prose.** Auditing a
rules rewrite endpoint-by-endpoint falsified three claims, one of which contradicted
a definition three paragraphs earlier in the same file that the rewrite had just
added. Every claim needs the grep that would falsify it, because a confident
sentence about code reads exactly the same whether or not it is true. The PR panel
confirmed the point from the other side: its largest crop of real findings was doc
claims that had drifted from the code they described — a bucket count, a poll that
was never built, an invariant stated as absolute that six call sites broke.

**A rule that a piece of code violates is sometimes the rule being wrong.** A
router committing in a handler looked like drift against the rewritten layering
rule; it turned out seeders deliberately do not commit, so their caller owns the
transaction. The rule gained the convention rather than the code gaining a service.

**The reusable piece is often one level below where the extraction stopped.** A
first cut exported `isSessionLive(exp, now)`, but the caller still computed
`exp * 1000 - now` itself — so the single expiry rule was half-shared, and the
leftover arithmetic forced a cast. `sessionRemainingMs` is the right primitive.
Worth remembering as a smell: **a cast next to a freshly extracted guard usually
means the extraction stopped one level too high.**

**Reading a performance finding literally can ship a bug.** The baseline listed
`refreshTags()` on every `/watchlist` mount as duplicate work, since login already
populates the store. It isn't quite: the tag counts are server-side and go stale as
entries change. Their only consumer mounts on demand, so the call moved there rather
than being deleted.

**A real cache trades away the one safety a per-mount fetch has for free.** Buying
it back is explicit invalidation at every write site. Centralizing that in the API
client keyed on path was argued against and rejected: that layer is deliberately
dumb — it has no global 401 handler for the same reason — and implicit cache
behaviour there would be invisible at the call site.

**Local dev now pays for the prod-shaped database.** The dev DB is a restored prod
dump instead of a small hand-scraped catalogue, and the backup tests each shell out
a real `pg_dump`/`pg_restore` against it, so the suite takes tens of minutes
locally. CI is unaffected — its DB is built empty. Scoping the backup tests to a
small dedicated database is the fix if it becomes intolerable.

## Future work / debt

- **CI builds its test schema from `create_all`, not the migration chain.** The
  deeper fix — build the test DB with `alembic upgrade head` and delete the
  `create_all` block, the extension `CREATE`s and the `stamp head` hack — would make
  the whole suite run against a migration-built schema. Deferred deliberately: it is
  a CI-wide semantic change (a broken migration would fail the entire suite) and
  deserves its own commit and green run.
- **`/filters/options` could drop three more round trips** with a
  `MediaDAO.filter_bounds()` selecting all four min/max pairs in one statement, at
  which point `get_min_max`'s string-keyed reflection guard could go too.
- **The anime genre filter still nested-loops back into `media`** — see the failed
  rewrites above; the lever is getting `anime_id` onto the genre rows.
- **`ratingScores` invalidation is per-tab.** The cache is module state, so a write
  in one tab leaves another tab's copy stale for the rest of the session, and several
  Phsar tabs are a normal way to use the app. Closing it wants a cross-tab broadcast
  (the `storage`-event idiom `auth.ts` already uses, or a `BroadcastChannel`) — new
  shared infrastructure, so it is a design decision rather than a review fix.
- **Nothing clears a token the server rejects before it expires.** After a
  `SECRET_KEY` rotation or a user deletion, the local `exp` guard passes and no 401
  handler exists to notice, so the tab renders signed-in with empty data until
  expiry. Bounded by `ACCESS_TOKEN_EXPIRE_MINUTES`; the escape is Sign out. A narrow
  escalation (count consecutive 401s on non-`/auth/*` paths) would restore the
  self-heal without reinstating the global handler the countdown flow needs absent.
- **`refreshTags()` now fires per Lists-tab open** rather than per page visit, since
  the tab is conditionally rendered. Correct, but a strict inversion for an admin
  flicking between tabs; a staleness guard like `ratingScores`' would fix it.
- **`visible` tracks the admin tab, not the browser tab.** Parked on the Jobs Log in
  a backgrounded window, the poll still runs — browsers throttle hidden-tab intervals,
  they don't stop them. Closing it wants a shared document-visibility primitive, and
  should take `JobBell` with it (2 s/30 s, ungated, mounted on every page), which is
  the larger consumer.
- **The prose reviewers don't check rules against the code they describe.** That
  needs a reviewer that reads the code behind each claim; worth adding once these
  have some mileage.
- **The baseline doc's B7 "landed" row mixes harnesses** with its own before-table,
  which is what produced the phantom regression above. Worth re-measuring both halves
  with one harness the next time that document is re-run.
