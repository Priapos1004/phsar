## Block A — index & migration hygiene

### The autogenerate drift was worse than "drift"

`alembic check` failed on **five** items, and two of them
(`ix_media_airing_now`, `ix_media_main_aired_from`) are the indexes root
`CLAUDE.md` documents as backing `select_due_media_for_sweep`. They existed only
in migration `8d4f2a1c9e7b`, never in `__table_args__`, so the *next* generated
migration would have dropped them — silently, unless someone read the diff
carefully.

**The durable rule:** an index that lives only in a migration is an index
autogenerate wants to delete. Declaring it in the model metadata is not
documentation, it's what keeps it alive.

### Gotcha: expression indexes must be spelled the way Postgres reflects them

`ix_jobs_scrape_query` was declared `func.lower(func.trim(payload["query"].astext))`
and proposed for drop-and-recreate on **every** autogenerate run. The cause is
that alembic diffs index expressions as *reflected strings*:

```
reflected (DB):  lower(TRIM(BOTH FROM payload ->> 'query'::text))
metadata:        lower(trim(payload ->> 'query'))
```

Postgres normalizes both spellings into the first when it stores the DDL, so the
`func.*` form could never match. Fixed by declaring the index with a
`text()` element in Postgres's own normalized form. **This changes no SQL** —
both spellings produce byte-identical stored DDL on both build paths
(`create_all` and the migration) — only what autogenerate compares.

The alternative considered and rejected: an `include_object` skip for this index
name in `env.py`. It would silence the noise but also silence *real* future
drift on the one index that most needs watching (it backs the dedup check on
every `/jobs/scrape` POST).

### The `alembic check` CI step needs its own database

The obvious placement — check the existing test DB — is useless, and this is
worth remembering because it looks fine:

`backend-test.yml` builds `testdb` with `Base.metadata.create_all` + `alembic
stamp head`. Running `alembic check` there compares **metadata against a schema
built from that same metadata**, so it passes no matter how far the migrations
have drifted. The check only means something against a database built by
*replaying the chain*, which is why the step creates a throwaway
`migrationcheck` DB and runs `alembic upgrade head` into it first.

Side benefit, and the reason the step is named "replay and match": this is now
the only place CI exercises the chain from empty at all — which answers the
v0.15.3 follow-up ("CI never replays the chain") far more cheaply than swapping
`create_all` for `upgrade head` in the test job. Verified locally: all 28
migrations apply to an empty DB and `alembic check` is green against the result.

### B3's index-drop justification is a write-path argument, not a size one

The two `last_checked_at` sidecar indexes are 88 kB and 56 kB — dropping them
for space would be pointless. The reason they're worth removing is that
`last_checked_at` is the only indexed **mutable** column on either sidecar, so
indexing it makes every sweep write a **non-HOT update** (prod: `n_tup_hot_upd
= 0` across ~5.1k lifetime updates). The nightly sweep pays that on every row it
touches.

They were also unusable, not merely unused: the staleness predicate is a
`coalesce` across a joined table (not sargable) and the `ORDER BY` sits on the
nullable side of a LEFT JOIN.

### Side effect of Stage 0: `pytest` is now slow locally

Not a Block A change, but it shapes the workflow for the rest of this branch.
The dev DB is a restored prod dump (66 MB) instead of the old 279-anime
catalogue, and the ~36 backup tests each shell out a **real** `pg_dump` /
`pg_restore` against it. The suite now takes tens of minutes locally where it
used to take a couple.

CI is unaffected — its DB is built empty by `create_all`, so its dumps are
trivial. This is a local-only cost, and the fix if it becomes intolerable is to
scope the backup tests to a small dedicated database rather than the dev one.
Worth a follow-up, not worth blocking this branch.

## Block B — search-path SQL

### Buffer counts here are NOT comparable to the baseline doc's

Worth stating before the numbers: this branch's harness sums every
`Buffers: shared hit=` in the plan tree, and EXPLAIN reports those
**cumulatively up the tree**, so a parent node re-counts its children. The
baseline doc used top-level figures. All the before/after pairs below are
internally consistent (same harness, same queries, best-of-3) but the absolute
values run several times the doc's. Fold the *ratios*, not the absolutes, back
into the baseline doc.

### B7 — the fix moves genre from HAVING to WHERE, and that's the stronger form

The per-genre correlated subquery lived in `apply_anime_having_filters`. The
replacement — one non-correlated pass, then `Anime.id IN (…)` — necessarily
moves it into `apply_anime_pre_filters`.

That reads like a semantic loosening and is the opposite: the documented
invariant is *"a filter selects WHICH ANIME, it never rescopes the aggregates,"*
and `Anime.id IN (…)` is exactly the shape that guarantees it. The HAVING form
was the one comparing against `media_count`, an aggregate over the grouped rows.

But it is deliberately a **second, separate** `IN` condition rather than being
folded into the existing categorical/studio subquery. Those conditions all have
to hold for the SAME media row ("studio X + type TV" = one media that is a TV by
X); genre majority is an aggregate over the anime's whole media set. Folding
them would silently change both.

| genres | buffers before → after | ms before → after |
|---|---|---|
| 0 | 2,894 → 2,894 | 21.1 → 16.1 |
| 1 | 318,566 → 75,373 | 28.6 → 14.1 |
| 2 | 439,780 → 126,008 | 26.3 → 10.4 |
| 3 | 484,173 → **177,024** | 48.6 → **10.3** |

**Results identical and in the same order at every genre count.** The headline
isn't the 2.7×, it's that wall-clock is now **flat** in the genre count
(14.1 / 10.4 / 10.3) where it used to climb — the superlinearity is gone, which
is what mattered since this fires on ticking chips.

### B1 — `min()` must wrap the distance, and must ignore group size

`min(vector)` doesn't exist in pgvector, so the aggregate goes around
`cosine_distance(...)`, not the embedding. Less obvious, and the thing the new
test pins: anime-level title search groups over the **joined media rows**, so a
6-media anime contributes 6 identical rows and a 1-media anime contributes 1.
The ordering aggregate therefore has to be size-invariant. `min` and `avg` are;
`sum` would rank a franchise six times worse purely for being a franchise. No
existing ranking fixture had more than one media per anime, so nothing would
have caught that.

187,511 → 45,100 buffers and **GroupAggregate + full sort → HashAggregate** on
all three probe queries (literal substring, typo'd, purely thematic), with **0
mismatched positions across all 50 rows** each.

### B8 — why the cache can't hand back a list

`functools.lru_cache` can't wrap the coroutine (it would cache a coroutine
object, awaitable once). So the memo goes on the **sync** encode, and
`generate_embedding` keeps its single `to_thread` path.

The cached value is shared by every caller of a key, and callers assign the
result straight onto ORM attributes — so `_encode_cached` returns a **tuple** and
`generate_embedding` copies it into a fresh list per call. A cached list would be
a shared mutable with no owner: one caller mutating its embedding would corrupt
every later hit on that text. `test_cache_hits_do_not_alias_the_returned_list`
mutates a returned list and asserts the next call is unaffected.

A hit deliberately still pays the thread hop — microseconds against a ~31 ms
miss, and the alternative is an on-loop fast path plus a threaded slow one for
one operation.

Measured (median of 10, per the baseline's own warning against best-of-N on CPU
work): distinct queries **31.5 ms**, repeat **0.10 ms** — a **310×** hit, and the
doc's finding that a repeat cost the same as a fresh encode is gone.

## Block C — admin + filter-options SQL

### B2 — all four atoms moved, not just the one that was measured

The baseline attributed the cost to the correlated `MIN(stable_check_count)`
being compiled once per stabilize level. That's right, but `_sweep_atoms` also
had two `EXISTS` and a correlated `MAX`, and since `_sweep_atoms` has exactly
**one** consumer there was no reason to leave them: all four roll up from the
same `GROUP BY media.anime_id`, so one CTE replaces four correlated
constructs.

| | buffers | ms | SubPlan mentions |
|---|---|---|---|
| as shipped | 272,059 | 27.2 | **18** |
| one CTE | **5,127** | **4.40** | **0** |

All 7 buckets identical at **both** grains (anime 169 · 31 · 476 · 239 · 209 with
14/9/8; media 185 · 32 · 741 · 1530 · 2007 with 15/9/8), and both still sum
exactly to the catalogue totals (1,124 / 4,495). 4.40 ms lands inside the
baseline's predicted 4.5–5.2.

### The no-coalesce rule has teeth, and I checked

The baseline warned: don't coalesce the pre-aggregated `min_stable`, because the
shipped scalar subquery yields NULL for a media-less anime, which must fall
through to `long_cycle`. With a LEFT JOINed CTE the hazard is the same and looks
even more like something to tidy up — an un-coalesced join column is exactly what
a reviewer "fixes".

So `test_media_less_anime_falls_through_to_long_cycle` exists, and I verified it
**fails** on the injected mistake rather than assuming it would: wrapping
`facts.c.min_stable` in `coalesce(..., 0)` moves the anime from `long_cycle` to
`stabilizing` and the test catches it. A test for a subtle invariant is worth
nothing until you've watched it go red.

### B4 — the discarded work was 4 of the media path's 15 round trips

`get_min_max` delegated to a general field-stats helper that ran a **second**
query per field for `avg`/`stddev`/`median`, of which the caller kept neither —
the `percentile_cont` sort was discarded on the next line.

| view_type | round trips | `percentile_cont` queries | ms |
|---|---|---|---|
| media | 15 → **11** | 4 → **0** | 149 → 119 |
| anime | 8 → 8 | 0 → 0 | 41.4 → 41.0 |

Payload identical (17 keys) at both view types. The anime path is untouched
because it never called `get_min_max` — its cost is the two full
`GROUP BY media.anime_id` passes, which is a separate question.

`get_field_stats` is **deleted** rather than kept "for later": it had no other
caller and no test, and its two validation raises — the only thing standing
between a field-name string and a `func.min` over it — were uncovered as a
result. Those moved to `_numeric_field` and now have their own tests, including
the hybrid-expression path (`total_watch_time` reaches the aggregate through the
`hasattr` half of the guard, which the media filter-options path depends on).

## Block D — payload size

### Decided up front: opt the backup download out of gzip

`GZipMiddleware` decides purely on size + content-type (it excludes only
`text/event-stream`), so the backup `FileResponse` — a `pg_dump -Fc` archive,
already zlib-compressed, up to ~2 GiB — would be streamed through gzip for ~0 %
gain, burning CPU on a 2-vCPU VM and dropping `Content-Length`. Setting
`Content-Encoding: identity` on that one response opts it out:
`IdentityResponder.send_with_compression` skips compression whenever
`content-encoding` is already present (verified in starlette 0.46.2's source).

Known wart to record rather than hide: RFC 9110 reserves `identity` for
`Accept-Encoding`, so this is the pragmatic FastAPI opt-out idiom, not a
conforming header. Alternatives weighed were accepting the waste (admin-only,
rare) and a custom middleware with a content-type allowlist (starlette keeps its
exclusion list in a module-level constant read inside the responder, so a clean
subclass means reimplementing more than it first appears).

### B12 — the flat projection surfaced a latent ordering bug

This is the finding worth keeping from Block D. The rewrite produced **all 456×36
and 341×25 fields identical**, but the row ORDER differed — 69 positions in
ratings, 230 in watchlist. Not a regression in the new code: both queries order
by `modified_at DESC` **only**, and on real data that column ties hard.

| | rows | distinct `modified_at` | biggest tie group |
|---|---|---|---|
| ratings | 456 | 369 | 7 |
| watchlist | 341 | 156 | **12** |

A bulk rate (or bulk watchlist-add) stamps one timestamp across every media in
an anime, so ties are the common case. Within a tie group the order was whatever
the planner emitted — and `get_all_for_score_items`' own docstring says the
consumer relies on the incoming order ("the client's stable sort breaks full ties
by recency without an extra sort key"). So **the same request could already
render tied rows in a different order on two loads**; the projection change only
made the pre-existing nondeterminism visible.

Fixed by adding `id DESC` as a second sort key to both. Two things that made the
verification honest:

- **Equivalence had to be judged modulo ties.** Comparing raw order would have
  reported a false failure. The harness compares the *sequence of tie groups*
  instead: 369 / 156 groups identical in sequence **and** membership, so no row
  crossed a `modified_at` boundary — which is all the old ORDER BY ever
  guaranteed. Only within-group order moved.
- **The test asserts repeat calls agree, not a fixed order.** A hardcoded
  expected order passes even against a nondeterministic query on a small
  fixture; stability is the property that matters.

### B12 — where the time actually goes now

| | round trips | fetch | + DTO build |
|---|---|---|---|
| `/ratings/scores` as shipped | 7 | 104.6 ms | 136–311 ms total |
| `/ratings/scores` flat | **1** | **25.9 ms** | 44.3 ms total |
| `/watchlist/items` flat | **1** | 12.6 ms | 22.7 ms total |

The baseline predicted 18.0 ms for the fetch; 25.9 is the honest number (best-of-3
warm). Worth noting the DTO build is now ~40% of the remaining cost — 456
Pydantic constructions at 18.4 ms — so that, not the query, is what a future pass
would attack.

### B13 — compression ratios reproduced exactly

7.2× on `/ratings/scores` (625.7 → 86.7 KiB) and 6.6× on `/watchlist/items`
(372.0 → 56.1 KiB), matching the baseline to the tenth of a KiB. Registered
between the maintenance gate and CORS so the CORS-outermost invariant survives;
`test_maintenance_503_still_carries_cors_headers` pins that a 503 short-circuit
still carries its CORS header, which is the failure the ordering rule exists for.

The backup-download opt-out is covered by asserting the response's first five
bytes are `PGDMP` and that `gzip.decompress` raises — a header-only assertion
would pass if the header were present but ignored.

## The `/simplify` pass found a bug the measurements couldn't

Run over the whole branch after Block D (Blocks A–C were already committed
without it — a process miss). Four angles in parallel: reuse, simplification,
efficiency, altitude. Worth recording what a quality pass caught that
before/after measurement structurally could not:

### The tiebreak was applied only where it was measured

Block D added `(modified_at DESC, id DESC)` to the two list queries whose
ordering the harness had exercised. Two others order on a bare timestamp and are
**paginated**: `RatingDAO.get_all_by_user` and `JobDAO.list_all`. There a tie
doesn't merely reshuffle — the sort may place a tied row differently per page
fetch, so the same row appears on page 1 *and* page 2, or is skipped. And the
ties are guaranteed by construction in exactly those two: a seasonal sweep
bulk-inserts hundreds of children in one transaction, so `server_default=now()`
stamps them identically.

**The lesson:** a measurement harness only looks where you point it. "I fixed the
thing I measured" and "I fixed the thing" are different claims, and the second
needs someone asking *where else does this shape occur*. The rule now lives once,
in `base_dao.recency_order(model)`, used at all four sites.

### The efficiency angle beat its own hand-written SQL

The reviewer benchmarked the correlated `array_agg` at ~78% of the projection's
cost and then falsified two plausible fixes before proposing one:

| shape | time | buffers |
|---|---|---|
| correlated `array_agg` (as merged) | 9.3 ms | 6,239 |
| `LEFT JOIN LATERAL` | 11.0 ms | 6,239 — *identical plan* |
| grouped over the whole catalogue | 17.2 ms | 2,216 — *worse* |
| **grouped, scoped to the user's media** | **5.0 ms** | **2,986** |

`/ratings/scores` fetch: 25.9 → **21.7 ms**, total 189 → **155 ms**, DTOs
byte-identical — and the cost no longer scales with page size. The LATERAL
result is the useful part to keep: it's the obvious optimization and it does
nothing here.

### One rule, two spellings — the genre-majority copy

`_anime_genre_majority_condition` reproduced
`filter_service._get_anime_majority_genres` rather than sharing it. The tell was
in the diff: the only change to `filter_service` was updating a prose
cross-reference to the new function name. Since the dropdown's promise is "these
genres can pass the filter", a threshold change would have silently offered
genres the filter then rejects. Both now project from one
`anime_genre_majority_relation` — verified byte-identical buffers at 0/1/2/3
genres, so it's purely a refactor.

### Guard tests were verified to fail

Two invariants got tests, and both tests were watched going **red** against an
injected fault rather than assumed to work:

- coalescing the pre-aggregated `min_stable` moves a media-less anime from
  `long_cycle` to `stabilizing` — caught.
- editing `ix_jobs_scrape_query`'s expression so it stops matching
  `JobDAO.scrape_query_expr()` — caught, by asking Postgres (`EXPLAIN` with
  `enable_seqscan=off`) whether the index is still usable rather than comparing
  SQL strings. String comparison would have needed the very normalization under
  test. Note the index is **partial** on `kind='user_scrape'`, so the test query
  must constrain `kind` or the planner can't use it regardless.

### Skipped, deliberately

- **Collapsing `_SweepAtoms`** — it keeps `_tier_bucket` grain-agnostic, and the
  media grain needs a 6-field struct either way.
- **Adopting `pickKey` in `adminJobsFilter`** — needs its `fallback` widened to
  `T | ''` for the no-filter sentinel; churn on shipped code for no behaviour
  change.
- **Restructuring the filter-lifecycle tests** — duplicated coverage between the
  routing and store describes, but they're passing tests from an earlier commit
  and the coverage isn't wrong.

### Follow-ups this raised

- **CI builds its test schema from `create_all`, not the migration chain.**
  `alembic check` runs against a throwaway `migrationcheck` DB for that reason.
  The deeper fix — build `testdb` with `alembic upgrade head` and delete the
  `create_all` block, the extension `CREATE`s and the `alembic stamp head` hack —
  would also make the whole suite run against a migration-built schema. Deferred
  deliberately: it's a CI-wide semantic change (a broken migration would fail the
  entire suite) and deserves its own commit and green run.
- **`/filters/options` could go 11 → 8 round trips** with a `MediaDAO.filter_bounds()`
  selecting all four min/max pairs in one statement, at which point
  `get_min_max`'s string-keyed reflection guard could go too.
- **The anime genre filter still nested-loops back into `media`** because Postgres
  underestimates `genre.name IN (...)` selectivity ~7× (10,407 of its 11,330
  buffers are that probe, just to fetch `anime_id`). With `enable_nestloop=off`
  the same query is 2,020 buffers. Two rewrites were tried and neither moved the
  plan; the lever is getting `anime_id` onto the genre rows.

## Block E — frontend fetch behaviour

### F1 — the guard was costing a request per hover, not per page

`GET /auth/validate` sat inside the root `LayoutLoad`. The load reads
`url.pathname`, which kit lists in `tracked_url_properties`, so **any** URL change
invalidated it — `?tab=ratings` → `?tab=stats` included — and
`data-sveltekit-preload-data="hover"` runs universal loads on hover, so moving the
cursor across a nav bar fired several.

Replaced with a local `exp` decode. Local costs nothing in authority: the JWT is
signed, so `exp` can't be forged, and every API call the page then makes still
rejects a bad token. The worst case admitted is a still-unexpired token for a
since-deleted user, whose first real request 401s.

The reusable piece turned out to be the **number, not the boolean**. A first cut
exported `isSessionLive(exp, now)`, but `evaluateSession` still computed
`exp * 1000 - now` itself — so the "single expiry rule" was half-shared, and the
leftover arithmetic forced an `(exp as number)` cast. `sessionRemainingMs` is the
right primitive; `isSessionLive` is one line on top of it and the cast disappears.
Worth remembering as a smell: **a cast next to a freshly extracted guard usually
means the extraction stopped one level too high.**

### F2/F3 — two session caches, and the invalidation is the load-bearing half

`/filters/options` is 8–15 backend round trips for data that changes only with the
catalogue, refetched on every `SearchBar` mount — and it mounts on both `/` and
`/search`. `/ratings/scores` is the heaviest response in the app and had three
independent consumers.

Coalescing would not have fixed F3: the visits are sequential, not concurrent. So
it had to be a real cache, and a real cache **trades away the one safety a
per-mount fetch has for free** — it can serve stale data. Buying that back is
five explicit `invalidateRatingScores()` calls at the rating-write sites, matching
the existing `refreshWatchlist` / `refreshTags` convention. The reviewer
explicitly argued against centralizing them in `api.ts` keyed on path: that layer
is deliberately dumb (it has no global 401 handler for the same reason), and
implicit cache behaviour there would be invisible at the call site.

**A shared cache factory was considered and rejected.** The genuinely common body
is ~8 lines; a generic `createRequestCache<K,T>` is ~14 on its own, and
`genres.ts` can't join it — it populates a writable, returns `Promise<void>`, and
*swallows* failures because tooltips are progressive enhancement. Folding it in
would mean options for store-vs-promise and rethrow-vs-swallow, which is where a
factory starts costing more than it saves. Revisit at a third keyed, rethrowing
cache.

### F4 — the "redundant" fetch wasn't redundant

The baseline listed `refreshTags()` on every `/watchlist` mount as duplicate work,
since login already populates the store. It isn't quite: `Tag.entry_count` /
`anime_count` are server-side counts that go stale as entries are added and
removed.

But their **only** consumer is `WatchlistTagsTab`, which mounts on demand. So the
call moved there rather than being deleted — `/watchlist` drops the request while
the counts stay correct. Reading the doc's finding literally would have shipped
stale badge counts.

### The cache broke a test in a way worth keeping

`searchbar.test.ts`'s "fetches filter options on mount" started failing: an
earlier mount in the same file warmed the cache, so the assertion saw zero
fetches. The fix was two-part, and only the first part is mechanical — reset the
cache per test for isolation, then **rename the assertion** to "on first mount of
a view", because the old name describes a guarantee that no longer holds. A
companion test now pins that a remount does *not* refetch, which is the actual
reason the cache exists.

## Block F — the jobs-log payload

Picked up from the debt list in
[2026-08-12-frontend-docs-restructure.md](2026-08-12-frontend-docs-restructure.md),
which found it and deliberately left it. Two independent halves; both landed.

### The two halves are not the same fix, and only one is a wire change

The doc had already separated them, and that separation held up: gating the poll
is frontend-only and removes the whole cost *for a parked admin*; projecting the
payload is a backend change and is the only thing that helps an admin actually
watching the Jobs Log. Doing either alone leaves half the cost.

### The eager-mount comment was right, so the gate went on the timer, not the fetch

`/admin` mounts every tab and argues for it in a comment: the first-paint fetch
cost buys instant tab switches for the rest of the session. The tempting fix —
gate the whole component on visibility — fights that, and would make the Jobs Log
the one tab that shows a skeleton on open.

The distinction that resolves it: a **one-off** fetch is what the eager-mount
trade buys, a **repeating** one isn't, because it costs the whole session rather
than one paint. So the initial and filter-driven loads stay ungated and only the
intervals stop. That framing is now what the comment on `/admin/+page.svelte`
says, so the next tab added there gets the rule rather than the anecdote.

### Coming back to a stopped poll needs an explicit catch-up fetch

Stopping the interval while hidden means the list is as stale as the detour was
long, and restarting the interval alone shows that stale list for up to another
30s. So the effect fetches once on hidden→visible.

The subtlety is that the same effect also re-runs when `hasRunning` flips (that's
how the 3s/30s cadence swaps), and it runs on mount — so an unconditional
catch-up fetch double-fires against the filter effect's initial load. A plain
`let pollWasStopped` (deliberately **not** `$state`) gates it: it only ever reads
inside an effect that already re-runs on `visible`, and making it reactive would
re-trigger that effect on its own write.

### The projection does not save the database read — only everything after it

Worth stating because the obvious phrasing ("the heavy arrays never leave
Postgres") is wrong, and it was in the first draft of every comment on this.
`jsonb - text[]` resolves to `jsonb_delete_array`, which needs a fully
materialised value: there is no partial detoast for jsonb the way there is for
text. So every listed `update_sweep` row still pays the full TOAST read and
decompression, plus an allocation to build the trimmed copy. Postgres-side cost
goes marginally **up**.

What the change actually removes is everything past the socket — the driver's
JSON parse, the validate/dump/rebuild walk per row in `admin_service`,
re-serialisation, gzip, wire bytes — and that is both the larger half and the
half that repeats on a 3s poll. The fix is worth having; the claim just has to
be the true one. Removing the DB-side read too means not storing the arrays on
the listed row at all (a sidecar), which is not worth it until profiling says so.

### `set_committed_value` is what keeps the projection from leaking upward

The list needed a *different* `result_summary` than the detail endpoint, without
`AdminJobResponse` splitting in two (its docstring defends being shared, so the
frontend can route from a row into the detail view) and without
`_job_to_admin_response` growing the field list its docstring says it doesn't
have.

`sqlalchemy.orm.attributes.set_committed_value` does it: the DAO defers the real
column, selects `result_summary - text[]` alongside the entity, and writes the
projected value onto the instance **as if it had been loaded**. The service and
schema layers are untouched. Plain assignment would have marked the instance
dirty, which is the version of this that eventually persists a truncated summary.

`defer(..., raiseload=True)` is the guard on the other side — a future path that
selects the entity without populating the projection faults loudly instead of
quietly emitting one lazy load per row.

**The trick has a real cost, and a test found it rather than a reviewer.** An
entity carrying a value the database doesn't have is a liar inside its session:
once the list query has run, that row sits in the identity map with a *projected*
summary, and the next read of it gets the truncated version. Merging the list and
detail assertions onto one seeded row (below) turned that from a hypothetical into
a failing test immediately. The fix is `populate_existing=True` on the detail
query — it is the endpoint that must be authoritative about the whole summary, so
it refuses the identity map's copy. Production sessions are per-request and would
not have hit this, which is exactly why it would have survived to become a real
bug the first time anything else read a job in that session.

### Denylist, not allowlist — because of which failure mode you get

An allowlist of the keys the list reads is more future-proof: a new heavy key
stays out automatically. It was rejected because it has to enumerate every kind's
small keys (`retryable`, `anime_count`, `filename`, `restored_from`, …) and a
forgotten entry **blanks a Jobs Log cell**. The denylist's failure is that a
future heavy key re-inflates a payload — worse in theory, far more visible, and
it can't render wrong data. The bump rules in `job_versions.py` now name the
constant, so the decision surfaces where a new key gets versioned.

### The compat claim in the debt note was too conservative

The note said the response-shape change forces backend and frontend to the same
tag. Strictly it does, by the repo's own rule — keys are removed, not added. But
a stale frontend against a new backend degrades to *nothing*: `jobSummary.ts`
reads only scalars, and the detail page fetches `/admin/jobs/{uuid}`, which still
returns the summary whole. Ship them together anyway; just don't treat a mixed
pair as an outage.

### What the tests actually pin

The list and detail assertions are **one test over one seeded row**, not a pair
of tests over two. Either assertion alone passes vacuously — an empty summary
satisfies "key not present" — and, as above, the shared row is what exposed the
identity-map bug. Splitting them for tidiness would have hidden it. Two more
tests cover what the `jsonb - text[]` shape makes non-obvious: a `backup` row
must come back whole even though the denylist is applied to every kind, and a
queued row with `NULL` summary must not error, since `NULL - text[]` is `NULL`.

The frontend gate was verified by breaking it — short-circuiting the `visible`
check turned 3 of the new tests red. Worth doing whenever a test asserts a
*negative* ("no fetch fired"), which passes for many reasons other than the one
intended.

### Gating a poll on visibility can cost more than not gating it

The catch-up fetch on re-show is the trap. Fired on every hidden→visible
transition, an admin flicking jobs → tokens → jobs → backups → jobs issues a
full `/admin/jobs` request per return, where the ungated 30s interval would have
issued one. So it is gated on *elapsed time* rather than on the transition: the
fetch exists to make up for missed ticks, and when none were missed there is
nothing to make up. The test for it asserts a negative, so it was written from
the failure direction first.

One axis is still open, and the comment says so rather than implying the problem
is solved: `visible` tracks the **admin** tab, not the browser tab. Parked on
Jobs Log in a backgrounded window this still polls — browsers throttle hidden-tab
intervals, they don't stop them. Closing it wants a shared document-visibility
primitive, and should take `JobBell` with it (2s/30s, ungated, mounted on every
page), which is the larger consumer.

## Block G — making backend.md describe the code

Not an efficiency change; it rides along because the branch had already found
that several of `backend.md`'s documented exceptions describe drift rather than
design. A rule that misdescribes the code is worse than no rule, because it is
read mid-edit and believed.

### The exceptions were four different things wearing one label

Sorting them was most of the work, and the sort is the reusable part:

- **A model exception.** The `asyncio.gather` carve-out permits gathering
  pure-CPU coroutines — and the one place entitled to use it declines in writing
  with a rationale. Nothing to do.
- **A self-contradiction.** The layering exception named `routers/jobs.py` as a
  thin read endpoint, and the very next sentence forbade what that file does:
  two quotas, a dedupe window, a MAL-id heuristic, and the write plus the worker
  wake-up. Fixed in the *code* — extracted `job_submission_service` — so the
  exception shrinks to the one honest case.
- **A drifted inventory around correct decisions.** The Roles section said
  "Three writes" and named four, missed the cron chain entirely, and its closing
  claim about gated reads was falsified by one endpoint. Each individual gate was
  defensible; the description had rotted around them.
- **An enumeration that had stopped enumerating.** The services-run-SQL
  exception named three categories covering well under half the sites. That is
  the one that actually costs a reader: they cannot answer "is my case inside
  it?", which is the only question the exception exists to answer.

### Describe an exception by its property, never by listing its members

The rewrite drops the three categories for a test — new SQL goes in a DAO,
assume you are outside the exception, and the cases that stay argue for
themselves at the call site. This is `workflow.md`'s "don't write counts that go
stale" applied to a set rather than a number: a list of members is a count in
prose, and it decays the same way with nothing to catch it.

The corollary is that the 62 remaining sites were deliberately **not** cleaned
up. Roughly 27 should stay regardless, ~20 interleave flush/expire/cascade
reasoning that would change transaction boundaries, and the ~15 mechanical ones
need DAOs that do not exist. Describing the set honestly costs nothing and helps
immediately; migrating it is its own branch and helps nobody today.

### Fixing the rule surfaced a real convention nobody had written down

`admin_split.py` commits in a router, which the rewritten layering rule appeared
to forbid. It turned out not to be drift: seeders deliberately do not commit, so
their caller owns the transaction — the same contract `create_default_tag`
documents for itself. So the rule gained the convention rather than the code
gaining a service. Worth the check every time: a rule that a piece of code
violates is sometimes the rule being wrong.

### Auditing the rewrite against the code caught the same class of error again

The rewrite was itself verified endpoint-by-endpoint, and three claims failed:

- `/auth/refresh` was listed among ungated **writes**, but it takes no `db` at
  all — contradicted by a definition three paragraphs earlier in the same file
  that the rewrite had *just added*.
- The cron-chain warning named the milder failure. Because that module binds auth
  per-route and neither it nor its parent carries a router-level dependency, a
  new endpoint there is not bearer-protected as claimed — it is unauthenticated.
- The layering rule's absolute had one live counterexample (above).

The lesson is not "check your work". It is that prose describing code cannot be
reviewed by reading the prose: every claim needs the grep that would falsify it,
because a confident sentence about code reads exactly the same whether or not it
is true. The first version of this rule was written that way, which is how it
drifted in the first place.

## Block H — a prose review step, because the correcting was recurring

Prompted by an observation from outside the diff: nearly every `/ship` run was
producing prose that had to be hand-corrected for duplication or verbosity. The
rules already forbade both. Nothing ran them.

### The rule existing is not the same as the rule being applied

`docs.md` has "No fact appears in two rows" and names the explain-then-point
shape outright; `workflow.md` bans counts that decay and even prescribes the
grep. Every failure being corrected by hand was already illegal. So the gap was
never wording — it was that a rule read mid-edit relies on the author noticing,
and duplication is exactly what an author cannot notice, because finding it means
searching every other doc for the fact you just wrote.

That is the argument for an agent rather than a checklist line: it is a fan-out
search problem, and a checklist item saying "check for duplication" is the same
advisory prose that already failed.

### Where it goes is decided by docstrings, not by .md files

The first instinct was `/update-docs`, which owns doc placement. Wrong: it owns
`.md` targets only, and a large share of the verbosity lands in docstrings and
code comments written during implementation, which it never sees. `/simplify`
would be the natural host — it already reviews prose — but it is a Claude Code
built-in with no file in this repo to extend. That leaves a step in `/ship`,
scoped to the whole diff's prose.

### The rubric lives in the agent, so it cannot be paraphrased

Written as two `.claude/agents/*.md` definitions rather than instructions inside
the skill. The reason is drift, which is the same failure the gate exists to
prevent: a rubric restated into an agent prompt each run gets restated slightly
differently, and the parts that go first are the nuanced ones. Here those are the
two calibrations that took an experiment to find — **length is not a defect**
(comments here are dense on purpose, and a reviewer that trims load-bearing *why*
makes the correcting worse, not better) and **`compound-docs/` is frozen**, so
past tense and running commentary are correct there and must never be flagged.

Split into ownership (needs cross-file search) and decay (local to the diff),
because one agent doing both does the cheap local half well and the expensive
search half badly.

### The rubric files do not register as agent types, and nothing says so

Found by dogfooding — pointing the new step at its own introduction returned
**"Agent type 'docs-ownership-reviewer' not found"**. A fresh headless session
confirms it: only the built-in agent types resolve, and nothing under
`.claude/agents/` appears. The six ISO reviewer files that were already sitting
there are inert too, so `/pr`'s panel names six agents that do not exist.

This is the failure `authoring-rules.md` predicts for rules — *"it would match
nothing, load never, and report neither"* — and it turns out to apply to agent
definitions as well, with the extra sting that a rule failing silently just
returns nothing while this fails loudly at the worst moment, mid-pipeline.

So the step **reads** the rubric into a general search agent rather than naming
it. That keeps the anti-drift property (the rubric is still a pinned file, not a
paraphrase) and does not depend on registration working. The check is one
command, and it belongs in the skill next to the instruction:

```
claude -p --model haiku "List ONLY the subagent_type values available to the Agent tool" < /dev/null
```

**The general lesson is the one this branch keeps re-learning**: a config file
that looks correct proves nothing about whether anything loads it. Rules got a
load test for this reason; agent definitions needed the same and did not have
one. Write the falsifying check before trusting the file.

### Calibrated on real work before being made a step

Run against the branch's own rules rewrite, they found the same rationale written
into three files, an enumeration duplicated across two homes, an
explain-then-point, and — the strongest kind of finding — a member-list that was
**already incomplete at merge time**. They cleared the dense comments and ignored
the compound doc's past tense, which is what made the calibration credible enough
to keep.

The gap they do not cover: rules drifting from the code they describe. That needs
a reviewer that reads the code behind each claim, and it is worth adding once
these have some mileage.

### Then they were run on their own introduction, and it was not a formality

The dogfood pass found six stale-prone counts and five duplications in the commit
that introduces them — including two that prove their own rule. The decay reviewer
caught `/ship`'s step number cited from three files *outside* the skill, in a diff
that had just renumbered four references *inside* it. The ownership reviewer caught
`workflow.md`'s durable-characteristic example transcribed into a rubric with half
the example dropped: a copy that had **already drifted on arrival**, which is the
strongest evidence the no-restatement rule could ask for.

Both cleared the dense calibration sections deliberately and reported the compound
doc's past tense as correct, which is what made the findings credible rather than
noise. A reviewer that flags everything teaches you to ignore it.

What neither could decide, and both surfaced instead: **`.claude/skills/` and
`.claude/agents/` appear in no row of `docs.md`'s placement table.** That absence
is why the "these files do not register" fact scattered into four homes before
anyone noticed — there was no rule saying where it goes. `docs.md` asks for
exactly that to be raised rather than settled alone.

### The missing home was an existing rule's glob, not a missing category

Adding table rows for skills and agents was the obvious move and the wrong one:
that table answers *where a fact lives*, and these are executable config, not
fact-homes. The actual owner already existed. `authoring-rules.md` holds the
lesson verbatim for rules — a file that looks right, loads never, and reports
neither — and the agent-registration failure is the same lesson for a sibling
artifact, with the twist that it fails loudly mid-pipeline instead of silently.

Its `paths:` was `".claude/rules/**/*.md"`, so it did not load when anyone edited
`.claude/agents/`. That is precisely the symptom `docs.md` predicts — *"a rule
that keeps getting violated — often its `paths:` glob is too narrow to load when
it's needed, so the structure is self-diagnosing"* — and the structure did
diagnose it, one layer later than would have been ideal. Widening the glob is
what makes a single home actually reach the person about to break it.

Skills needed nothing: `workflow.md` already says the skill owns its steps.

### Testing a `paths:` widening has a trap of its own

Both arms of the load test lied once before telling the truth, in opposite
directions.

The first pass asked a question the model could answer *without* the rule — it
reasoned from the agent list already in its own context — so a correct answer
proved nothing. `authoring-rules.md` warns about exactly this ("pick a fact that
appears in **no** other loaded doc") and it is easy to violate, because a fact
worth writing down is usually a fact that can be inferred.

The second pass then returned a false **absent**: the prompt said "do not read
anything under `.claude/rules/`", and the model honoured that as a gag order on
knowledge it already had rather than as a scoping instruction. A prohibition in
the test prompt fakes the failure the test is looking for. Ask for "guidance
already in your context" instead of forbidding a directory.

The rule's own instruction — repeat any absent answer before believing it —
carried both arms to a verdict: absent twice with nothing matching, and the exact
command reproduced after reading one rubric.
