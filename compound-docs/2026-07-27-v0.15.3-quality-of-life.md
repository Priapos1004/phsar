# v0.15.3 — quality-of-life upgrades & little fixes

## Summary
Eight items, four of them bugs earlier releases left behind. Jobs Log: `upcoming_sweep`
rows rendered a blank Detail cell, backup rows didn't show the dump size, and the kind
label was overlong. Ratings statistics gained **season** and **age-rating** breakdowns
(subtab renamed Categories) with click-through to the filtered grid, and the cumulative
watch-time chart now reads its own window. The sweep's long tail gained a per-row
180-day window for media over a decade old. Backups record the Alembic revision they
carry, and a restart with nothing restorable takes a dump immediately. Anime search
stopped letting a filter rescope the score it ranks by. No migration — every new field
is Pydantic-only or lives in the existing per-dump JSON sidecar.

A six-perspective review at PR time found three defects in the *new* backup work
(below) and two tests that passed for the wrong reason. Worth stating plainly: the
feature was fine in the happy path and wrong in every degraded one.

## Key decisions (rationale not obvious from the code or docs)
- **The archival sweep cadence is a per-row WINDOW on one atom, not a fifth tier.**
  `due_long_tail` compares `last_checked` against a `CASE` interval (180 days once
  `aired_from` is past the archival cutoff, else 90). A fifth OR-branch was written first
  and rejected: `due_long_tail` is unconditional, so anything stale 180 days is already
  stale 90 — the new branch is dead code unless tier 4 is narrowed by `not_(archival)`,
  and that narrowing is a coupling nobody will remember. The window form also makes NULL
  correct *for free* (an undated media fails the `WHEN`, lands on the 90-day `ELSE`),
  which deleted a guard, its comment, and the reasoning behind both.
- **`integrity` stays a pure file-corruption verdict; the composite is a separate field.**
  `apply_retention` pins the most-recent-`ok` dump as its archival anchor, so folding a
  schema verdict into `integrity` would leave retention anchorless *immediately after
  every migration* — exactly when the install is most exposed.
- **`unknown` is deliberately not `ok`.** A dump with no recorded revision might restore
  cleanly, but nothing on disk says so. This is also what makes the card and the
  self-heal agree.
- **The self-heal does nothing when the live revision is unreadable.** `status` is a
  comparison against that value, so `None` makes the predicate *unsatisfiable* — no dump
  can clear it, including one taken right now. "Nothing looks restorable" and "we can't
  tell" need opposite responses, and only the first justifies a dump.
- **Convergence lives in the dedupe path.** A dedupe hit stamps the revision it parsed
  onto the matched sidecar. Byte-identical content means it applies verbatim, and this is
  the only path that can stamp an existing dump.
- **The restore endpoint stays ungated; the dialog carries the warning.** Rolling the
  schema back is a legitimate admin choice, so the guard is informational — but it has to
  be *in the modal*, because the modal covers the row badge.
- **`resetKey` belongs on `EChart`, not `{#key}` in the consumer.** The behaviour being
  overridden (`setOption(…, notMerge)`) is the wrapper's decision, and a consumer remount
  additionally re-pays `echarts.init` and blanks the plot for the initial-measurement tick.
- **Season/age labels drill into your own ratings; studio labels leave for search.** Not an
  inconsistency — they answer opposite questions ("what did I rate in Fall 2025" vs "what
  else did this studio make"). Genre stays inert because it has no second question.
- **Categorical bucket keys are the raw filter value (`"17"`, not `"R-17+"`).** The
  click-through writes the key straight into `ratingsFilter`; a display-label→filter-value
  reverse lookup breaks silently the first time a label is reworded.
- **The backup self-heal runs FIRST among the post-yield passes, in its own try/except.**
  First because all of them are idempotent derived-data repairs, so a dump taken before
  them loses nothing recoverable. Isolated because it is the only one that touches the
  filesystem and shells out — the least critical pass must not gate the most critical ones.
- **`JOBS_SWEEP_MAX_PER_RUN` stays at 500.** Prod is over-subscribed (~652 due/night at
  the time of writing) but `ORDER BY last_checked_at ASC` self-balances: a media that
  misses a night is staler the next and outranks whatever was refreshed.
- **An anime-view filter selects WHICH ANIME, never which media the aggregates average.**
  `apply_anime_pre_filters` emits `Anime.id IN (SELECT media.anime_id WHERE …)` instead of a
  WHERE on the grouped rows, because those rows also feed `avg_score`/`avg_scored_by`/
  `total_episodes`/`media_count` and every HAVING filter. One subquery, so the conditions
  still have to hold for the same media row.

## Failed approaches (all of these were built before being reverted)
- **The animation bug got the wrong diagnosis first, and the fix exposed a second bug.**
  I blamed ECharts index-diffing between datasets; the correct cause was `resize()`
  finishing in-flight animations, fired by the `ResizeObserver` *after* the option
  `$effect` because the chart's height tracks its row count. Fixing that then made the
  `notMerge` **exit** tween visible — old bars animating away over the new ones. Two
  mechanisms, two layers. **Learning: an intermittent animation is usually cancellation,
  not a wrong tween — and removing a mask reveals whatever it was masking.**
- **Keying the remount on all three controls.** Over-generalized from "dim swap" to
  "any control change", which forced a restart-from-zero on re-sorts where an in-place
  tween is the better affordance. Scoped back to `dim`.
- **A frontend-composed restorability verdict.** `dumpStatus` returned `'ok'` for
  `schema_current === null` while the self-heal treated the same row as unrestorable.
  **Learning: when two consumers answer the same question, the answer is a field, not a
  helper each of them calls.**
- **`_set_meta_field` for the dedupe-path revision stamp.** It acquires the module write
  lock, and `_finalize_partial_dump`'s callers already hold it — `asyncio.Lock` is not
  reentrant, so this deadlocks the backup job outright. The replacement re-reads the RAW
  sidecar for a second reason: the caller's metadata came from `list_backups` and carries
  derived fields (`status`, `schema_current`, `is_current`) that must never be persisted.
  **Learning: check lock ownership before reusing a "shared" write helper from inside
  another write path.**
- **`EXISTS(aged) AND NOT EXISTS(newer)` for the anime-grain archival roll-up.** Correct,
  but the planner hashed both subplans over all of `media`: **+68% on the Overview card's
  query** (14.9 → 25.1 ms, +737 buffers). A correlated `MAX(aired_from) < cutoff` is
  provably identical on every shape and costs +1.5 ms. **Learning: `MAX` ignoring NULLs is
  what makes the ∀ roll-up NULL-safe without a guard.**
- **A `title` prop on `TagBarLabel` that no caller ever passed** — added for a case the
  formatter already handled before the prop was reached.
- **A DOM-driven test for the "By restorability" sort.** The shadcn Select can't be driven
  in jsdom. Extracting the comparator to a util and testing it directly is better anyway.
- **A test assertion that was simply wrong**: `paddedAxisMin({min: 5, max: 5}) === 0`. The
  pad is 0.01, so it returns 4.99. Written from the docstring rather than the arithmetic.
- **A correlated `EXISTS` over an aliased `Media` for the anime-filter rewrite.** Worked, but
  the alias forced an entity parameter through two shared helpers. SQLAlchemy never
  auto-correlates a subquery's *only* FROM, so a plain uncorrelated `IN` needs no alias:
  same plan, ~20 fewer lines.

## Gotchas & learnings
- **A fail-soft read turns a degraded value into a decision input.** `read_db_revision`
  returning `None` was designed to keep the listing working; it also silently made the
  self-heal's predicate unsatisfiable, so an install with an unreadable revision would
  `pg_dump` on **every restart** and evict real archival history through the 14-recent
  window — worst during a crash loop, i.e. when history matters most. The same fail-soft
  read had already localized a config gap into whatever finally asserted on it (see the CI
  note below). **Failing soft is right for a read and dangerous for a predicate; the
  branch that consumes it has to distinguish "false" from "unknown" itself.**
- **Two tests can pin a bug rather than the fix.** A `makeBackup` factory defaulting
  `status: 'ok'` plus an override of only `schema_current: null` produced a pair the server
  cannot emit, and one test asserted the reverted green-`ok`-for-a-revisionless-dump
  behaviour by name. Reintroducing the reverted bug would have kept the suite green.
  **A fixture that isn't a reachable server state proves nothing — check the factory's
  defaults, not just the overrides.**
- **An extraction makes a branch testable without making an omission detectable.** Moving
  `payloadSummary` out of the component produced 16 tests and still shipped a second
  instance of the same bug it was extracted for: the `restore` branch reads
  `result_summary.filename`, but the backend writes `restored_from`, so every restore row's
  Detail cell was blank. The new test invented a `filename` key to match. **When you write
  a fixture for a shape you didn't read from the producer, you are testing your assumption.**
- **SQL `NOT NULL` is `NULL`.** Negating a nullable comparison to narrow a branch drops the
  NULL rows out of *both* branches — here, undated media never refreshed again: silent,
  permanent, invisible to any test that didn't seed a NULL. The fix removed the negation.
- **`_seed_anime` defaults `aired_from=None`**, so a new "undated media" test was
  byte-identical to the existing long-tail test. The existing test now pins a *dated* row.
- **`cumulativeWatchTime` filtered by cutoff *after* accumulating**, so clipping the x-axis
  also clipped the visible history's start. A window containing no ratings drew nothing at
  all — and with `1m` as the default range, that was anyone who hadn't rated in a month.
- **Tests never boot the lifespan** (`tests/routers/conftest.py` uses `ASGITransport`
  without a `LifespanManager`), so the startup self-heal adds no `pg_dump` to the suite —
  and no test would have caught it aborting its sibling backfills either.
- **CI's test DB has no `alembic_version` table.** `backend-test.yml` builds the schema with
  `Base.metadata.create_all`, and that table is Alembic's own bookkeeping — not in the ORM
  metadata, so it is the one thing `create_all` and `upgrade head` disagree about. Fixed
  with `alembic stamp head`, not `upgrade head`, since the schema is already at head.
  **Learning: fail-soft reads localize a config gap into whatever finally asserts on the
  degraded value — the error surfaced three commits after the cause.**
- **Monkeypatched stubs encode the return shape.** Widening `_compute_content_hash` to
  `(hash, revision)` touched six stubs across one file; changing the self-heal to read the
  envelope then moved the stub target again.
- **`_rebuild_meta` uses the cheap TOC check, not the hash pass**, so it cannot recover the
  revision — an orphan-rebuilt sidecar reads `unknown` until its content is re-confirmed
  through the dedupe path.
- **Svelte 5 warns on `let x = someProp`** (non-reactive capture) even when a snapshot is
  what you want. A `Symbol` sentinel expresses "no value applied yet" without the warning.
- **A kind-keyed if-ladder whose miss is a blank cell shipped the same bug twice** in one
  release (`upcoming_sweep`, then `restore`). The module already had the right precedent two
  doors down — `JOB_SUCCESS_HREF` is a `Partial<Record<JobKind, …>>` whose own docstring says it
  is a table "rather than an if-ladder in JobBell". `payloadSummary` is now a
  `Record<JobKind, (row) => string>`, so an unhandled kind is a compile error. **A ladder over a
  closed union is a table that hasn't been written yet; the giveaway is a `return ''` fallback.**
- **A guard keyed on the value instead of the event rescans on rejection.** The revision parse
  short-circuits once the `COPY public.alembic_version` block has been *seen* — keying it on
  `revision is None` would have looked correct and quietly rescanned the whole ~20k-line stream
  whenever `_REVISION_PATTERN` rejected the value, i.e. exactly the malformed case.
- **A prop typed `unknown` can't express "primitive only".** `resetKey` compares by
  reference, so `resetKey={[dim, sort]}` — the natural way to write a composite key —
  `clear()`s on every option update and restarts every animation from zero. No type error,
  no test signal, symptom visible only in a browser. Now typed to primitives.
- **Snapshot statistics rot in comments.** "The long cycle is ~73% of the catalog" was
  true the day it was measured. Restated structurally: it's the *terminal* bucket every
  media drains into and never leaves, so it's the only tier whose cost grows without bound.
- **A twin-parity test proves nothing about the row set the twins run over.** v0.14.14 pinned
  the Python display aggregate equal to the SQL ranking aggregate, and both were still correct
  here — what diverged was their *input*: a WHERE on a grouped query does double duty (which
  rows match AND what the aggregate averages), so narrowing it re-broke the invariant the
  parity test exists to protect. Caught by a **filter** test.
- **Checking an ordering invariant against the API response measures the rounding.**
  `avg_score` is 2dp and `avg_scored_by` an integer, so recomputing `S_w·log10(V_w+1)` from the
  response reported 6 violations on prod data — all ≤0.026. Compare against the unrounded SQL.
- **Restore a prod dump into a SEPARATE scratch DB to validate a prod-shaped bug.** The dev
  catalog (279 anime) understated this one; the reported case only exists at prod scale
  (1095 anime / 4356 media). Two pitfalls: the host's pg15 `pg_restore` cannot read a pg17
  archive (`unsupported version (1.16) in file header`) — run the container image's tools
  instead; and a dump from a newer pg emits `SET transaction_timeout`, which pg17 reports as
  one ignored error and otherwise restores fine. Never restore over `anime_db`.
- **Two pytest runs against the same dev DB and backup dir invent failures.** Four
  backup-dedupe tests failed under concurrency and passed in a clean single run. Confirm a
  "pre-existing failure" by stashing the change, not by re-running beside another suite.
- **A `# Deferred import to avoid circular dependency` comment was folklore.** Probed all four
  import orders: `from app.models.anime import Anime` at module top level imports cleanly.

## Follow-ups (measured, not applied)
- **`count_by_sweep_tier_priority` evaluates its correlated `MIN` once per stabilizing
  branch.** `stabilizing_cases` emits one `WHEN` per check level and, at the anime grain,
  the compared expression *is* the scalar subquery — so the compiled SQL contains it three
  times and Postgres plans three SubPlans with no cross-node caching. Measured on the dev
  catalog: **6,592 buffers as shipped; 13,247 in the settled shape** (once media graduate
  past the stabilize threshold, every non-airing anime evaluates all three branches);
  **256 buffers / ~1.1 ms** for a pre-aggregated `GROUP BY media.anime_id` CTE joined once,
  verified to return identical counts in all six buckets. That shape is what the media-grain
  sibling already uses. Note the docstring's "dynamic in the threshold" claim also multiplies
  the subquery executions — raising 3 → 6 doubles the card's cost. This supersedes the
  earlier open item, which mis-attributed the cost to the new archival `MAX` (402 buffers,
  ~3%) and to the two `EXISTS` atoms (hashed, evaluated once).
- **`ix_media_freshness_last_checked_at` and its `anime_freshness` twin have 0 lifetime
  index scans** and are worse than inert: `last_checked_at` is the only indexed *mutable*
  column on either sidecar, so indexing it makes every sweep write a non-HOT update
  (`n_tup_hot_upd = 0` across ~5.1k lifetime updates). The planner can't use them — the
  staleness predicate is a `coalesce` across a joined table (not sargable) and the `ORDER BY`
  sits on the nullable side of a LEFT JOIN, so the qualifying set is materialized and
  top-N heapsorted before the `LIMIT` regardless. Dropping both needs a migration and a
  prod-snapshot plan check first. The CLAUDE.md "Backed by" claim is corrected.
- **Drop the 384-dim vector out of the title-search `GROUP BY` key.** `search_anime_aggregated`
  groups by `(anime.id, anime_search.title_embedding)`, so a 384-float value is part of the
  hash/sort key for every input row. Grouping by `anime.id` and ordering by `MIN(distance)` is
  equivalent (`AnimeSearch` is 1:1 with `Anime`) and measured **23.6 → 7.9 ms** on the prod
  snapshot at identical result order. Needs `apply_vector_ordering` to aggregate only the
  distance, not the literal/fuzzy bonus terms. Biggest win available on the search path.
- **Ordering tiebreaks are missing at four sibling sites**: the anime weighted score and anime
  description distance (same function), `media_dao`'s unscored tail, and `rating_dao`'s
  `modified_at.desc()` (one bulk rating writes N rows with identical timestamps).
  `apply_vector_ordering` currently accepts no tiebreak.
- **The anime aggregates could be made unreachable by any WHERE.** They are inlined into the
  filtered query, so "a filter must not narrow the grouped rows" is held by a docstring plus one
  test. Computing them in a derived table keyed on `anime_id` and joining it — the shape
  `anime_dao`'s `per_anime_score` CTE and `filter_service.anime_agg` already use — makes the
  class of bug unrepresentable and collapses the `apply_anime_having_filters` / `for_anime=True`
  split, where today picking the wrong one silently swaps any-media for card-derived semantics.
- **Anime-view HAVING range filters changed meaning** as a side effect of item 7:
  `episodes_*` / `total_watch_time_*` now aggregate over the anime's full media set even under
  a WHERE filter. This is the correct card-consistent semantics, but only the genre-majority
  denominator case is pinned by a test; the episodes/watch-time siblings are uncovered.
- **`_compute_content_hash` no longer matches its name or its job** (it returns a tuple and
  extracts schema metadata). `_scan_dump(path) -> DumpScan` would stop the next extraction
  widening a tuple that six test stubs hand-roll.
- **`SweepTiersCard`'s key union re-lists `AdminSweepTierBreakdown`'s keys.** Deriving it
  would make a bucket missing from `ROWS` a type error instead of a silent sum-invariant break.
- **`rowTintClass`'s three positional numbers.** `rowTintClass(hentai, unknownTags, probeMedia)`
  has no compiler protection against a transposition. (`payloadSummary`'s if-ladder was the
  sibling item and is now a `Record<JobKind, …>` dispatch table — see the learning below.)
- **The dump status → user-facing copy mapping is written twice** in `BackupsCard.svelte`: once
  as the badge tooltip, once as the restore-dialog `Notice`, with the same two facts reworded.
  The idiomatic fix here is `jobBadges.ts`'s shape — a `Record<BackupStatus, …>` in
  `backupStatus.ts`, which already owns this verdict's presentation. Deliberately not applied:
  the `outdated` copy interpolates two `<code>` elements, so a shared string table would either
  drop the markup or need `{@html}`. Both ladders also use `{:else}` for `unknown`, so a verdict
  a newer server adds silently renders `unknown`-specific copy.
- **`_set_meta_field` and `_stamp_revision` are two read-modify-writes of the same sidecar**,
  separate only because the first takes `_BACKUP_WRITE_LOCK` and the second runs inside it.
  Extracting a lock-free core used by both would make lock ownership structural instead of a
  docstring assertion. Not applied: 3 lines of duplication against refactoring a locked write
  path. Related and deeper — one `BackupMetadata` doubles as the on-disk record and the API
  view, so every write site must remember to strip the derived fields; a persisted-only sidecar
  model with the response composed from it makes that class unrepresentable.
- **`backup_dispatcher` lists the dump dir twice back to back** (`reverify_backups` then
  `apply_retention`) — ~19 sidecar reads + validations each, with nothing between them mutating
  the dir except reverify's own `integrity` rewrites. Having reverify return its refreshed list
  and `apply_retention` accept it would halve that; the ordering constraint is real
  (`_evict`'s most-recent-ok pin reads the integrity reverify just changed), so the list passed
  must be the post-rewrite one.
- **`_rebuild_meta` still can't recover `alembic_revision`** for a dump whose content is never
  re-confirmed. A targeted `pg_restore --data-only -t alembic_version -f -` decompresses one
  tiny block.
- **`status`/`schema_current` are populated only by `GET /admin/backups`.** PATCH, upload and
  restore declare `response_model=BackupMetadata` but return sidecar-derived objects, so those
  fields carry defaults. The card discards those bodies today — a contract trap, not a live bug.
- **A dump produced with `pg_dump --inserts`** emits `INSERT INTO public.alembic_version`, which
  the `COPY`-based parse doesn't read, so such an upload lists as `unknown` permanently.
- **A failed dump skips retention** (`backup_dispatcher` calls `apply_retention` after
  `create_backup`, and `check_disk_space` raises through it), so a volume under the floor can
  never be trimmed by the mechanism meant to bound it. Moving both tail calls into a `finally`
  fixes it; pre-existing, but the self-heal turns it from "the nightly cron fails" into "every
  restart fails".
- **`EChart` leaks its instance when unmounted before the first non-zero measurement** —
  `chart` is assigned inside the `ResizeObserver` callback but the cleanup disposes `chart?`.
  Pre-existing on `main`; capture `instance` in the `onMount` closure instead.
- **`EXPLAIN` the count-card query at prod scale.** Every measurement here is against the
  dev catalog; prod is ~2.5× that. The *selection* query was measured as plan-identical.
- **`alembic stamp head` asserts that the models and the migration chain agree, without
  checking it.** CI still never replays the chain, so a migration that drifts from the ORM
  stays invisible. Swapping `create_all` for `alembic upgrade head` would catch drift and match
  `docker/entrypoint.sh`, at the cost of migration runtime on every push.

## Manual verification (done in-browser during the session)
Every user-facing surface in this branch was exercised by hand:
- the Categories chart — a dimension swap grows the bars in from zero with no residue of
  the previous dimension, and a re-sort tweens in place without restarting;
- season and age labels land on `/ratings?tab=ratings` with the right filter and grid view;
- cumulative watch time at the default `1m` range — readable slope, flat left edge, and a
  plateau rather than an empty chart for a month with no ratings;
- the Backups card — `ok` / `schema outdated` / `unknown` pills, the live-revision
  reference in the controls row, and the per-row revision beside the size;
- the admin Overview SweepTiersCard at both grains, five rows summing to 100%.

Three of these were found *by* that hand-checking rather than confirmed by it — the ghost
bars, the cumulative chart's missing left-edge plateau, and the calendar-month vs 30-day
window question. The ECharts render path has no automated coverage (jsdom has no canvas),
and both animation bugs were invisible to `svelte-check` and vitest.

Operator notes for the deploy: the **first boot takes one extra backup** (no dump on disk
records a revision yet, so nothing is `ok`) — expected, one-time. The first sweep after
deploy moves ~46% of media onto the 180-day window, which is strictly *less* work. This
release changes `GET /admin/backups` from a bare list to an envelope, so both images must
move to this tag together.
