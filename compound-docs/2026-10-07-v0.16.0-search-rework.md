# v0.16.0 — search rework (running notes)

Raw notes, kept per block; `/pr` rewrites this into the template's shape.

## Title search becomes a fuzzy substring filter

**Before:** a title query ranked the whole catalogue by title-embedding distance minus
two literal bonuses (a flat ilike bonus, a scaled word_similarity bonus above 0.4), so
every query returned 50 rows, "xyzzy" included. The result set had no edge, which a
carousel or a "see all" page cannot work with.

**Now:** a row matches when a title variant (romaji, English, Japanese, the JSON text of
`other_names`; at anime grain the anime's own and every media's) contains the query
(ILIKE, score `1 + similarity`) or fuzzy-matches it (`word_similarity` ≥ 0.61, or ≥ 0.5
when nothing reaches 0.61). Substring hits rank first, then weighted score, then the PK. The anime grain decides the match in
HAVING (`GREATEST(anime variants, MAX(media variants))`) so the aggregates keep the
anime's full media set. Not Levenshtein (whole-string, length-penalised, unindexable),
not vector.

### Threshold study (dev DB: 1,231 anime / 4,888 media, read-only)

word_similarity compares the query's trigrams with those of the best contiguous stretch
of the title, as shared / (query ∪ stretch). A typo at the end of a word leaves one
unbroken run of matching trigrams ("frieran" → Frieren 5/8). A letter dropped or swapped
mid-word splits the match, and the stretch spanning both halves carries the title's
unmatched trigrams between them ("friren" → Frieren 5/10 = 0.5). The first write-up of
this study read it as plain k/n, which only holds for an unbroken run; the user's
"friren" exposed it.

| Query | Intended row | Best other row |
|---|---|---|
| frieran / toradra / overlrd / konosba | 0.625 (5/8) | ≤ 0.625 |
| friren · frieen · evnagelion · naurto (mid-word) | 0.50 · 0.57 · 0.55 · 0.43 | |
| one pice | One Piece 0.667 | One Punch Man 0.556 |
| clanad · vinlad saga · solo levling | 0.667 · 0.667 · 0.69 | |
| spy famly · evangelian · chainsaw men | 0.70 · 0.73 · 0.77 | ≤ 0.46 |
| demon slayr · kimetsu no yaba · hunter x huntr | 0.83 · 0.81 · 0.82 | |
| jujutsu kaisn · shingeki no kyojn · boku no hero academy | 0.86 · 0.89 · 0.90 | ≤ 0.43 |
| brotherhood (FMA:B is a media title) | FMA 1.38 via the media | Uchuu Kyoudai 0.583 |
| code gaess · mashel · hakyuu · bleech · akria | 0.545 · 0.571 · 0.571 · 0.429 · 0.333 — lost | |
| xyzzy · spreadsheet | — | Pokemon XY&Z 0.50 · 0.38 |
| jojo → Evangelion; death not → 16 rows; k-on → 57; dan da dan → 59 | | exactly 0.60 (3/5, 6/10) |

**T = 0.61**: above the 3/5 ratio where partial-word noise lands, below 5/8 where
end-of-word typos start. At the roadmap's suggested starting point of 0.5, "aot" returned every
"Ao …" title, "xyzzy" returned Pokemon XY&Z and "frieran" returned Tomodachi Game. At
0.65, frieran / toradra / konosba were lost. `> 0.6` does not work: word_similarity is
float4, and 0.6f promotes to 0.6000000238.

**Fallback to 0.5, only when 0.61 matches nothing** (the user's call, after "friren"
missed). Mid-word typos sit at 0.43–0.57, among the noise, so no single threshold keeps
both. At a flat 0.5, every query gained a weak tail ("frieran" +27 rows, "narut" +35,
"aot" → every "Ao …" title). The empty-only retry recovers "friren" (Frieren plus one
other row) and leaves every other search's edge alone. A nonsense query then shows
near misses ("xyzzy" → Pokemon XY&Z) instead of nothing. Each DAO runs its statement at
0.61, then at 0.5 if that was empty (`fetch_search_results`). A single query at 0.5
trimmed afterwards would be cheaper, but the trim is only correct while the match is
the primary sort key, which block 3's sorts break. Filters count toward "empty": if
filters exclude every 0.61 match, the 0.5 pass can surface weaker matches that pass
them. Edit distance would catch mid-word typos without the noise, but that is the
settled "not Levenshtein" decision.

Kept on purpose:
- "re zero": Digimon Adventure (substring "adventu·re zero two", 1.14) ranks above
  Re:Zero (fuzzy 1.00, because the colon breaks ILIKE). Promoting whole-word matches would
  flip the "Overlord of Darkness before Lord, of Ashes" precedence, which decides that a
  literal substring beats any fuzzy hit.
- "monstr": 16 substring hits outrank Monster (0.71).
- A typo in a short title can be lost even by the fallback ("akria" → 0.33).

### Latency

EXPLAIN ANALYZE on the anime query: ~125 ms for a hit, a typo or a miss alike, almost
all in the HashAggregate evaluating ~25k trigram calls over seq scans of both tables.
The embedding version cost ~50 ms SQL plus a ~30 ms encode on a query-cache miss.
Accepted without an index. The upgrade is a GIN `gin_trgm_ops` index plus a `%>`
candidate pre-filter (`pg_trgm.word_similarity_threshold` defaults to 0.6). Only the
admin completion card queries as you type (300 ms debounce).

### Other block 1 decisions

- Queries are stripped where they enter, by one `SearchQuery` type
  (`Annotated[str, StringConstraints(strip_whitespace=True)]`): the token schema's
  `query`, and the `query` param of `/search/anime`, `/search/media`, `/search/ratings`
  and `/search/mal`. The first draft also called `.strip()` in the three services and the
  `/search/mal` router; simplify moved it to the boundary. **FastAPI gotcha**:
  `query: SearchQuery = Query(default="")` silently drops the constraint, and only
  `Annotated[SearchQuery, Query(...)] = ""` (or no `Query` at all) honours it. The
  padded-query tests caught it. Add-library's `ScrapeJobRequest` strips via
  `model_config = ConfigDict(str_strip_whitespace=True)`, so `min_length` measures the
  stripped string. The roadmap claimed the add-library duplicate check ran on the raw
  string; it was already `lower(trim(...))` behind `ix_jobs_scrape_query`. Only
  `min_length` and the stored payload saw padding.
- The strict-then-loose retry lives in one helper, `fetch_search_results`, which every
  search DAO runs its statement through. The first draft looped in each DAO.
- `/search/ratings` title search scores **every** media, not just the user's rated ones:
  the match references only `Media` columns, so the planner pushes it into the media seq
  scan (~104 ms for users with 350 or 491 ratings alike). Left as is. No frontend page
  calls the endpoint yet, and the GIN index upgrade fixes it along with the rest. A
  fenced subquery of the user's ratings is the targeted fix.
- `/search/ratings` title search used to inner-join `media_search`, so rated media without
  an embedding vanished from it. It now uses the same match and joins nothing.
- Title embeddings are still written but no search reads them. Dropping them is a
  separate call, once fuzzy search has proven itself.
- Tests: the old "anime ranking is invariant to media count" test guarded the MIN over the
  title-embedding distance and went with it. The precedence test sets weighted score
  against the substring tier, so the fixture can't pass on the fallback. Every guard
  (substring tier, threshold, ilike case, other_names, HAVING vs WHERE, no embedding
  join, each strip) was sabotaged and seen to fail.

## Description search: literal first, then semantic down to a relative cutoff

**Before:** a description query ranked the whole catalogue by description-embedding
distance (AVG over the anime's media at anime grain), so it always returned 50 rows, and
a name lost to noise: for "shinji" ~240 unrelated rows sat closer than the first
Evangelion row.

**Now:** a media is a literal hit when every `\w+` token of the query starts a word of its
titles or description (`concat_ws` of title, name_eng, name_jap, the other_names JSON
text and the description; `~* '\m'‖token`). Literal hits rank first, then semantic hits
with `distance ≤ catalogue mean − SEMANTIC_MARGIN (0.30)`, each tier nearest first, PK
last. A media with an empty description has a NULL distance, so it is never a semantic
hit. When the strict pass returns nothing, one retry runs with every token at
`word_similarity ≥ 0.61`. The anime grain does `bool_or(literal)` / `AVG(distance)` in
HAVING. All three surfaces (anime, media, `/search/ratings` description) outer-join
`media_search`. Notes search stays purely semantic (no literal tier, no cutoff).
`fetch_search_results(db, *passes)` runs the first pass that returns anything: title
search passes one statement per threshold (`title_match_passes`), description search
the strict and the fuzzy statement (`description_passes`). `apply_vector_ordering` and
`_VECTOR_COLUMNS` are gone.

### Study, part 1 (dev DB, read-only: 1,231 anime / 4,888 media, every media embedded)

Literal test, media hits and full-scan latency:

| Test | izumi | rintaro | okabe | time travel | love | latency |
|---|---|---|---|---|---|---|
| ILIKE `%w%` | 19 | 7 | 9 | 65 | 380 | 22–26 ms |
| **word start `\m`** | **16** | **7** | **6** | **62** | **334** | **9–11 ms** |
| whole word `\m…\M` | 14 | 0 | 6 | 26 | 247 | |
| word_similarity ≥ 0.61 | 19 | 7 | 8 | 69 | 334 (friendship 607 vs 72) | 400–480 ms |
| FTS english, unindexed | 14 | 0 | 6 | 59 | 335 | ~265 ms |

ILIKE adds infixes of other names (Nishizumi, Kamiizumi; Chousokabe, Hokaben; glove,
beloved). Whole word and FTS lose prefixes (Rintar**ou**, travel**s**). FTS would also need a
GIN index (migration) to be fast.

Cutoff. An absolute D fails: a query's mean distance to the catalogue runs from 0.60
("shinji") to 0.93 ("cooking"). Short queries sit close to everything. Semantic-only media
admitted:

| Query | literal | D 0.45 | D 0.50 | D 0.55 | **mean − 0.30** | mean − 0.25 |
|---|---|---|---|---|---|---|
| shinji | 12 | 230 | 746 | 1,518 | **0** | 4 noise |
| izumi | 16 | 4 | 67 | 369 | **0** | 0 |
| xyzzy / spreadsheet | 0 | 0 / 0 | 2 / 0 | 4 / 0 | **2 / 2** | 4 / 5 |
| giant robots | 4 | 4 | 13 | 27 | **19** | 31 |
| a boy who can see ghosts | 0 | 0 | 7 | 17 | **17** | 47 |
| detective solves murders | 0 | 0 | 1 | 1 | **12** | 35 |
| friends start a band in high school | 4 | 0 | 2 | 2 | **9** | 18 |

At mean − 0.30 the survivors are relevant (Yami Shibai, Gakkou no Kaidan, xxxHOLiC, Yu
Yu Hakusho; Conan, Pluto, Kamonohashi Ron; BanG Dream, Euphonium, Bocchi). The
0.25–0.30 band is mostly noise (Sazae-san and Golden Time for "time travel"). Reading:
mean − distance = q̂·(d̂ − c), with c the catalogue's mean unit vector, i.e. cosine after
centering, the standard fix for hubness. The baseline is an unfiltered scalar subquery,
planned as an InitPlan (~5 ms).

Hubs: 249 media have `''` or NULL descriptions. Their "description" vector encodes the
title alone, and they topped every name query (Agami, Shirotan, Anpanman specials at
0.22–0.42 for "izumi" / "shinji" / "xyzzy").

Typo retry (empty-only, every token at word_similarity ≥ 0.61): izumii / izumy → 16,
okabee → 6, rintaru → 7, isekay → 21 media. It never fires on nonsense, which keeps ~2
semantic rows. At 0.5 it is noisy (shinjy → 273). ~0.4–0.55 s, on the empty path only.

### The literal tier reads titles too (after the user's app check)

"Though I Am an Inept Villainess" never says "villainess" in its synopsis, and its
semantic gap is 0.235 < 0.30, so a description-only literal tier lost it. Reading the same
text the vector encodes fixes that. Drift over ~50 queries, real DAOs, read-only:

- Better: villainess 13 → 17 anime / 15 → 28 media (P@10 1.0 both); isekai 16 → 49
  anime; 魔法少女 5 → 15 anime (P@10 0.2 → 0.8); 異世界 0 → 29 anime; isekay and
  villianess typos.
- Worse, small: a name prefixes a romaji title word ("shinji" → *Shinjiteita…*,
  *Shinjiau*; shinjy +5). Some top-10 swaps: magical girl anime P@10 0.9 → 0.8, death
  game media 0.5 → 0.4, vampire 0.8 → 0.7 (a label artifact: the added Mayonaka no
  Occult Koumuin is a vampire story).
- Per-field matching (every word inside one title variant or the description) instead of
  the concatenation: it drops cross-field noise (Tensura and Keroro for "time travel",
  Death March for "death game") but also relevant hits (Konosuba and Juniku Ojisan for
  "reincarnated in another world", a Tensura entry for the slime sentence). Four media
  P@10 values −0.1, two +0.1. A wash, so the simpler concatenation stays.

### Typo retry: Levenshtein, estimated (follow-up option)

"villianess" swaps letters mid-word. The real villainess rows score 0.467 in
word_similarity, below noise at 0.545 (Villager, *Easygoing Territory Defense*, *Heroes
Rising*), so no threshold separates them. Per-word Levenshtein (≤ 1 edit for 4–7 letters, ≤ 2
for 8+), checked offline on the same text: villianess → 27 media, izumy 14, isekay 88, okabee
6, rintaru 7, shinjy 24 (same noise as trigrams), xyzzy / spreadsheet 0. A transposition
counts as 2 (`fuzzystrmatch` has no Damerau). Tokenizing the catalogue takes 285 ms (522k
words, 34.6k distinct); with the C levenshtein, ~0.35–0.45 s per one-word query, about
what the trigram retry costs. Needs a `CREATE EXTENSION fuzzystrmatch` migration.
Matching against a materialized vocabulary would take ~10 ms, but needs a word table kept
current on every save and sweep. Not done; a candidate follow-up.

### Problem cases kept

- A far literal hit outranks a close semantic one: "friends start a band…" → Yano-kun
  (distance 0.92) before BanG Dream! Yume∞Mita (0.48).
- Words that co-occur by coincidence are literal hits: "found family" → Devil May Cry and
  Dandadan before Spy x Family.
- Common words flood the literal tier ("the" → every media, ordered by distance).
- The anime-grain AVG (settled) drops Conan for "detective solves murders"; its movies
  pass at the media grain. Before the cutoff, AVG only ranked such a franchise low.
- Typos find nothing unless they are at the end of a word (see Levenshtein above).

### Other block 2 decisions and gotchas

- Latency, EXPLAIN ANALYZE of the compiled anime statement: strict pass 22–36 ms, fuzzy
  pass ~400–420 ms. The baseline is a single InitPlan.
- The cutoff subquery is not correlated with the outer row because its FROM is explicit
  (`select_from(MediaSearch).join(Media)`). The first draft aliased both models "to
  prevent correlation"; sabotage showed the aliases changed nothing, so they went. Dropping
  the explicit FROM does correlate it (the mean becomes the row's own distance) and fails
  10 tests.
- `literal_binds` renders the bound regex `\mizumi` as `'\\mizumi'`, which Postgres reads as
  a literal backslash. Rewrite `'\\m` → `'\m` before psql, as with `ESCAPE '\\'`.
- The empty-description rule lives at read time (a CASE in the distance, and a Media join
  in the cutoff because of it). The defect is made at write time:
  `_compute_search_embeddings` stores `"{titles} "` as the "description" vector when there
  is none, for `AnimeSearch` too, which merge detection's title_desc signal compares.
  Storing NULL instead (nullable column, ~249 rows) would remove the CASE everywhere.
  Parked: a migration plus a backfill, and it changes merge detection's inputs.
- `description_passes` serves all three grains. `having=True` wraps the literal test in
  `bool_or`, the distance in `AVG`, and orders by `Anime.id`, so the tier rule exists
  once, as `title_match_passes` does for titles.
- `test_search_anime_description_query` asserted only `len >= 1` and passed because the
  old ordering had no cutoff; its media carry no description. Deleted, since the new tests
  cover the path. With it went the fixture embeddings in `test_search_anime.py`, which no
  remaining test read and which would have hidden a title path re-joining `media_search`.
- Tests assert their fixture distances against the cutoff first (computed the way the
  search does), on dev and on CI where the fixtures are the whole catalogue. Twelve guards
  were sabotaged and seen to fail: the literal sort key, word start, the empty-description
  rule, the outer join, the cutoff, literal-only, any-word instead of every word, the
  explicit FROM, the fallback (removed and always on), titles not read, HAVING → WHERE.

## Sorts and limit

`sort` (relevance, top_rated, score, popularity, added, release, title, random),
`sort_dir` and `limit` (1–1000, default 50) on `/search/anime` and `/search/media`, as
plain query params; sort joins the token in v0.16.1. `limit` is one `SearchLimit` on all
three search endpoints: `/search/ratings` drops its `le=200`, since its rows are one
user's library.

### Decisions

- **Every query sorts, description included** (the user's call, reversing the roadmap's
  "a description query always ranks by relevance"). The block 2 cutoff made the
  description set finite, so a sort orders it as it orders a title query's. The passes
  decide the set and the sort only replaces the ORDER BY. The strict→loose retry is
  unaffected, because whether a pass is empty doesn't depend on its order. The same
  params give the same list in a search and in a carousel. `relevance` is each query's
  own match order; without a query it is top rated (today's default) and ignores
  `sort_dir`.
- **Rejected: re-sorting a response in the browser when only the sort changes.** That is
  correct only below the limit. The response lacks `created_at`, the id tiebreak and the
  release key, and title order would need a JS twin of the `en_US` collation. A re-query's
  SQL costs ~20 ms.
- **Tiebreak**: key NULLS LAST → weighted score desc → PK in the sort's direction. A
  PK that follows the direction makes newest-first `created_at DESC, …, id DESC`, like
  `recency_order` (`rules/database.md` names the exception). It also makes the tie
  testable: insertion order is id asc, so only a descending tiebreak opposes it.
- **Release**: anime = `COALESCE(MIN(season) over unaired, TBA if any unaired undated,
  MAX(season) over aired)`; media = its own season, or TBA. `TBA_SEASON_KEY = 99_999`
  (years ≤ 2200). `SEASON_KEY` moved from `watchlist_dao` to `search_filters`.
- **Title**: `display_title` puts `NULLIF(…, '')` on both names to match
  `resolveTitle`'s falsy check; Japanese falls back to romaji. The roadmap spelled the
  NULLIF for English only.
- **Random**: `md5(uuid || UTC date)`, the date from `search_filters.utc_today()` so a
  test can move it. No API param, so everyone gets the same order.

### Study (dev DB, read-only: 1,231 anime / 4,888 media)

- Phase A, EXPLAIN ANALYZE, 3 runs each: top_rated, release asc/desc, title and random
  all take 17–21 ms at limit 50 and at 1000. The HashAggregate (~15 ms, the weighted
  means) dominates; the sort node is a 0.4 ms quicksort.
- Phase B (eager load + aggregates + DTO): anime limit 50 ≈ 80 ms; limit 1000 ≈
  0.6–0.7 s plus ~60 ms of DTO build, 737 KB of JSON. Media at limit 1000 ≈ 0.2–0.37 s,
  1.9 MB of JSON (descriptions), before GZip. Accepted, since see-all may load longer.
  The upgrade is a flat projection (`media_projections`) in place of `selectinload`.
- Data: no `''` names (122 anime / 1,320 media have NULL `name_eng`). Anime release
  buckets: 1,040 latest aired, 136 next announced, 55 TBA, 0 without a season. Media:
  64 TBA, 4 aired without a season.

### Problem cases kept

- Stale announcements: 4 media are still "Not yet aired" after their season has passed
  (e.g. Kaiju No. 8's Summer 2026 entry, seen in Fall 2026) and sort at that past season.
- Common description words plus a sort ("love" → 334 literal media) show the most
  popular of a loose set.
- Release descending opens with the 55 TBA anime, tied and ordered by weighted score.

### Tests and gotchas

- Release rows can't carry the sentinel season: a TBA media and a no-season row have
  none. So the release tests scope by a title token ("zqv"), which also covers title
  query + sort; `_ordered_fixture_titles(in_season=False)`.
- Every fixture row in a test shares `created_at`, because `now()` is the transaction
  start. The `added` tests set it explicitly.
- 32 guards sabotaged and seen to fail: each key, the default directions, NULLS LAST,
  the PK direction (both ways), the weighted secondary, NULLIF, the Japanese fallback,
  the language wiring at both grains, every release term and their order, the sort
  ignored or appended after the match order instead of replacing it, a query ignoring
  every sort and a relevance query sorted as top rated (both grains), limit not passed
  at either grain, the cap, and the random date and key.
- The sort replaces each pass's ORDER BY in `fetch_search_results`, the one place every
  pass goes through. The first draft overrode it per branch (an `order` kwarg on
  `description_passes`, an inline swap in the title branch); simplify moved it.

## Release reads the main story (block 3b)

An anime's release key reads `MAIN_STORY_RELATIONS` media only, in all three terms
(next announced, TBA, latest aired): the user's call, the readiness check's reasoning
(an announced OVA is not a season you wait for, a recap doesn't make a franchise fresh).
The media grain is unchanged; a side story sits at its own season.

- Dev DB: 271 of 1,231 anime change key. 262 move earlier, because a side story aired
  after the main story (Yu Yu Hakusho: OVA Fall 2018 → main Fall 1992; Umamusume: an
  announced Summer 2026 side story → Fall 2023). 6 lose a TBA side story, 3 shift
  otherwise. No anime lacks main-story media, so none ends with a NULL key.
- Test: one anime ("Zqv Recap") whose main story aired Spring 2012 and whose side stories
  aired later, are announced dated and announced undated. Each term that counted them
  would move it elsewhere; all three filters, plus a main-only media grain, were sabotaged
  and seen to fail.
- Open for block 4: `has_upcoming` mirrors the card's all-media flag, so an anime whose
  only announcement is a side story passes it yet sorts at its latest main season.

## Rejected: a title-vector fallback after the trigram passes (block 3b)

Asked for because "böse" finds nothing: no title contains it or is spelled like it, and
the multilingual embeddings no title search reads anymore would be the way in. Measured
on the anime title vectors, read-only, with the description cutoff's relative rule
(catalogue mean − margin):

| Query (trigram empty) | admitted at margin 0.30 | wanted among them |
|---|---|---|
| böse | 7 | 1 (Devilman, 2nd) |
| zauberin / drache / schwert / mädchen | 6 / 8 / 9 / 14 | 0 |
| bleech / akria | 5 / 8 | 0 (Bleach ranks 19th) |
| qwertz / spreadsheet / lorem ipsum | 5 / 0 / 0 | — |

Short-title hubs (Shuwawan!, Jormungand, Sirotan, Gill, Gleipnir) top every short query,
nonsense included, with the same gaps as a real hit, so no margin separates them. It is
the empty-description hub problem from block 2: a vector of a title alone sits near
every short query. Description search finds nothing for these words either; a lone
foreign word sits too far from every synopsis to clear its cutoff (~0.5–0.8 s on that
empty path).

Trade-off accepted: literal-only title search gives up the multilingual matching the
title embeddings offered, so a query in a language no title variant uses finds nothing.
If revisited, the fix is hub correction (CSLS: score each row against how close it sits
to every short query, from a stored per-row hubness score — a migration, a backfill and
an update on every save), not a margin.

## Catalogue filters (block 4)

`upcoming_main`, `top_percent` (1–100), `genre_mode` (default `all`) and `studio_mode` (default
`any`). The last three live on `MediaSearchFilters`, so `/search/ratings` honours them through
the shared `apply_media_filters`. `upcoming_main` lives on the new `CatalogueSearchFilters`
(anime + media endpoints and the token), which `/search/ratings` doesn't take. Tokens keep
`CURRENT_SEARCH_API_VERSION`: the new fields are optional, and an older token verifies to their
defaults.

### Decisions

- **`upcoming_main`, not the card's `has_upcoming`** (the user's call, "decide first" from 3b).
  It is the card's flag with the upcoming term limited to `MAIN_STORY_RELATIONS`: a main-story
  media not yet aired, in an anime with current or finished content. The card keeps its
  all-media flag. Named apart from `has_upcoming` so the two don't read as one field in the same
  response. A card-flag filter is additive later (v0.16.4 custom carousels), if wanted.
  `false` filters nothing (a toggle).
- **One definition for both grains**: `upcoming_main_media()` is the media-grain condition, and
  the anime grain keeps the anime holding such a media. It is a pre-filter of its own (like genre
  majority), not coupled to type/season. The roadmap's "hoist the three bool_or flags out of the
  airing-status branch" no longer applied once the term went main-only.
- **Top N% = the badge, by construction.** `top_percent_ranking(per_anime)` returns
  `(id, top_percent)` with the badge's rounding in SQL (`(rank·100 + total − 1) div total`,
  `rank()` so ties share their best rank). Both badges select it, and the filter compares it, so
  `top_percent=2` keeps exactly the rows whose hero chip reads 1% or 2% (the chip prints the
  integer as is). The ranking runs over the whole catalogue, unfiltered.
- **The media badge lost its single scan.** A count of better rows avoids the sort for one row,
  but the filter needs every row's rank. Measured: 50 ms (scan) vs 52 ms (rank), both dominated
  by numeric `log`, see below.
- **Studio `all` is coupled to the categorical filters** (the user's call, against the roadmap
  note). The anime's media that match type/season/source/relation together carry every
  selected studio, so both modes are one shape (`HAVING count(DISTINCT studio) >= N or 1`) and
  any ≡ all for a single studio. The roadmap's decoupled union broke that: toggling one studio
  plus `media_type=TV` any → all would have added 85 anime across the 15 biggest studios, and
  27 of their 105 pairs give different results with TV. Without a categorical filter the two
  readings are identical.
- **Float8 `log10` in `weighted_score_expr`** (the user's call). Numeric `log(10, x)` cost ~60×
  more per row and dominated every ordering by score and both badges. The `Numeric` cast in
  `_relation_weighted_mean` existed only for it. Still computed live. A stored generated
  `media.weighted_score` with an index, plus a per-anime aggregate kept on save, sweep, merge and
  split, is the upgrade past ~10× the catalogue.

### Study (dev DB, read-only: 1,231 anime / 4,888 media)

- `has_upcoming` definitions, anime: card flag 151 · main upcoming + any aired **122** · main
  upcoming + main aired 119 · main upcoming incl. never-aired 162 · wholly unaired 40. The 29
  between card and main-only announce only side content (Dragon Ball Super: Beerus,
  Toaru Anbu no Item, the new Higurashi TV, the SAO movie, Votoms and Crayon Shin-chan movies).
  Under the card's definition, "upcoming + release asc" opened with Votoms (1983), Minky Momo
  (1991), Crayon Shin-chan (1992); main-only leaves just the 4 stale announcements before the
  current season. Media grain: 128 unaired main media of aired anime (164 counting side stories).
- Top N%: 0 mismatches between the rank form and the single scan's count over 4,260 media; 0
  violations of the P = badge / badge − 1 boundary at either grain. 20 media and 5 anime sit
  exactly on a boundary, so `<` vs `<=` is observable.
- EXPLAIN ANALYZE, numeric log → float8 log10:

  | | numeric | float8 |
  |---|---|---|
  | anime Phase A, default sort | 21–27 ms | 3.6 ms |
  | media query, default sort | 57 ms | 2.8 ms |
  | anime / media badge | 17 / 52 ms | 3.6 / 3.4 ms |
  | anime / media + top 20% | 22 / 67 ms | 5.4 / 4.9 ms |

  Raw: `log(10, x)` over the scored media 81 ms, `log10(x::float8)` 1.4 ms. 0 of 1,105 anime and
  0 of 4,260 media change rank or top-percent. Studio any / all on the anime query ≈ 2.5 / 0.8 ms.

### Problem cases kept

- The 29 side-content announcements read "+ upcoming content" on their cards and fail
  `upcoming_main`.
- The 4 stale announcements pass and open "upcoming + release asc" at a past season.
- Wholly unaired anime fail at both grains (their card reads "Not yet aired"). A carousel of
  new shows *and* continuations can't be one filter set; it would be two carousels.

### Tests and gotchas

- Tests sit in `test_search_ranking.py` beside its helpers. Badge and filter share one
  expression and agree on any rounding, so the test first checks every fixture badge against a
  count done in Python. The first draft checked only the middle row: on the dev catalogue one rank
  is 0.09%, so `rank() − 1` and a ranking without the anchor moved it within its bucket and
  passed. The fix checks every row, including the out-of-season anchor, which tops every
  catalogue (score 10, 100M votes). `rank() − 1` reads 0 there, and a ranking over the filtered
  rows drops it. Three scored rows, so on CI's whole catalogue two of the three badges (34, 67)
  depend on rounding up; with four, every rank is a multiple of 25.
- 35 guards sabotaged and seen to fail on the final code: each upcoming term (main only, alternative version
  counted, unaired, both aired branches) and its wiring at both grains and in the router; the
  release key reading the shared `ANNOUNCED_MAIN_STORY`; `<=`, the ceil term, `rank()`'s base,
  unscored rows ranked at either grain, the ranking's population, the filter's wiring, the router
  param and its bounds; `needed` fixed at any and at all for genres at both grains and in the
  shared studio builder; DISTINCT; studio decoupled from the categorical filters; studio
  narrowing the joined rows (the no-rescope test); the media studio wiring; both mode params;
  natural log for log10; the token's parent and its `top_percent` bounds.
- Simplify review: one `_carrying_studios` builder serves both grains (the first draft wrote the
  anime grain's studio rule out again), and `ANNOUNCED_MAIN_STORY` is shared by the filter and
  the release key, which "closest to release" needs to agree. Kept on purpose: the test's hand
  count writes the ranked population out again, because sharing the builder would let a
  rescoped population pass. The aired test is the card's `current or finished` allowlist, not
  `!= Not yet aired`.
- The upcoming fixture announces an alternative version, so a `== Main` regression fails. The
  studio fixture's "Only X" has two media by X, so counting media instead of studios fails.
